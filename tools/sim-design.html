Section 1

What is actually on the site

The non-uniformity is not scattered. It is four codebases that never met. A widget's behaviour is predicted almost perfectly by which lineage it was born in.

Lineage 1 · Segment 1

5 pages · ~27 widgets · no shell at all

  • Every widget is hand-built markup with a bare .btnrow.
  • No frame, no title, no step counter, no narration slot.
  • One bespoke Focus button exists — .fqfocus on the float stepper — and nothing else has one.
  • .simbox here is a different component from .simbox in Segment 2.

4 pages · 15 widgets · half a shell

  • .simbox + .simhd + .focusb on 15 of them — the frame exists.
  • Narration .stepmsg on only 7 of 15.
  • No fitCv: the drawing never grows for a projector.
  • The strings page has none of it — no frame, no Focus, no Back.

  • Frame, Focus, narration and counter on all 50 — no exceptions.
  • Four engines: ChainSim, VarSim, ConvSim, TableSim.
  • Next / Back / Reset verified working on every one.
  • Cost: each page carries its own copy of the engine — eight copies to edit.

The one sentence

The fix is not 120 fixes. It is one shell with slots, seven stage types that plug into it, and one engine file that all 21 pages load — instead of eight copies and four traditions.

Everything below is about choosing what that one shell looks like.

Why this matters for the rewrite

Seven renderers cover everything, and four of them already exist in some form. The work is not inventing pictures — it is agreeing one frame so a student who learns to drive the array simulator in Week 3 can drive the AVL simulator in Week 13 without being taught again.

Section 4

Four parts that go into whichever shell wins

Each one fixes a specific thing you reported. They are independent of the layout choice.

fixes · loop passes not visible

The step rail, grouped by pass

Replaces 3 / 13. Every step is a segment; segments are grouped and labelled by loop pass; a condition step is tinted green or red. A student can see at a glance that the loop ran four times, and click straight into pass 3.

fixes · variable updates not visible

The watch strip

Every variable the code touches gets a chip. The chip flashes amber on the step where it changes, so nothing moves silently. Today only the nodes animate; LOC, C and the pointers change with no signal.

LOC4 C4 ITEM7
fixes · code highlight not uniform

Landing on the condition, every pass

The while and if lines get their own step each pass, tinted by the answer with a TRUE/FALSE tag. Currently 30 loop listings in Segment 1 and three of four Segment 2 pages never land on a condition at all.

2while LOC <= N:TRUE
3if DATA[LOC] = ITEM:FALSE
fixes · too small far away / too big to fit

Focus that enlarges type, not just the box

Focus today caps the drawing at 62% of screen height, so on a 768px projector many drawings come out smaller than on the laptop, while the code stays at 15px. The proposal: two columns above 1100px, code raised to 19px, and the height cap lifted because the stage no longer fights the listing for height.

My recommendation

B on the page, C in Focus. The deck gives the drawing the width it needs while you are teaching from the laptop, and Focus — which only ever runs on the projector — switches to the bench, where one dark surface at 19px is the most readable thing in a lit room. A is the fallback if you want the smallest possible change.

Whichever you pick, the four parts in Section 4 and the single shared engine file go in regardless.
