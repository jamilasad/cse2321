Where we are

Last class ended with a picture: four nodes scattered in memory, each one holding a value and the address of the next, and a variable called head holding the address of the first.

So far p->next has just meant “follow the arrow”. Today you find out what it really is. Nothing new is being invented — we are only putting names to a picture you already have.

1

Section 1

Every variable already has an address

⏱ 7 min

You already know that memory is a long row of numbered cells — we drew it in Segment 1, and again last class. So int x = 10; gives you two things: the value 10, and the cell it is kept in. That cell’s number is its address.

What is new today is one small thing: C++ will tell you that address if you ask, and the way you ask is &.

Three variables, and where they live
▸

Press Next step. Three variables are declared, and then we ask each one where it lives.

—

Read & as “the address of”

&x is said out loud as “the address of x”. It is not a copy of x and it is not 10. It is the number of the cell where the 10 is being kept.

Notice the variables sit in consecutive cells. That is the array idea from Segment 2, and it is exactly what a linked list refuses to require.

Real addresses look uglier than these

On the board I use small numbers like 104 so the picture fits. A real program prints something like 0x7ffee3b4a8 — a long hexadecimal number, and a different one every time you run it.

That is fine. You never care what the number is. You only care that two things have the same address or different ones.

The one thing to be careful about

C++ reuses & for several unrelated jobs: a & b is bitwise AND, a && b is logical AND, and int& r = x makes a reference.

Position tells you which is which. With a value on both sides it is an operator. Sitting in front of a single variable, as in &x, it means address of — and that is the only use we need today.

Check yourself — 1 of 6
You run the program twice. Both times it prints the value of x and the address of x. What do you expect?
The value is fixed; the address is not yours to choose. You wrote x = 10, so 10 is what you get, every run.

Where the operating system puts that 10 is its business, and it may pick a different cell next time. Modern systems even move things about on purpose, as a security measure, so that an attacker cannot predict where anything lives.

So never write a program that depends on a particular address. What you will actually use an address for is comparing it — asking whether two of them are the same, or whether one is the special “nothing” address you meet in Section 4.

Section 2

A pointer is a variable that holds an address

⏱ 8 min

An address is a number, and numbers can be stored. A variable whose job is to hold an address is called a pointer. That is the whole definition.

So a pointer is an ordinary variable in its own cell, with its own address. Its value just happens to say where something else is.

What actually goes inside a pointer
▸

Watch what actually goes inside p. It is not a copy of 10.

—

This is the most important sentence in the class

There is no arrow stored anywhere in memory. The arrow is just how we draw the number 104 sitting inside p.

Every arrow on the board is a number written down. That is why a linked list works at all: an address is data, so a cell can hold one.

Reading the declaration

int* p; reads as “p is a pointer to an int”. The star belongs to the type: the type of p is int*.

int* p, int *p and int * p all mean the same thing. Pick one. I write int* p, because the star goes with the type.

Watch out for this one

int* a, b; does not make two pointers. It makes a a pointer and b a plain int — the star sticks to the name, not the type. Declare pointers one per line and this never bites.

The type has to match, and the compiler will insist

An address is only a number, so you might expect any pointer to hold any address. C++ says no:

  int x = 10;
  double* q = &x;  ← does not compile

An address says where the data starts. It says nothing about how many bytes to read, or how to read them. That is the type’s job: int* means “4 bytes, a whole number”; double* means “8 bytes, a decimal”.

So the rule is: a pointer must be declared for the kind of thing it points at. That is why a node’s link is Node* next.

Check yourself — 2 of 6
After int x = 10; int* p = &x; — what is stored inside p?
The address of x. In the diagram above that is 104, so the cell labelled p literally contains the number 104.

It is not 10 — nothing was copied. And it is not “an arrow”: an arrow is not something a computer can store. The arrow is a drawing convention we use so that a page of addresses is readable by a human.

Hold on to this, because next class you will store an address inside a node, and that is the whole linked list.

Section 3

The star — going to the address

⏱ 8 min

Holding an address is half of it. The other half is going there. A * in front of a pointer means “not this pointer — the thing it points at”. That is called dereferencing.

It works both ways: you can read through a pointer, and write through one.

Reading and writing through p
▸

Watch the last step carefully. We never mention x by name, and x changes anyway.

—

Now the part that confuses everybody, and it is worth naming out loud rather than hoping you absorb it. The symbol * does two different jobs depending on where it appears.

In a declaration

int* p;

The star is part of the type. It says: p is going to hold the address of an int. Nothing is being dereferenced — p does not even have a value yet.

In an expression

*p = 99;

The star is an action. It says: go to the address inside p, and use whatever is there. Here it writes 99 into that cell.

A trick for telling them apart

Is there a type name beside the star — int, Node, char? Then it is a declaration, and the star means “pointer to”.

No type name means ordinary code, and the star means “go there”.

Why writing through a pointer matters so much

Reading through a pointer is convenient. Writing through one lets a function change something outside itself.

That is how a function can add a node to your list and have it still be there afterwards.

Check yourself — 3 of 6
After int x = 10; int* p = &x; *p = 99; — what does cout << x print?
99. The line *p = 99 does not touch p at all — p still holds the same address it always did.

What it changes is the cell that p points at, and that cell is x. So x becomes 99 even though the line never mentions x.

This is exactly how a function reaches out and modifies something it was only told about, rather than given a copy of. Compare it with p = &y, which changes p itself and leaves x completely alone. One star, entirely different outcome.

Section 4

nullptr — a pointer aimed at nothing

⏱ 6 min

A pointer has to hold something. Sometimes the honest answer is “nowhere”, and C++ has a value for exactly that: nullptr.

You have drawn it already — the dashed NULL box at the end of the list. It is not a node, and not an empty node. It is a pointer value meaning “this points at nothing”.

A pointer with nowhere to go
▸

The last step is the crash you have already seen in the delete animation. Now you will know why it happens.

—

Dereferencing nullptr is the crash

*p or p->data when p is nullptr means “go to address zero and read it”. Nothing is there, and the operating system will not let you look, so your program is killed on the spot — a segmentation fault.

It is not a compile error. The program builds perfectly and dies when you run it.

The habit that prevents most of these

Before *p or p-> anything, ask: could p be null right now? If it could, check first.

Every loop you have seen already does this:

  •  while (p != nullptr) — stop before dereferencing nothing.
  •  if (head == nullptr) — the empty-list branch in add-at-the-end.
  •  while (fast != nullptr && fast->next != nullptr) — and now you can see exactly why the order of those two tests matters.

nullptr, NULL and 0

Older code writes NULL, and older still writes plain 0. All three work, and your textbook and every past exam use NULL — so read it comfortably.

In new code use nullptr: NULL is really the number 0 in disguise, and can be mistaken for an integer. nullptr can only be a pointer.

In an exam, write whichever the question uses.

Section 5

A struct is a box with named parts

⏱ 7 min

Last class a node was drawn as one box split into two halves: the value on the left, the address of the next node on the right. A struct is how you tell C++ to make exactly that shape.

struct Node { int data; Node* next; };
→
datanext
one Node, two named parts

Read it as a sentence: a Node is a thing made of an int called data and a pointer-to-Node called next. The two halves of the drawing are now two named fields, and you reach them with a dot: n.data and n.next.

The strange part, which is the whole trick

A Node contains a pointer to a Node — a thing that refers to its own type. That sounds impossible, like a box inside itself.

It works because Node* next does not hold a Node. It holds an address, and an address is a fixed size — 8 bytes, whatever it points at. So a Node is 4 + 8 = 12 bytes, and the compiler can lay it out.

Write Node next; and it really is impossible: a Node holding a Node holding a Node, forever, with no size that works. The star is what makes a linked list possible.

Two small pieces of C++ housekeeping

The semicolon. A struct ends with }; — brace and semicolon. Forget it and the errors point at the line after the struct. If the compiler is angry about something that looks fine, check the line above.

Defining is not creating. struct Node { ... }; makes no nodes; it describes a shape, the way a recipe is not a meal. Node a; is the line that sets memory aside.

Your textbook draws the same thing differently

Lipschutz uses no structs. It stores a list as two parallel arrays: node k has its value in INFO[k] and the next node’s index in LINK[k]. Same idea, with indices standing in for addresses.

5 of the last 6 exams use that notation, so read it fluently — we drill it in Class 8. For today: INFO is data, LINK is next, START is head.

Check yourself — 4 of 6
Why must the link field be declared Node* next; and not Node next;?
Because of size. Ask how big a Node is. With Node* next the answer is easy: 4 bytes for the int plus 8 for the address, whatever that address happens to point at. The compiler can lay it out.

With Node next the answer is: 4 bytes, plus the size of a Node — which is 4 bytes plus the size of a Node, forever. There is no number that satisfies it, so the compiler rejects the definition outright.

The third option states something true, but it is a consequence of using a pointer rather than the reason for it. And the first is simply wrong: Node next; does not compile at all.

Section 6

Pointer to a struct — and the arrow at last

⏱ 9 min

Put the last two sections together. How do you get at data when all you hold is a pointer to the node?

You know both halves already: dereference to get the node, then take the field with a dot.

What it really means(*p).dataGo to the address in p to get the node, then take its data field. Correct, and awkward — those brackets are compulsory, because a dot binds tighter than a star.
=
What everyone writesp->dataExactly the same instruction, in a spelling built for humans. Same machine code, no brackets to forget.

That is it. That is the arrow you have been reading off the board for a week. p->data means “follow p, then take data”, and p->next means “follow p, then take next”. Every diagram in Class 1 was a picture of this operator.

Following the arrow, once and twice
▸

Two nodes wired together. Watch which cell lights up as the expression gets longer.

—

How to read a long chain of arrows

Read strictly left to right, one hop at a time, out loud:

p->next->data  is  “go to p’s node · take its next · go there · take its data”.

Every -> is one arrow travelled. Count the arrows in the expression and you have counted the nodes you move.

That is why fast = fast->next->next moves two nodes at a time. Not a special instruction — two hops on one line.

Dot or arrow? There is one rule

It depends only on what is to the left:

  •  a Node on the left → dot  a.data
  •  a Node* on the left → arrow  p->data

In a.next->data both appear, and both are right: a is a Node, a.next is a Node*.

Get it backwards and the compiler stops you. Say it a few times — node dot, pointer arrow.

Check yourself — 5 of 6
You have Node* p pointing at the first node of 10 → 20 → 30 → 40. What does p->next->next->data give you?
30. Count the arrows and walk them one at a time.

p is at 10. The first ->next hops to 20. The second ->next hops to 30. Then ->data takes the value out of that node, which is 30.

Two next hops means two nodes along from where you started, so you land on the third node, not the second.

A useful safety note for real code: this expression only works if both of those nodes actually exist. On a two-node list p->next->next is already nullptr, and asking it for data crashes — which is precisely the case the fast walker's loop condition is written to prevent.

Section 7

Build last week’s list, by hand

⏱ 11 min

Everything you need is on the table. Let us take the picture from Class 1 — 10 → 20 → 30 → 40 — and write the C++ that produces it.

Four nodes wired together, head on the first, and then the traversal loop you have read many times and can now run.

Four nodes, wired by hand
▸

Press Next step and watch the drawing from Class 1 assemble itself, one line of code at a time.

—
The whole program 
#include <iostream>
using namespace std;

struct Node {
    int   data;
    Node* next;
};

int main() {
    Node a, b, c, d;              // four nodes, four boxes

    a.data = 10;  b.data = 20;
    c.data = 30;  d.data = 40;

    a.next = &b;                 // the arrows you drew...
    b.next = &c;
    c.next = &d;
    d.next = nullptr;           // ...and the NULL at the end

    Node* head = &a;             // the head chip

    Node* p = head;
    while (p != nullptr) {
        cout << p->data << " ";
        p = p->next;
    }

    return 0;
}
Every line below corresponds to one thing you drew on the board in Class 1.
Node a, b, c, d; — four empty two-part boxes appear. [nothing is linked yet] a.data = 10; — write a value into the left half of a box. [a dot, because a is a Node] a.next = &b; — write b’s address into the right half. [this line IS the arrow] d.next = nullptr; — mark the end of the list. [the dashed NULL box] Node* head = &a; — a pointer holding the first node’s address. [the head chip] Node* p = head; — a second pointer to do the walking. [head stays put] p = p->next; — follow one arrow. [repeat until p is nullptr]
nodes created4 arrows drawn3 traversalO(n)

Look at what the loop condition is really doing

Three pieces, and you understand all three. Start p where head points. Keep going while p is on a real node. Move on with the address in this node’s next field.

When p reaches d, that next field holds nullptr, so p becomes nullptr, the condition fails, and the loop stops without ever asking nothing for its data. The dashed box was doing real work.

The dot-and-arrow line to check yourself on

a, b, c, d are Nodes → dot. head and p are Node* → arrow.

Same list, different punctuation, decided only by whether you hold the node or its address. If you can explain why a.next = &b and p = p->next are both right in one program, you have understood this class.

Check yourself — 6 of 6
In the program above, why is it a.next = &b; and not a.next = b;?
Because next is a Node*, so the only thing you may put in it is an address.

b on its own means the whole node — both of its halves. &b means the single number saying where b lives. Those are different types, so a.next = b; does not compile.

And that is a good thing, because it is the compiler enforcing the idea from §2: a node never contains another node, it only ever contains where to find one. If nodes could contain nodes, a linked list could not exist.

What you still cannot do

⏱ 6 min

That program works — but we had to know there were exactly four nodes and name every one of them before it ran. A list whose whole point is that it grows cannot be built that way.

So let us do it properly: one global head for the list, and a function that adds a node at the front. Three lines, straight from Class 1.

A modular version — and why it fails
▸

This compiles with no warnings at all. Watch where it goes wrong.

—

The node dies when the function ends

A variable declared inside a function lives only until that function returns. Its memory goes straight back and gets reused by whatever runs next.

So head is left holding the address of a box that is no longer yours. Every line is legal C++ and the compiler says nothing — which is what makes it so hard to find.

What is actually needed

Memory that outlives the function that asked for it, and stays yours until you say otherwise.

C++ has exactly that: the heap. You ask with new and give back with delete. That is next class — and it is the last idea a linked list needs.

Exam & Interview · Segment 3 Class 2

Where today actually counts

Let me be straight with you: pointers are not a topic on your CSE-2321 exam. Not one question in the last six exams asks what a pointer is. Today still matters — just not in the way the other classes do.

Be honest about it

Not examined — and unavoidable anyway

CSE-2321 is a data structures course, not a C++ course. The exam asks you to define a linked list, compare it with an array, write a procedure, fill in an INFO/LINK table. None of those questions contain the word “pointer” as the thing being tested.

So why did we spend an hour here? Because every single one of those answers is written in this notation. Today is not a topic, it is the alphabet the rest of the segment is written in.

But: “each node has an information field and a link field, and the link field holds the address of the next node.” That word address is what you learned to justify today.

Which should you write in the exam?

Whichever the question uses. If it says “Let LIST be a linked list in memory” and mentions INFO and LINK, answer in that notation — it is what the marking scheme expects.

Where marks really go

Four exam mistakes that are pointer mistakes underneath

1. Losing the rest of the list

In insert-at-position, writing prev->next = newNode before newNode->next = prev->next. The moment prev’s next cell is overwritten, the address of the rest of the list is gone, and no variable anywhere is holding it.

You saw this in Class 1 as “grab the rest of the list first”. Now you can say why: that cell held the only copy of an address, and you wrote over it.

2. Walking one step too far

Add-at-the-end with while (p != NULL) instead of while (p->next != NULL). The loop ends with p holding nullptr, and then p->next = newNode tries to write into a node that does not exist.

3. Forgetting the empty list

Any procedure that begins p = head and immediately asks for p->data or p->next is wrong when the list is empty, because head is nullptr. A single line — if (head == NULL) ... — is frequently worth a mark on its own.

4. Testing in the wrong order

while (fast->next != NULL && fast != NULL) dereferences fast before checking it. You now know precisely why that is fatal, and why swapping the two halves fixes it.

The single question to ask yourself

Every one of those four is the same question, unasked: “can this pointer be null right now, and does anything still hold the address I am about to overwrite?”

Ask it before every -> and before every assignment into a next field, and most of the ways to lose marks on a linked-list question simply stop being available to you.

Beyond the exam

Pointers in an interview

The reverse of the exam situation applies here. Pointers are not a footnote in interviews — for any job involving C or C++ they are among the most heavily probed topics there is, and the questions are almost all versions of what you saw today.

In an interview

💼“What is the difference between a pointer and a reference?” asked constantly
A pointer is a variable holding an address. It can be reassigned to point somewhere else, it can be null, and you must dereference it with * or ->.

A reference (int& r = x;) is another name for an existing object. It must be bound when it is created, it can never be rebound, it cannot be null, and you use it exactly as if it were the object itself.

The line that shows you actually understand it: “a reference is what you use when the thing definitely exists and will not change identity; a pointer is what you use when it might be absent or might move.”

You have already met a reference-to-pointer, Node*& head, in the C++ tabs — it means “the actual head variable, not a copy, so that I can change where it points.”
💼“What is a dangling pointer? A wild pointer? A memory leak?” the three classics
Dangling — it points at memory that used to be valid and no longer is. Exactly §8: the local node died and head kept its address.

Wild — it was never initialised at all, so it holds whatever rubbish was in that cell. int* p; with no value, then *p = 5. Always initialise a pointer, to nullptr if you have nothing better.

Leak — you asked for memory and lost the only address that could give it back, so nobody can ever free it. That one needs new, so it belongs to next class.

The tidy summary: a dangling pointer is memory freed too early; a leak is memory never freed at all.
💼“Why does this function not change my variable?” the debugging one
C++ passes arguments by value — the function gets a copy. Change the copy and the original is untouched. This is the single most common bug of a first C++ month.

Three ways out, and you should know all three: pass a pointer (void f(int* p), then *p = 9), pass a reference (void f(int& r), then r = 9), or return the new value and assign it at the call site.

Section 3 is the reason the first two work: writing through a pointer reaches the original, because the address is the original’s address.

This is also why linked-list functions take Node*& head rather than Node* head — inserting at the front has to change head itself, and a copy of head would be thrown away when the function returned.
💼“How big is a pointer?” the sneaky one
8 bytes on a 64-bit machine, 4 on a 32-bit one — and crucially, the same size whatever it points at. A char* and a Node* are both 8 bytes, because both hold an address and addresses are all the same size.

This is the fact that makes Node* next inside a Node legal, as you saw in §5. It is also the honest cost of a linked list: an int is 4 bytes but its link field is 8, so a list of ints spends more memory on the links than on the data. That is the standard “disadvantage of linked list” exam point, with a real number attached to it.

If you rehearse one thing from today

Be able to say, in your own words and in under thirty seconds: what a pointer holds, what & and * do, what nullptr means, and why a Node contains a Node* rather than a Node.

That last one is the whole reason a linked list can exist, and it is a genuinely good answer to give when someone asks you to explain the data structure.
