Where we are

You spent three classes on arrays. You learned one formula, and it gave you O(1) reading.

Today you learn what that formula costs — and what you are forced to build when memory refuses to pay it. One line of revision before we start: a pointer is a variable that holds an address. That is all you need today.

1

Section 1

The array wants one unbroken block

⏱ 6 min

Before we leave arrays behind, put their costs on the board. You proved every one of these in Segment 2:

read A[i]O(1) searchO(n) insertO(n) deleteO(n) sizefixed

One O(1) and three O(n)s. That single good number comes from one rule: an array is one block of memory, decided in advance, every cell beside the last — so A[i] is found by one calculation: Base + i × w. That calculation is the whole reason reading is instant.

This rule costs more than it first appears. Below is a piece of real memory. Other programs are already using some of the cells. The free cells they left behind are not next to each other.

Looking for four cells in a row
RAM · 16 cells

The orange block below is an array of 4 integers. It needs 4 free cells side by side. Press Try to fit it to move it along the memory.

—

The problem, in one line

Eleven cells are free. The array needs four in a row. The longest row is three. It does not fit.

There is enough free memory in total. There is not enough free memory in one continuous block. This situation has a name: fragmentation.

Problem A — it might not fit

Programs start and stop all the time, and each one leaves a gap of free cells behind. So free memory ends up split into many small gaps.

An array must fit inside one single gap. If no gap is large enough, the array cannot be created — even when the total free space is more than enough.

Problem B — it cannot grow

You must decide the size before you start.

If you choose too small, adding one more item means finding a bigger block and copying every element into it — that is O(n), every time it happens. If you choose too large, the extra cells are never used.

Both problems come from the same rule: one unbroken block, committed up front. So here is the question that starts everything today:

The question

Could we store the four values in the gaps we already have — and still know what order they are in?

Check yourself — 1 of 5
Memory has 11 free cells, but the longest unbroken stretch is 3. Can you create an array of 4 integers?
No. Total free space is not the test. An array needs one unbroken run as long as the array, because A[i] is found by the formula Base + i×w — and that formula is only true if cell i+1 really does sit right after cell i.

Reading speed is not the issue here. The allocation simply fails.

Dig deeper

?Does this really happen on a modern computer?
Less often than this picture suggests, and it is worth knowing why. Your program does not see physical RAM directly. It sees a virtual address space, and the operating system maps those virtual pages onto scattered physical frames. So a large array can look continuous to your program even when physical memory is not.

It still matters in three real cases: embedded systems with no MMU, kernel buffers for hardware (DMA), which must be contiguous in physical memory, and 32-bit programs, where the virtual address space itself runs out of large gaps.

And Problem B never goes away, on any machine: growing an array still means allocate-bigger-and-copy.

The key question of this class

RAM does not store lines. It only stores numbers. So how do we store this line?

Everything that follows — the second cell, head, the node, the whole data structure — is forced by that one question. Answer it and you have invented the linked list.

Think before you scroll

We need one number, stored somewhere in memory, that says “the next value is over there.”

A cell holds a number. Which number would identify a location?

The answer

The number that identifies a location is its address. So beside each value we take one more cell and write in it the address of the next value.

The imaginary line becomes a real number, sitting in real memory.

Two cells per value

One for the value, one for the address of the next value. They sit side by side because we asked for them together.

The arrow is a number

There is no arrow in memory. The arrow on the screen is just us drawing what the number means.

head is not a node

Check yourself — 2 of 5
Cell 105 holds the number 101. What does that number mean?
The next value is stored at address 101. It is a location, not a value and not a position.

Go and look at cell 101 and you find 20. That indirection — a number that tells you where to look rather than what the answer is — is the entire idea of a pointer, and the entire idea of a linked list.

Dig deeper

?Is one cell really enough for an address?
On this page every cell is drawn the same size, which keeps the picture clean. Real memory is not so tidy: on a 64-bit machine an int takes 4 bytes and an address takes 8. So the “address half” of a node is usually twice the size of the data half.

That matters for one exam point: a linked list of int can use three times the memory of an array of the same numbers. Keep the simple picture for now — but remember the real cost when you are asked for the disadvantages.
?Why not store the position number instead of the address?
Because a position number only means something if the values are already in order in memory — and Section 2 showed you exactly what that is worth here. Memory reads 20, 10, 40, 30. Position 3 of what?

An address needs no block and no ordering. It works no matter where in memory the next value happens to be, which is precisely why it survives the scattering.
?Where do those free cells actually come from?
The operating system keeps track of which parts of the heap are free — and it keeps that record as a linked list of free blocks. A linked list, used to hand out the memory that linked lists are made of.

Your textbook gives this free list a name: the AVAIL list. When you write new Node in C++, you are taking a node off AVAIL; when you write delete, you are giving it back. We meet both properly in Class 3.

Definition — learn this line

A linked list is a collection of nodes. Each node has two parts:

1. the data part — the value we want to store
2. the next part, also called the link field — the address of the next node

One separate variable, called head (the textbook calls it START), holds the address of the first node. The last node's next part holds NULL, which signals the end. head = NULL means the list is empty.

An important reminder

The tidy picture is a convenience, not the truth.

The nodes are still at 104, 101, 112 and 108: scattered, out of order, exactly where memory put them. The arrows are still only numbers stored in cells.

Whenever the tidy diagram starts to feel like the real thing, press Show me the RAM again. That button will stay useful for the whole segment, not only today.

Check yourself — 3 of 5
Why can the nodes of a linked list sit anywhere in memory, in any order?
Because each node carries the address of the next one. The order is stored inside the data, not in where the data sits.

An array stores order by position, so its cells are trapped side by side. A linked list stores order by address, so its nodes are free — which is why memory could read 20, 10, 40, 30 and the list could still read 10, 20, 30, 40.

Section 5

Reading it — traversal

⏱ 7 min

An array gives you A[3] instantly. A linked list gives you nothing instantly. There is no formula — the only way to reach a node is to start at head and follow the arrows. That walk is called traversal, and every other operation is built on it.

Walking the list
PRINT(head) — print the data in every node.
1. p = head [start at the first node] 2. while p != NULL: 3.    print p->data 4.    p = p->next [to the next node]     [End of Step 2 loop.] 5. Exit.
▸

Press Walk and watch p move along the arrows. The live step is marked beside it.

—
reach node kO(n) print allO(n) extra memoryO(1)
Traverse & print Reference — you will write this in Class 2
void print(Node* head) {
    Node* p = head;
    while (p != nullptr) {
        cout << p->data << " ";
        p = p->next;
    }
}

There is no A[i] here

To reach the 4th node you must touch the 1st, 2nd and 3rd on the way. Reaching node k costs k steps, so in the worst case it is O(n). The array does it in one step.

One walker is enough

However long the list, traversal needs exactly one extra variable — p. That is O(1) extra memory. Never copy the list to walk it.

The mistake everyone makes once

Writing p = head->next inside the loop instead of p = p->next. Then p jumps back to node 2 every single time and the loop never ends. The walker must move from where it is, not from the start.

Check yourself — 4 of 5
A sorted linked list has 1000 nodes. Can you use binary search on it?
No. Binary search needs O(1) access to the middle. In an array the middle is A[(low+high)/2] — one formula, one step. In a linked list, reaching the middle means walking 500 nodes.

You could still do it, but every “jump” would cost O(n), which destroys the whole point. Your textbook says it in one line: “binary search cannot be applied to a sorted linked list, since there is no way of indexing the middle element.” Knowing the length does not help.

In an interview

💼“Walk the list and compute something” — one pattern, many questions also examined
Once you can traverse, a whole family of questions is the same three lines with a different middle. Past exams have asked for a procedure to find the maximum value, the maximum even value, the sum of values under a limit, and to add an item at the end.

Recognise the shape and you never have to think about it again:
p = head  →  while p != NULL  →  do the thing with p->data  →  p = p->next

In an interview they will call the same skill “iterate the list” and use it as a warm-up before the real question.

Section 6

Inserting — first, last, and at a position

⏱ 13 min

This is what we came for. In an array, inserting means moving everything. In a linked list, nothing moves — we only redraw arrows. There are exactly three cases, and they are the three your Autumn 2025 exam asks for by name.

Inserting into the list
Insert first
Insert first — put a new value at the beginning of the list.
1. Create a node — call it newNode — and put the value in it. 2. newNode->next = head [the new node points where head was pointing] 3. head = newNode [head now points at the new node]
Insert last — put a new value at the end of the list.
1. Create newNode, put the value in it, and set newNode->next = NULL. 2. Find the last node — call it LN. [walk from head until next is NULL] 3. LN->next = newNode
Insert at position n — put a new value so that it becomes the n-th node.
1. Find the (n−1)th node — call it prev. 2. Create a node — call it newNode — and put the value in it. 3. newNode->next = prev->next [grab the rest of the list first] 4. prev->next = newNode [only now may prev let go]

Insert first Reference — you will write this in Class 3
void insertFirst(Node*& head, int item) {
    Node* nw = new Node;  nw->data = item;
    nw->next = head;
    head     = nw;
}
void insertLast(Node*& head, int item) {
    Node* nw = new Node;  nw->data = item;  nw->next = nullptr;
    if (head == nullptr) { head = nw; return; }
    Node* LN = head;
    while (LN->next != nullptr) LN = LN->next;
    LN->next = nw;
}
void insertAt(Node*& head, int pos, int item) {
    if (pos == 1) { insertFirst(head, item); return; }
    Node* prev = head;
    for (int i = 1; i < pos - 1 && prev; i++) prev = prev->next;
    if (!prev) { cout << "invalid position"; return; }
    Node* nw = new Node;  nw->data = item;
    nw->next   = prev->next;
    prev->next = nw;
}

Insert at position n — steps 3 and 4 must be in this order

Suppose you write step 4 first: prev->next = newNode. Now prev points at the new node, and nothing points at the rest of the list any more. There is no way to reach it again.

Step 3 then runs: newNode->next = prev->next. But prev->next is now the new node itself, so the new node points at itself.

Rule: connect the new node to the list before you disconnect the old link. This is the most common linked-list mistake there is.

Autumn 2025, Q3(c) asks for insertion at a given position that runs in O(1) at the beginning or end and O(n) at an intermediate position, handling invalid positions. Two of those three you can now write. O(1) at the end needs one more thing — a tail pointer, which we add in Class 5. Without it, insert-last is O(n) and no amount of clever code changes that.

Check yourself — 4 of 5
You want to insert a value at position 500 of a 1000-node linked list. What does it cost?
O(n). This is the distinction that separates a full-marks answer from a half-marks one.

The rewiring is genuinely O(1) — two assignments, no shifting. But you must first walk 499 nodes to get there, and that walk is O(n). End to end, inserting at an arbitrary middle position is O(n) in a linked list and O(n) in an array.

The linked list wins when you are at the front, or when you are already standing on the node — not when you have to go looking.

Section 7

Deleting — first, last, and the n-th

⏱ 11 min

Delete is the mirror of insert, and it has the same three cases. There is one new idea, and everything about singly linked lists follows from it:

To remove a node you must stand in front of it

A node only knows what comes after it. Nothing points backwards. So to unhook node X you need the node before X — we always call it prev — because the only thing you can change is prev->next.

That single limitation is why delete needs a walk, why the two-way list exists, and why prev appears in every delete algorithm you will ever write.

Deleting from the list
Delete first
Delete first — remove the node at the beginning.
1. Let FN be the first node. [FN = head] 2. head = FN->next [head skips over it] 3. delete FN [give the two cells back to memory]
Delete last — remove the node at the end.
1. Walk to the (n−1)th node — call it prev. [stop when prev->next->next is NULL] 2. last = prev->next [take hold of it before unhooking] 3. prev->next = NULL [the list now ends one node earlier] 4. delete last
Delete the n-th node — remove the node at position n.
1. Walk to the (n−1)th node — call it prev. 2. cur = prev->next [take hold of the node we are removing] 3. prev->next = cur->next [step straight over cur] 4. delete cur

Delete first Reference — you will write this in Class 3
void deleteFirst(Node*& head) {
    if (head == nullptr) return;      // empty list
    Node* FN = head;
    head = FN->next;
    delete FN;
}
void deleteLast(Node*& head) {
    if (head == nullptr) return;
    if (head->next == nullptr) { delete head; head = nullptr; return; }
    Node* prev = head;
    while (prev->next->next != nullptr) prev = prev->next;
    Node* last = prev->next;   // step 2 — hold it first
    prev->next = nullptr;
    delete last;
}
void deleteAt(Node*& head, int pos) {
    if (head == nullptr) return;
    if (pos == 1) { deleteFirst(head); return; }
    Node* prev = head;
    for (int i = 1; i < pos - 1 && prev->next; i++) prev = prev->next;
    Node* cur = prev->next;
    if (!cur) { cout << "invalid position"; return; }
    prev->next = cur->next;
    delete cur;
}

Why two of the three are O(n)

Look at the last column. In every case the rewiring is O(1) — one or two assignments, and no element ever moves.

What costs time is finding prev. Delete-first is fast only because head already points at the node we want, so there is nothing to search for. Everywhere else we have to walk, and the walk is O(n).

In Class 7 you will meet a list where every node also stores a link backwards. In that list prev is free, and this problem disappears.

Dig deeper

?Why not just “delete the node you are standing on”?
Because you cannot. Standing on node X, you can reach X->next and everything after it — but the node pointing at X is invisible from where you are. Unhooking X means changing somebody else's next, and you have no way to reach that somebody.

There is a famous trick: copy the next node's data into X and delete the next node instead. It works — except when X is the last node, where there is no next to copy. Interviewers like this one precisely because of that edge case.
?What happens to the cells after “delete”?
They go back to the free list — the same one Section 3 mentioned. Your textbook calls it the AVAIL list, and writes the step as LINK[LOC] := AVAIL; AVAIL := LOC, which is exactly “put this node at the front of the free list”. It is an insert-first, on a different list.

In C++ that whole idea is one word: delete. Forget it and the cells are never reused — a memory leak. In Java or Python a garbage collector does it for you, which is convenient and costs you the control. Class 3 and Class 6.

In an interview

💼Reverse a linked list — and why it is really just insert-first LeetCode 206
The most asked linked-list question anywhere. And you already have the answer: take nodes off the front of the old list one at a time and insert-first each one into a new list. The first taken ends up last; the last taken ends up first. That is a reversal, with no new nodes.

Written out, it is four lines — and it is the standard answer interviewers expect, just with different names (newHead is usually called prev, and head is called curr):

nxt = head->next  →  head->next = newHead  →  newHead = head  →  head = nxt

If you can explain why saving nxt must come first, you have answered the follow-up they always ask.

Not examinable at IIUC — reverse has never appeared in a CSE-2321 exam. We build it properly in Class 5, once the code is in place.

Which is better for searching, and why?

This exact question comes up again and again. The array. For an unsorted collection both are O(n), but the array reads sequential memory and is faster in practice. For a sorted collection the array wins outright — O(log n) by binary search, against O(n) for the list, because a linked list has no way to index the middle element.

In an interview

💼Why do real programs use arrays even when Big-O says otherwise?
Big-O counts operations. Hardware cares about where the data is.

When the CPU reads one array element it pulls a whole cache line — typically 64 bytes, so around 16 ints — into fast memory. The next 15 reads are then nearly free. An array traversal is a straight run through memory and the hardware prefetcher predicts it perfectly.

A linked list loses all of that. Each node may sit anywhere, so every p = p->next can be a cache miss — and a cache miss costs roughly a hundred times more than a cache hit. This is why std::vector is faster than std::list for most real programs, even for insertions in the middle, until the lists become very large.

Saying this in an interview marks you out immediately: “asymptotically they're the same, but the array wins on cache locality.”

Your own slides already list “better cache locality” as an array strength — so this one is fair game in the exam too.

Model answer

★Full marks — and why each sentence earns its mark
Definition. A linked list is a linear collection of data elements called nodes, where the order is maintained by links rather than by position. Each node has two parts: the information part, which holds the data, and the link field (next pointer), which holds the address of the next node. A separate pointer variable START (or head) holds the address of the first node, and the last node's link field holds NULL, marking the end. START = NULL means the list is empty.

Memory structure. An array occupies one unbroken block of memory, with elements side by side, so element k is found by the formula Base + k×w. A linked list's nodes may be scattered anywhere; the order is carried by the addresses stored inside the nodes. As a result an array's size is fixed in advance, while a linked list can grow and shrink one node at a time.

Operations. Reading the k-th element is O(1) in an array but O(n) in a linked list, which must be traversed from START. Inserting or deleting at the front is O(n) in an array, because every element must shift, but O(1) in a linked list, because only two links change.

Which is better for searching — and why. The array. If the data is unsorted, both take O(n), but the array's elements are contiguous so it is faster in practice. If the data is sorted, the array can use binary search in O(log n), while a linked list cannot — there is no way to index the middle element, so it is stuck at O(n).

Cost of the linked list. It needs extra memory for the link field in every node.

You will not have time to write all of this for 2 marks. Write the definition, one line on memory structure, one line on operations, and the searching verdict with its reason. The rest is what turns a 1.5 into a 2.
⚠The three ways students lose this mark
1. Saying “linked list is faster for insertion” and stopping there. Faster where? At the front, yes. At an arbitrary position, both are O(n). An unqualified claim reads as a half-understood one.

2. Forgetting the question asked about memory structure. Spring 2025 asks for it by name. Contiguous block versus scattered nodes joined by addresses — say it explicitly.

3. Giving no reason for the searching answer. “Array is better” earns nothing on its own. The reason is the mark: binary search needs indexing, and a linked list has none.

Asked twice

Insert at a given position

4 marks

Autumn 2025 · Mid Term · Q3(c) · 1 + 2 + 1 marks

“Write an algorithm or program to insert a node into a singly linked list at a given position (pos, starting from 1). Your solution should:
• Insert in O(1) time if inserting at the beginning or end
• Insert in O(n) time when inserting at any intermediate position
• Handle invalid positions appropriately.”

Read the question again

The exam is telling you the complexity distinction from §9. Beginning is O(1). Intermediate is O(n). And O(1) at the end is only possible if the list keeps a tail pointer — which is exactly why we add one in Class 5. A list with no tail cannot satisfy this question.

Model answer

★The structure the examiner is looking for
Handle the cases in this order — it is also the order that makes the code shortest:

1. Invalid position. If pos < 1, or pos is greater than length + 1, print an error and exit. Say in one line how you know the length — either you keep a counter, or you discover it while walking.

2. pos = 1 — the beginning. This is insert first from §6: newNode->next = head; head = newNode. O(1), because head is already in your hand.

3. The end. Without a tail pointer this is the insert last of §6: walk to LN, then LN->next = newNode — that walk makes it O(n). To satisfy the question's O(1) you must keep a tail pointer and say so: tail->next = newNode; tail = newNode. Class 5.

4. Any intermediate position. Exactly §6's third case: walk pos − 1 steps to reach prev, then newNode->next = prev->next; prev->next = newNode. The rewiring is O(1); the walk makes the whole operation O(n). Say which line does which.

Finish with one sentence naming the complexity of each case. The marks for “O(1) / O(n)” are awarded for saying so, not for the code alone.

You can already write two of the three

§6 gives you all three cases — insert first (O(1)), insert last (O(n) without a tail) and insert at position n (O(n)). The only gap is the question's demand for O(1) at the end, which is impossible without a tail pointer. That is Class 5, and it is worth writing one sentence saying so: an examiner would rather read “O(1) at the end requires a tail pointer to be maintained” than a wrong claim.

One sentence that earns marks in half these questions

“The rewiring is always O(1). What costs O(n) is finding the node — and only first needs no searching, because head already points at it.”

Write that once and every complexity in the table follows from it.

Watch for this

⚠Two lines that must be in this order — and the marks they cost
In insert at position n: newNode->next = prev->next must come before prev->next = newNode. Reverse them and the rest of the list is unreachable, and the new node points at itself.

In delete: cur = prev->next must come before prev->next = cur->next. Reverse them and you have no way to reach the node you were supposed to delete — a memory leak in C++, and a wrong answer in the exam.

Both are the same rule: take hold of what you need before you let go of it. Examiners look for it, and interviewers ask about it directly.

Beyond the exam

Interview corner

Nothing in this card can appear on a class test. It is here because you will be asked it in a job interview, and because the first-round DSA question at almost every software company in Chittagong and Dhaka is a linked-list question.

From today's class

💼“What is the difference between an array and a linked list?” warm-up
This is the same question as the exam's, and it is the standard opener — they use it to see whether you think in trade-offs or in memorised lists.

A strong 30-second answer: “An array is one contiguous block, so indexing is O(1) and it has excellent cache locality, but its size is fixed and inserting means shifting. A linked list scatters nodes and joins them with pointers, so it grows freely and inserts at a held position in O(1) — but indexing is O(n), it costs an extra pointer per node, and pointer chasing wrecks cache performance. In practice I'd reach for a vector unless I specifically need O(1) splicing.”

That last clause is what separates a student answer from an engineer's.
💼“Reverse a linked list” LeetCode 206
Covered in the interview box in §7. It is the single most-asked linked-list question. Be ready to write it iteratively, explain why saving next must come first, and then give the recursive version if asked.
💼“Why is std::vector usually faster than std::list?” senior signal
Covered in §8, and you can now see it: press Watch on the “insert in the middle” row. Both sides are O(n), but the array copies neighbouring cells — which hardware is very good at — while the list follows scattered pointers. The answer is cache locality, not Big-O.

Coming in later classes

💼The two-pointer family Class 4
One idea — a fast pointer and a slow pointer — answers three separate interview questions: find the middle of a list (LeetCode 876, and on two of your own mid-terms), detect a cycle (LeetCode 141, Floyd's algorithm), and remove the n-th node from the end (LeetCode 19).

Cycle detection is set as a lab problem for this segment.
💼The dummy head node Class 7
A sentinel node placed before the real first node, so that “insert at the front” stops being a special case and the same two lines work everywhere. Interviewers notice when you reach for it.

Your textbook already teaches it — under the name header list. Same object, different vocabulary.
💼LRU Cache Class 7 · LeetCode 146
A hash map plus a doubly linked list, giving O(1) lookup and O(1) eviction. It is the classic answer to “when would you actually use a doubly linked list?” and a staple of second-round interviews.
