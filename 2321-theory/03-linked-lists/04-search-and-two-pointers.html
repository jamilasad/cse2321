Section 1

Searching — walk until you find it

⏱ 7 min

An array can hand you A[3] using a formula. But searching is a different question. If I ask an array “where is the value 30?”, the formula is no help — the array has to look in its cells one at a time.

A linked list has to do exactly the same thing. Start at head, look at the value, and if it is not the one you want, follow the arrow to the next node. Keep going until you find it or run out of nodes.

Here the list loses nothing

Searching an unsorted array is also O(n) — it also checks cell by cell. So on this one operation the two are level. The array’s real advantage was never searching. It was indexing: going straight to a position you already know.

The unsuccessful search is the expensive one

If the value is there you might stop early. If it is not there you have no choice but to touch every node before you can say so. That is why the second run above is the longer one.

The notation your exam uses

Your textbook writes this list as two parallel arrays, INFO and LINK, with START instead of head. The same algorithm is then written SEARCH(INFO, LINK, START, ITEM, LOC), and instead of returning a node it sets LOC — the position of the node it found, or NULL if the search failed. 5 of the last 6 exams used that notation, so you should be able to read it. It is the same walk with different names.

Check yourself — 1 of 6
An unsorted linked list has 1000 nodes. You search for a value that is not in the list. How many nodes do you have to look at?
All 1000. The “average 500” figure is for a successful search, where you stop the moment you hit the value.

When the value is absent there is nothing to stop you. The list is unsorted, so a small value early on tells you nothing about what is further along. The only way to be sure the value is missing is to reach NULL — and that means touching every node.

In the next section you will see what changes when the list is sorted.

Section 2

A sorted list lets you give up early

⏱ 7 min

Now suppose the list is kept sorted, smallest first. That gives you one new piece of information while you walk: if the value under p is already bigger than the value you want, then everything after it is bigger too. Your value cannot be further along. You can stop right there and say it is not in the list.

So the sorted search has two ways to end the walk instead of one: you found it, or you passed the place where it should have been.

Be honest about what sorting bought you

The early stop is real, and on average it halves the work of a failed search. But the complexity has not changed. It is still O(n).

Ask for a value bigger than everything in the list — say 99 — and you still walk every single node before you can stop. Sorting improved the average, not the worst case.

So what did sorting buy the array?

Something far bigger. A sorted array can be searched with binary search in O(log n) — 1000 items in about 10 steps instead of 1000. Sorting changes an array’s whole complexity class.

The linked list is sorted too. So why does it only get a better average instead of O(log n)? That is the next section — and the reason is what earns the mark whenever an exam asks “which is better for searching an element, and why?”

Check yourself — 2 of 6
The sorted list is 10→20→30→50→60. You search for 45. How many nodes do you compare before you can answer?
4. You have to look at 50 in order to learn that you have gone too far. 10, 20 and 30 are all smaller than 45, so each one tells you to keep walking. The fourth node holds 50, and 50 > 45, so at that moment you can stop and answer “not in the list”.

You never look at 60. On a list of five that saves one node. On a list of a thousand, where the value would have been near the front, it saves a great deal more — but in the worst case it saves nothing at all.

Section 3

Why binary search dies on a linked list

⏱ 8 min

Binary search is the reason a sorted array is so powerful. Look at the middle, throw away half, repeat. A thousand items are searched in about ten steps.

It rests on one assumption, and it is easy to miss because in an array it costs nothing: you can jump to the middle in a single step. That is the formula from Segment 2 again.

mid = (low + high) / 2
then look straight at A[mid] — one formula, one step

Your turn

Can binary search be used on a sorted linked list? Yes or no — and the reason in one sentence.

No. The formula gives you an index, and a linked list has no way to turn an index into a node. You would have to walk to it — which is the exact cost binary search exists to avoid.

To look at node 4 you must be standing on node 3. Watch both do the same search below, side by side, and count what each one actually pays.

—

The problem is not only that walking is slow

Watch step 7 again. Binary search says “the answer is in the left half, set high = mid − 1”. For an array that is one subtraction. For a singly linked list it is impossible — p is standing on node 5 and there is no arrow pointing backwards. The only way back is to start again from head.

So half of binary search’s moves are moves a one-way list cannot make.

And even if you never had to go back

Suppose the answer was always in the right half, so you only ever walked forwards. You would still walk n/2 nodes to the first middle, then n/4 to the next, then n/8…

n/2 + n/4 + n/8 + …  ≈  n

That sum is n. So the walking alone is O(n) — the same as simply checking every node from the start, but with far more complicated code. You do fewer comparisons, and it buys you nothing, because comparisons were never the expensive part.

Say it in one line in the exam

Your textbook puts it like this: “binary search cannot be applied to a sorted linked list, since there is no way of indexing the middle element.”

If you are asked to explain it, the marks are in the reason, not the fact: binary search needs O(1) access to the middle, and a linked list only offers O(n) access to anything.

In an interview

💼“So is there a structure that gives you both?” not examined
This is the natural follow-up question, and there are two good answers.

A skip list is the direct one. It is a linked list with extra express lanes: some nodes also carry a pointer that skips 2 ahead, some skip 4, and so on. You search by taking the longest jump that does not overshoot, then dropping down a lane. That gives O(log n) search while still being made of nodes and pointers — and it is how Redis stores its sorted sets.

A balanced binary search tree is the other. It is also built from nodes and pointers, but arranged so that halving is built into the shape rather than bolted on. You will build one in Segment 5, and it is the reason std::map can find a key in O(log n).

The general lesson is worth keeping: the halving is not the clever part — being able to reach the middle cheaply is.
Check yourself — 3 of 6
Someone tells you they implemented binary search on a sorted linked list and it runs in O(log n). What is wrong?
They counted the wrong thing. There really are only about log n comparisons — that part is true. But each of those comparisons needs p to be standing on the middle node first, and getting there costs a walk.

Add the walks up and you get n/2 + n/4 + n/8 + … ≈ n. The total is O(n).

This is a good habit to build now: when you state a complexity, ask what does one step of this algorithm actually cost on this data structure? The same algorithm has different costs on different structures.

Section 4

One walk, many answers

⏱ 9 min

Past exams have asked for a procedure to find the largest value in a list, the largest even value, and the sum of the values below a limit. They look like three questions. They are one question asked three times.

Every one of them is the walk you already know. Only the work inside the loop changes.

p = head
while p != NULL:
    do something with p->data
    p = p->next

Learn the frame once. Then each new question is only about what goes in the yellow box — and about what you set up before the loop starts.

Task

▸

The same list, the same walk, three different jobs. Pick a task above and step through it — then switch task and watch how little actually changes.

—

Read the limit in the question, letter by letter

The run above sums the values below 30, so the node holding exactly 30 is not added — the test is <, strictly less than.

Now look at how a real exam worded it: “finding the sum of even numbers that are less than or equal to N”. That is <=, and it is also two conditions, not one — even and within the limit. A procedure that gets the walk perfectly right and the comparison slightly wrong still loses the mark.

The trap is in the line before the loop

A very common answer starts with max = 0. It gives the right answer on the list above, and the wrong answer on -5 → -2 → -9, where it reports 0 — a value that is not even in the list.

Start from a value that is in the list instead: max = head->data, then walk from the second node. And before any of that, check whether the list is empty at all — if head is NULL there is no maximum to return.

“Largest even value” needs an answer for “there isn’t one”

The list 7→3→9 has no even value at all. Your procedure must be able to say so, rather than returning a leftover 0. Use a flag, or return a sentinel such as −1, and say in words what it means. Exams give marks for handling that case; most answers forget it.

Notice also that the largest even value is not the largest value with the odd ones removed afterwards — in the run above the largest value is 45, which is odd, and the answer is 30.

time, all threeO(n) extra memoryO(1) passes over the list1

In an interview

💼This frame has a name, and you will meet it again also examined
Carrying one running value along a sequence is called a fold or a reduce. You have just written three of them by hand.

Once you see it, it turns up everywhere: std::accumulate in C++, reduce in Python and JavaScript, SUM and MAX in SQL. All of them are “set up an answer, walk the data, update the answer”.

The part interviewers actually probe is the part exams probe too: what does your function return for an empty input? A confident “I’d return an optional, because there is no maximum of nothing” is a better answer than any amount of clever looping.
Check yourself — 4 of 6
Why is max = head->data a safer start than max = 0?
Because the values might all be negative. On -5 → -2 → -9, starting from 0 means nothing in the list ever beats it, so the procedure returns 0 — a value that was never in the list.

Starting from head->data guarantees the answer is a real element. It does happen to save one comparison as well, but that is not the reason.

And the third option is simply false — head->data is just the starting guess, which the walk then improves.

Section 5

Add at the end — the walk that stops one early

⏱ 7 min

You wrote insertLast last class. It comes back today because it is the one walk that does not stop where every other walk stops.

Your turn

Here is the whole function. It compiles, and it is wrong. What happens when you run it on 10→20→30?

void insertLast(Node*& head, int item) { Node* newNode = new Node; newNode->data = item; newNode->next = nullptr; if (head == nullptr) { head = newNode; return; } Node* p = head; while (p != nullptr) p = p->next; p->next = newNode; }

The loop can only stop when p becomes NULL — and by then the last node is behind you, with no arrow pointing back. p->next = newNode then asks NULL for its next field: segmentation fault.

The fix is one word: while (p->next != nullptr) — keep walking while there is still a node after this one. Now the loop stops on the last node instead of past it, which is where you need to be to attach anything.

Run both versions below and watch where p ends up.

Run
Stopping one node early
Adding 40 at the end
▸

A new node holding 40 is waiting below the list. The only question is where p stops walking.

—

The empty list is a separate case, and it is not optional

If head is NULL there is no last node to walk to. Worse, p->next would be asking a node that does not exist for its next field, which crashes immediately.

So an add at the end answer has two branches, and both are worth marks:

  •  list is empty → head = newNode, and you are finished.
  •  list is not empty → walk to the last node, then last->next = newNode.

walk to the endO(n) the attachingO(1) with a tail pointerO(1)

All of that walking is avoidable

The attaching itself is one assignment. The O(n) comes entirely from having to find the last node, every single time you add one.

So keep a second pointer that always points at the last node, and adding at the end becomes O(1). That pointer is called tail, and it is Class 5. Notice we are not adding it yet on purpose — feeling the cost first is what makes the fix obvious later.

Check yourself — 5 of 6
Why does adding at the end use while (p->next != NULL) instead of while (p != NULL)?
It has to stop on the last node. You cannot attach anything to NULL — NULL is not a node, it is the absence of one.

p != NULL keeps walking until p has fallen off the end. At that moment the last node is behind you, and a one-way list has no arrow going backwards, so you cannot get to it again without starting from head.

p->next != NULL asks a different question: is there a node after this one? When the answer is no, p is standing exactly where you need it.

Section 6

Two walkers — the middle in one pass

⏱ 11 min

Here is the question, and it has been on both of the last two mid-terms: find the middle node of a linked list in a single traversal.

Think about why it is awkward. To know which node is the middle you need to know how long the list is. To know how long the list is you have to walk it. And once you have walked it you are at the end, not the middle.

Your turn

You are given head and nothing else — no length, no count. Find the middle node.

Get any correct answer down first. Then read the question again: it says in a single traversal. Can you meet that?

If your answer was walk once to count, then walk again to node n/2 — that is correct, and it is O(n). It is worth partial marks. But read the question again: it says in one traversal, and this needs two. It touches about 1.5n nodes and has to store the count, so it solves the problem while ignoring the constraint — which is the part being tested.

The one-pass version stops thinking about counting and starts thinking about speed. Send two walkers along the same list at the same time, and let one of them move twice as fast:

🐢 slow moves one node per turn  ·  🐇 fast moves two nodes per turn

Fast is always exactly twice as far along as slow. So at the moment fast reaches the end, slow must be at the halfway point. No counting, no second pass, and no need to know the length in advance.

The pair has a name worth remembering: the tortoise and the hare — slow is the tortoise, fast is the hare. You will meet the same two walkers again in your lab, where they answer a different question (Floyd’s cycle-finding algorithm, §7).

head slow — the tortoise, one step fast — the hare, two steps
Run

▸

Both walkers start on the first node. Press Next step and watch the gap between them open up — slow is always halfway to fast.

—

Read the loop condition again — both halves earn their place

The loop is while (fast != NULL and fast->next != NULL), and students often drop one half of it. Each half catches a different ending, and you saw both above:

  •  Odd length — fast lands on the last node. There is nothing after it, so fast->next is NULL. The second check stops you.
  •  Even length — fast steps clean past the end and becomes NULL itself. The first check stops you.

Keep only the first and the odd case crashes. Keep only the second and the even case crashes. You need both.

And they have to be in that order

Write it the other way round — fast->next != NULL && fast != NULL — and the even case crashes.

By then fast is NULL, and the very first thing that line does is ask NULL for its next field. Checking afterwards that fast was NULL is too late; the crash has already happened.

C++ evaluates && from left to right and stops as soon as the answer is decided. So when fast != NULL is false, the right-hand side is never run at all. That behaviour is called short-circuit evaluation, and here you are using it deliberately: the first check is what makes the second one safe.

timeO(n) traversals1 extra memoryO(1) needs the length?no

Which of the two middles, when the length is even?

A list of 6 has no single middle — both 30 and 40 have equal claim. The version above returns the second one, 40. That is the usual convention and it is what LeetCode 876 asks for.

If you need the first middle instead, stop the loop one turn earlier by using while (fast->next != NULL && fast->next->next != NULL). In the exam, either is fine — but say which one you chose. Writing “for an even length this returns the second of the two middle nodes” shows you noticed the case, and that is what the mark is for.

This is also how you insert at the middle in one pass

Last class you inserted at position n by walking to node n−1 — which means you had to be told what n was.

The Autumn 2025 mid-term asked something sharper: insert a node in the middle of a list, and then explain “how the same insertion can be achieved by traversing the linked list only once”. This is the answer. Run slow and fast; when fast reaches the end, slow is already standing at the middle, so insert there. The length was never needed and the list was never walked twice.

One practical detail: to insert before the middle you also need the node in front of it, so carry a third pointer one step behind slow. Same walk, one more variable.

Check yourself — 6 of 6
A list has 6 nodes: 10 20 30 40 50 60. Using while (fast && fast->next), which node does slow end on?
40. Follow the two walkers turn by turn: slow goes 10→20→30→40, while fast goes 10→30→50, then off the end.

On that last turn fast tries to take two steps from 50. One step reaches 60, the second falls off, so fast becomes NULL. The loop condition checks fast != NULL first, finds it false, and stops — without ever touching fast->next. Nothing crashes, precisely because that check comes first.

slow has taken three steps and is standing on 40, the second of the two middle nodes.

The gap between two walkers is a tool

⏱ 7 min

The middle was one use of a general idea: put two walkers on the list and control the relationship between them. Change what you control, and a different answer comes out.

The k-th node from the end

This one sounds like it needs the length: the 2nd from the end of a list of 6 is the 5th from the front, and you only know that if you know it is 6.

Your turn

The table says what to do — same speed, a fixed gap of k. It does not say why it works, and that is what earns the mark.

Run one walker k nodes ahead, then move both together. When the leader falls off the end, where is the follower, and how do you know? Try it on paper with 6 nodes and k = 2.

Hint — name the one quantity that never changes.

The gap. Both walkers take one step per turn, so the distance between them is k at the start and k at every moment after.

The leader stops when it falls off the end, so it is 0 from the end. The follower is k behind — so it is k from the end. The length never entered the argument, which is why you never needed it.

slow — the answer fast — k steps ahead
A fixed gap, dragged along
The 2nd node from the end
▸

Six nodes, and we want the 2nd from the end — without counting them. Watch the gap open, then stay fixed.

—

The case that breaks it

If k is bigger than the list, opening the gap runs fast off the end and the next fast->next crashes.

So check at every step of the gap-opening that fast is still a real node. If it becomes NULL early, the list has no k-th node from the end. Saying that in an answer is usually worth a mark on its own.

Cycle detection — the tortoise and hare again, asked something else

Suppose the last node points back at an earlier node instead of holding NULL. The list loops forever and an ordinary traversal hangs.

Send the tortoise and the hare in anyway. If the list ends normally the hare reaches NULL and you are done. If it loops the hare can never escape, and since it gains one node per turn it must eventually land on the tortoise. Two pointers meeting means a cycle, and nothing is stored — O(1) memory.

This is your lab task, so it is left as an idea rather than code. Its name is Floyd’s cycle-finding algorithm.

In an interview

💼“Two pointers” is a named technique — and it is not only about lists not examined
If you look at any interview preparation site you will find two pointers listed as one of the core patterns, next to sliding window and binary search. What you did today is the linked-list half of it.

The array half looks different but is the same idea. In a sorted array, to find two values that add up to a target, put one index at each end and move them towards each other: too small, move the left one right; too big, move the right one left. That is O(n) instead of the O(n²) of checking every pair — and again, no extra memory.

A useful way to hold all of it in your head: a second pointer is a way of remembering something about the data without storing it. The gap between the two walkers is the memory.

One sentence that explains the whole table

That is the honest summary of a linked list: it is not slower at thinking, it is slower at arriving.

Reference

📜The whole program, in one piece — ready to compile

Everything from Classes 1 to 4 assembled: the node, the six operations, the four walks, and the clean-up. Nothing here is new — every function has been on screen and stepped through. Copy it, compile it, and change one thing at a time.

#include <iostream>
using namespace std;

struct Node {
    int   data;
    Node* next;
};

// ---------- build ----------

void insertFirst(Node*& head, int item) {
    Node* nw = new Node;
    nw->data = item;
    nw->next = head;
    head     = nw;
}

void insertLast(Node*& head, int item) {
    Node* nw = new Node;
    nw->data = item;
    nw->next = nullptr;

    if (head == nullptr) { head = nw; return; }

    Node* LN = head;
    while (LN->next != nullptr)           // stop ON the last node
        LN = LN->next;

    LN->next = nw;
}

void insertAt(Node*& head, int pos, int item) {
    if (pos == 1) { insertFirst(head, item); return; }

    Node* prev = head;
    int i = 1;
    while (i < pos - 1 && prev != nullptr) {
        prev = prev->next;
        i++;
    }
    if (prev == nullptr) return;

    Node* nw = new Node;
    nw->data   = item;
    nw->next   = prev->next;              // this line must come first
    prev->next = nw;
}

// ---------- remove ----------

void deleteFirst(Node*& head) {
    if (head == nullptr) return;

    Node* FN = head;                      // hold it before head moves
    head = FN->next;
    delete FN;
}

void deleteLast(Node*& head) {
    if (head == nullptr) return;
    if (head->next == nullptr) { delete head; head = nullptr; return; }

    Node* prev = head;
    while (prev->next->next != nullptr)
        prev = prev->next;

    Node* last = prev->next;
    prev->next = nullptr;                 // unhook first
    delete last;                          // free second
}

void deleteAt(Node*& head, int pos) {
    if (head == nullptr) return;
    if (pos == 1) { deleteFirst(head); return; }

    Node* prev = head;
    int i = 1;
    while (i < pos - 1 && prev->next != nullptr) {
        prev = prev->next;
        i++;
    }
    if (prev->next == nullptr) return;

    Node* cur  = prev->next;
    prev->next = cur->next;
    delete cur;
}

// ---------- read ----------

void print(Node* head) {
    Node* p = head;
    while (p != nullptr) {
        cout << p->data << " ";
        p = p->next;
    }
    cout << endl;
}

Node* search(Node* head, int item) {
    Node* p = head;
    while (p != nullptr) {
        if (p->data == item) return p;
        p = p->next;
    }
    return nullptr;                       // the failed search is a full walk
}

int largest(Node* head) {
    int max = head->data;                 // start from a real value
    Node* p = head->next;
    while (p != nullptr) {
        if (p->data > max)
            max = p->data;
        p = p->next;
    }
    return max;
}

Node* middle(Node* head) {                // tortoise and hare
    Node* slow = head;
    Node* fast = head;
    while (fast != nullptr && fast->next != nullptr) {
        slow = slow->next;                // one step
        fast = fast->next->next;          // two steps
    }
    return slow;
}

Node* kthFromEnd(Node* head, int k) {
    Node* fast = head;
    int i = 0;
    while (i < k) {
        fast = fast->next;
        i++;
    }

    Node* slow = head;
    while (fast != nullptr) {             // the gap never changes
        slow = slow->next;
        fast = fast->next;
    }
    return slow;
}

// ---------- clean up ----------

void freeList(Node*& head) {
    Node* cur = head;
    while (cur != nullptr) {
        Node* nxt = cur->next;            // save it before the delete
        delete cur;
        cur = nxt;
    }
    head = nullptr;
}

int main() {
    Node* head = nullptr;

    insertLast(head, 10);
    insertLast(head, 20);
    insertLast(head, 30);
    insertFirst(head, 5);
    insertAt(head, 3, 15);
    display(head);                          // 5 10 15 20 30

    cout << largest(head) << endl;        // 30
    cout << middle(head)->data << endl;   // 15
    cout << kthFromEnd(head, 2)->data;    // 20
    cout << endl;

    deleteLast(head);
    deleteAt(head, 2);
    display(head);                          // 5 15 20

    freeList(head);                       // every new needs its delete
    return 0;
}

Take home

A linked list can only answer questions at the speed it can walk.

That single sentence explains everything in the table above. It is why search stays O(n) even when sorted, why binary search is pointless here, and why the two-pointer trick matters so much — it is the one way to learn something about the shape of a list without walking it twice.

Asked 4 times · both new mid-terms

Find the middle in one traversal

1–4 marks

Spring 2025 · Mid Term · Q3(b) [OR] · 4 marks

“You are developing a music playlist manager using a singly linked list. Each node in the list stores the name of a song. The playlist contains an odd number of songs, but the number of songs is unknown. Write an efficient algorithm or C/C++ function to find the middle song of the playlist using only one traversal.”

Autumn 2025 · Mid Term · Q3(b)(ii) · 1 mark

“Explain how the same insertion can be achieved by traversing the linked list only once.”

Part (i) had asked for an algorithm to insert a node in the middle position of a linked list. So (ii) is the two-walker trick applied to insertion — see the last box in §6.

Autumn 2023 · Final · Q2(b) · 4 marks

“You are given a linked list containing an odd number of elements. You don’t know how many numbers there are in that list. Write an algorithm or C/C++ code to find the middle element of this list.”

The [OR] alternative that year asked for the same thing on a two-way linked list, “by iterating only once over the list”. The two-walker answer is identical — the backward pointers change nothing.

Model answer

★Full marks — and why each part earns its mark
The idea, in one sentence. Use two pointers that move at different speeds: slow advances one node per turn and fast advances two. Since fast covers twice the distance, when fast reaches the end of the list, slow is standing at the middle.

The algorithm.
  1. slow = head
  2. fast = head
  3. while fast != NULL and fast->next != NULL:
  4.     slow = slow->next
  5.     fast = fast->next->next
  6. return slow

Why it satisfies “only one traversal”. Every node is visited at most once by each pointer, and the pointers never restart. The list is walked once, and the length is never computed. Contrast with the two-pass method — count the nodes, then walk n/2 — which is also O(n) but traverses the list twice, and is therefore not an answer to the question asked.

Complexity. Time O(n), extra memory O(1) — only two pointer variables, regardless of how long the list is.

The odd-length note. Both exams say the list has an odd number of elements, so there is exactly one middle and this returns it. Add one line anyway: “if the length were even there would be two middle nodes, and this version returns the second.” It costs you a sentence and shows you understand the boundary.

For 4 marks: the idea, the algorithm, the one-traversal justification, and the complexity. For the Autumn 2025 1-mark version you only need the idea plus “insert at slow when fast reaches the end”.
⇆The same question, asked about a two-way list
Autumn 2023 Final, Q2(b) [OR], 4 marks. “You are given a two-way linked list containing an odd number of elements. You don’t know how many numbers there are in that list. Write an algorithm or C/C++ code to find the middle element of this list by iterating only once over the list.”

The answer is the algorithm above, unchanged. Write it out, then add the sentence that earns the last mark: “the prev field does not help here.”

Why it does not help. The tempting answer is “walk in from both ends until the two meet” — and it is wrong, because you do not know where the end is until you have already walked to it. Getting to the last node is the traversal you were told to do only once. Two walkers from the front is still the only method that fits the wording.

Two-way lists are Class 7. The point worth carrying: a second pointer changes what you can do at a node, never how you find one.
⚠The three ways students lose this
1. Answering with the two-pass method. Counting the nodes and then walking half way is correct code and a wrong answer — the question says “only one traversal” and that phrase is the thing being tested. Expect to lose most of the marks.

2. Writing the loop condition as while (fast->next != NULL && fast != NULL). The two halves are in the wrong order, so on an even-length list you dereference NULL before you check it. Even though these questions promise an odd length, the ordering is what an examiner looks at.

3. Dropping half the condition. while (fast != NULL) alone crashes on odd lengths, because fast->next->next is evaluated when fast->next is NULL. Both halves are load-bearing.

Asked 3 times

Write a procedure that walks the list

3–5 marks

Spring 2023 · Final · Q2(a) · 5 marks

“Suppose LIST is a linked list in memory consisting of numerical values. Write a procedure for each of the following:
i) Finding the maximum even number of the values in LIST
ii) Finding the sum of even numbers that are less than or equal to N of the LIST (Note: N is the last two digits of your ID. i.e. if your ID is C151216, then N=16).”

Spring 2024 · Final · Q2(b) [OR] · 3 marks

“Let LIST be a linked list of integers in memory. Write a procedure to find the maximum MAX of the values in LIST. What is the time complexity of this procedure?”

The identical question, without the complexity sentence, was Q2(b) [OR] of the Autumn 2022 Final.

Notice what the 2023 question really did

It made N the last two digits of your student ID. Every student had a different limit, so nobody could copy an answer — and it forced you to write the procedure in terms of a variable rather than a number. Write N, not 16.

Model answer

★All four procedures, written the way they should be written
Every one of these is the same frame. Set up the answer, walk the list once, update the answer, return it.

(a) Maximum value — MAX.
  1. if head == NULL: return “list is empty”
  2. MAX = head->data  [start from a value that is really in the list]
  3. p = head->next
  4. while p != NULL:
  5.     if p->data > MAX: MAX = p->data
  6.     p = p->next
  7. return MAX
Time complexity: O(n) — every node is examined exactly once, and no node is examined twice. Extra memory O(1). The 2024 exam asks for this sentence explicitly, so write it.

(b) Maximum even value. Same walk, two changes. You cannot start from head->data, because the first value may be odd — so start from “nothing found yet”:
  1. FOUND = false
  2. p = head
  3. while p != NULL:
  4.     if p->data % 2 == 0 and (FOUND == false or p->data > MAXEVEN):
  5.         MAXEVEN = p->data;  FOUND = true
  6.     p = p->next
  7. if FOUND == false: return “no even value in the list”
  8. return MAXEVEN
Step 7 is worth a mark on its own, and most answers leave it out.

(c) Sum of even numbers that are less than or equal to N. Here zero is the correct starting value, and there are two conditions joined by and:
  1. SUM = 0
  2. p = head
  3. while p != NULL:
  4.     if p->data % 2 == 0 and p->data <= N:
  5.         SUM = SUM + p->data
  6.     p = p->next
  7. return SUM
Note <=, not < — the question says less than or equal to. And N is a variable, not your own ID digits hard-coded.

(d) Add ITEM at the end. See the next card — it was asked as its own 5-mark question.

Asked once, for 5 marks

Add an ITEM at the end of a list

5 marks

Spring 2023 · Final · Q2(a) [OR] · 5 marks

“Write a procedure which adds a given ITEM of information at the end of a list.”

Fifteen words, five marks. That tells you the marks are not in the walking — they are in the cases you remember to handle.

Model answer

★The answer, and where the five marks actually are
  1. Create a newNode and put ITEM in its information field.
  2. newNode->next = NULL  [it is going to be the last node]
  3. if head == NULL: head = newNode; return  [the empty-list case]
  4. p = head
  5. while p->next != NULL: p = p->next  [stop ON the last node]
  6. p->next = newNode
  7. Exit.

Where the marks are. Step 2 — setting the new node’s link to NULL, so the list still has a proper end. Step 3 — the empty list, which has no last node to attach to and would crash at step 5. Step 5 — the condition p->next != NULL rather than p != NULL. And a closing line on cost: O(n), because the last node must be found by walking; with a tail pointer it would be O(1).

If the question is set in the textbook’s notation — INFO, LINK, START, AVAIL — then step 1 becomes “take a node from the AVAIL list”: NEW = AVAIL, AVAIL = LINK[AVAIL], INFO[NEW] = ITEM, LINK[NEW] = NULL. That notation is drilled in Class 8.

Asked twice

Search a sorted linked list

3 marks

Spring 2024 · Final · Q2(b) · 3 marks

“Let LIST be a sorted linked list. Write an algorithm to search an element from the LIST. What is the time complexity of this algorithm?”

Autumn 2022 · Final · Q2(b) · 3 marks

“Let LIST be a sorted linked list. Write an algorithm to search an element from the LIST.”

Model answer

★Full marks — the early exit is the whole point
SEARCH(head, ITEM) — LIST is sorted in increasing order.
  1. p = head
  2. while p != NULL:
  3.     if p->data == ITEM: return p  [found]
  4.     if p->data > ITEM: return NULL  [gone past it — it cannot be ahead]
  5.     p = p->next
  6. return NULL  [reached the end]

Step 4 is what makes this a sorted-list answer. Without it you have simply written the ordinary search and the word “sorted” in the question has done nothing. Say in words why it is allowed: the list is in increasing order, so once a value larger than ITEM is reached, every value after it is larger still.

Time complexity: O(n). Say this plainly, and then add the sentence that shows you understand it: sorting improves the average case, because an unsuccessful search can stop early, but the worst case is unchanged — an ITEM larger than every value still requires the whole list to be walked.

The sentence that gets you the last half mark. Binary search cannot be used here, because a linked list gives no way to reach the middle element in one step; reaching it costs O(n), so the total remains O(n).
⚠Two ways this answer goes wrong
1. Writing binary search. The word “sorted” makes people reach for it automatically. On a linked list it is not an improvement — it is worse than the plain walk, because every “jump to the middle” is itself a walk, and half the jumps go backwards, which a one-way list cannot do at all.

2. Claiming O(log n). If you write binary search and claim O(log n), you have lost the complexity mark as well. See §3.

Beyond the exam

The same three topics, in an interview

These questions are not on your exam. They are, however, on almost every technical interview for a first software job — and each one is something you already did today, asked in different words.

In an interview

💼“Find the middle of a linked list” LeetCode 876 · easy
Word for word the exam question, and usually a warm-up. Say the two-pointer idea before you write anything, then write it.

The follow-up is almost always “what if the length is even?” — so volunteer it: “there are two middles; this returns the second, and I can return the first by stopping one turn earlier.” Volunteering the boundary case is the difference between a pass and a good pass.
💼“Remove the n-th node from the end, in one pass” LeetCode 19 · medium
This is §7’s fixed gap, plus a deletion. Open a gap of n+1 rather than n, so that slow stops on the node before the one being removed — you cannot delete a node in a one-way list without holding its predecessor. That is the same lesson as delete-at-position from Class 1.

The trap is deleting the head itself. A dummy node in front of head makes that case disappear entirely, and you will meet that trick properly in Class 7.
💼“Does this list have a cycle?” LeetCode 141 · your lab
Same two walkers, different question: if fast ever lands on slow, there is a cycle; if fast reaches NULL, there is not. O(1) memory, which is the point — the obvious answer of storing every visited node in a set works but costs O(n) memory, and the interviewer is waiting for you to beat it.

You will implement this in the lab, so treat it as homework rather than trivia.
💼“Why is a linked list slower than an array in practice, even when Big-O says they are equal?” the senior question
The answer is cache locality, and it is the one that marks you out.

When the CPU reads one array element it pulls a whole cache line — typically 64 bytes, about 16 ints — into fast memory, so the next fifteen reads are nearly free, and the hardware prefetcher predicts the straight run perfectly. A linked list loses all of that: each node can sit anywhere, so every p = p->next risks a cache miss, which costs roughly a hundred times more than a hit.

That is why §1’s honest “both are O(n)” still comes out in the array’s favour on a real machine, and why std::vector beats std::list for most real workloads.

Your own slides list “better cache locality” as an array strength, so this is fair game in the exam too.

If you only rehearse one thing from this class

Rehearse the two-walker middle, out loud, in under a minute: the idea, the six lines, why it is one traversal, the complexity, and what happens on an even length.

It is the single highest-value minute in Segment 3 — it has appeared on both new mid-terms, it is a standard interview warm-up, and every other two-pointer question is a variation on it.
