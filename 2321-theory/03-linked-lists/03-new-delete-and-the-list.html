Where we are

Last class you built the four nodes and printed them. Then one thing would not work: a function that adds a node to the front.

The reason is not the pointers. It is where the node was kept. That is what this class is about, and once it is fixed, every operation you drew in Class 1 becomes code you can run.

1

Section 1

Where your variables have been living

⏱ 6 min

Every variable you have written so far went to the same place, and you never had to know its name. It is called the stack.

The rule is short. Every call gets a frame — a band of memory holding that call's variables. When the call returns, the frame is thrown away, and everything in it goes with it.

One frame per call
▸

Press Next step. Watch the right-hand half of memory: we do not touch it once.

—

The stack is automatic

You never wrote a line to make a frame or to remove one. The compiler does both, at the { and at the }.

That is exactly why it is convenient — and exactly why it cannot hold a list.

The heap is yours

The other half is the heap. Nothing is put there automatically and nothing is taken away automatically. You ask for memory, and it stays until you give it back.

We ask for the first time in Section 3.

Both halves are ordinary RAM

Stack and heap are not two kinds of hardware. They are two ways of managing the same memory you saw in Class 1 — one automatic and short-lived, one manual and long-lived. The cells and the addresses are the same cells and addresses.

Check yourself — 1 of 6
A function declares int total = 0; and returns. What happens to total?
It goes with the frame. The variable was part of that call, and the call is over.

Call the function again and you get a new total, in a new frame, possibly at a different address. Nothing carries over — which is what you want almost every time, and exactly what you do not want when you are building a list.

Section 2

The node that dies at the closing brace

⏱ 8 min

Class 2 ended on a function that would not work: insertFirst. The fault is easier to see in something smaller, so we will use a function that just makes one node and hands it back — and which we need in Section 4 anyway.

Everything in it is correct C++. It compiles. And it is broken, for the reason you met one minute ago.

Returning the address of a local
▸

Press Next step. The node is built correctly — watch where it is built.

—

Why this is worse than a crash

The frame is gone, but the cells are still there, and for a moment they still hold 10. So the program often prints 10 and looks perfect.

Then you add one more function call. That call gets a frame in the same place, writes its own variables over those cells, and your list quietly fills with rubbish. The bug appears far from the line that caused it. This has a name: a dangling pointer.

The compiler does warn you

Most compilers say something like
warning: address of local variable ‘n’ returned

It is a warning, not an error, so the program still builds. Turn warnings on and read them.

Returning a value is fine

Nothing is wrong with return n; when n is an int — that copies the value out before the frame goes.

The problem is returning an address of something inside the frame. The copy you get is a copy of the address, and the thing it points at is gone.

The same fault killed insertFirst

Last class you wrote Node newNode; inside the function and pointed head at it. Same mistake, same cause: the node was in the frame, and the frame went at the closing brace. head was left pointing at memory the program no longer owned.

Fix the where, and both functions work. You write the real insertFirst in Section 5.

Dig deeper

?Why does it print the right answer sometimes?
Because nothing erases memory. When a frame is thrown away, the stack pointer simply moves back — the bytes are untouched, and they stay untouched until the next call writes over them.

So the read is not "wrong", it is undefined: the standard makes no promise at all. It may print 10, it may print rubbish, it may crash, and it may do different things in a debug build and a release build. A test that passes tells you nothing.

This is the single most common reason a C++ program works on your machine and fails on the examiner's.
Check yourself — 2 of 6
Your friend runs the program above and it prints 10. What has that proved?
Nothing at all. The value survived because no other call had overwritten those cells yet.

Add one function call before the cout and the same program prints something else. Correctness in C++ is not decided by one run — and a compiler will never silently move your variable somewhere safer.

Section 3

new — memory that outlives the call

⏱ 8 min

The node has to survive the function that made it. So it must not be in that function's frame.

One word changes where it goes.

Section 2 — dies at the brace Node n; A whole node, in this frame. Gone the moment the call returns.
→
Section 3 — outlives the call Node* n; n = new Node; A pointer in this frame, and the node itself in the heap.

The right-hand side is two separate ideas, so it is written as two lines. Node* n; makes somewhere to keep an address. n = new Node; asks the heap for the room and writes the address down.

Read new Node as “give me room for one Node, and tell me where it is”. What comes back is an address, so what you keep it in is a Node*.

The same function, on the heap
▸

Press Next step. Same steps as Section 2 — watch which half of memory the node lands in.

—

The dot became an arrow

In Section 2, n was a Node, so you wrote n.data.

Here n is a pointer to a Node, so you write n->data — the arrow from Class 2. Nothing new; the same rule, now with new.

Two variables, one node

When the call returns, the pointer n is destroyed with the frame — that is fine. It was only ever a piece of paper with an address on it.

The address was copied out into p first, and the node it names is in the heap, untouched.

What you have just taken on

The heap keeps that node for ever, or until you say otherwise. Every new is a promise to hand the memory back later with delete. We meet it in Section 6, and Section 8 is about what happens when you forget.

Check yourself — 3 of 6
What is the type of new Node?
Node*. new does two things: it takes room in the heap, and it gives you back where that room is.

So Node n = new Node; will not compile — you are trying to put an address into a Node. It has to be Node* n = new Node;, and this is the mistake to expect in your own code for the next week.

Section 4

Build the list: 10 → 20 → 30 → 40

⏱ 8 min

This is the same list you drew in Class 1 and built with locals in Class 2. Now it goes in the heap, and it will still be there when the function ends.

Two variables do the work. head remembers the front and then never moves. t is a walker that always stands on the last node, so we know where to attach the next one.

Four nodes, wired in the heap
▸

Press Next step. Watch t: it is always standing on the last node.

—

The program has ended. The list has not.

Run the simulator to the last step and look at the chip. The stack is empty — main is over, its frame is gone, t with it. The four nodes are still sitting in the heap, and not one line ever asked for them back.

That is not a bug yet, because the program is finishing anyway. It becomes one the moment this runs inside something bigger. Section 6 shows what delete actually does about it, and Section 8 gives the whole list back properly.

The pattern is two lines

t->next = makeNode(v); hangs a new node on the end.
t = t->next; steps the walker onto it.

Repeat those two lines and the list grows as long as you like. That is insertLast with the walk already done for you — and it is why Class 5 wants a tail pointer.

Where is makeNode’s frame?

It appears and disappears four times, too fast to be worth drawing — you watched exactly that happen in Section 3.

What matters here is what it leaves behind: each call puts one node in the heap and hands the address back. head is a global so the list outlives every one of those calls.

Lose head and you lose everything

Nothing else in the program knows where the first node is. If you overwrite head before you have saved it — say by writing head = makeNode(5); when you meant to attach — the four nodes are still in the heap, still linked, and completely unreachable. You cannot free them and you cannot print them. That is a leak, and Section 8 is about it.

One more function, and you will use it every day

You cannot see a linked list. Write this once, now, and call it after every operation for the rest of the segment — it is how you will know an insert worked before you trust it.

void display(Node* head) {
    Node* p = head;
    while (p != nullptr) {
        cout << p->data << " ";
        p = p->next;
    }
    cout << endl;
}

It changes nothing and returns nothing. p is a walker, exactly like t above: start at head, print, step on, stop at nullptr. Take Node* head by value here — display has no business moving the caller’s head, and the copy makes that a compiler-enforced promise rather than a good intention.

display(head); after the build above prints 10 20 30 40. Every listing from here on assumes you have it.

Check yourself — 4 of 6
You delete the line t = t->next; from the middle of the build. What does the list contain?
10, 20, 40. Without the step, t is still on node 20, so the next line writes 20->next a second time — and 40 replaces 30.

Node 30 is still sitting in the heap. Nothing points at it, so nothing can reach it or free it. No crash, no warning, no error message — just a list that is quietly one node short.

Section 5

Insert — all three, in code

⏱ 12 min

These are the three cases you stepped through in Class 1, line for line. Nothing about the pictures has changed. What is new is that you can run them.

One detail before we start, and it is the one people get wrong.

Does not work void insertFirst(Node* head, ...) head is a copy. Setting it changes the copy, and the caller’s list is untouched.
→
Works void insertFirst(Node*& head, ...) The & makes it a reference parameter. Inside the function head is not a copy — it is the caller’s variable, under a second name. Setting it sets theirs.

That is the third job of & from Class 2, doing real work at last. Two names, one variable — no second pointer is made, which is why head = nw; reaches all the way back into main. Insert-last and insert-at only need it for the empty-list case — but they take it too, so all three functions look alike.

Inserting into the list
insertFirst
▸

Press Next step.

—

These two lines are in this order for a reason

Write prev->next = nw; first and prev lets go of the rest of the list before anything else is holding it. The next line then reads prev->next, which is now the new node — so the new node points at itself, and everything from position n onwards is lost.

Connect before you disconnect. Every insert and delete in this course obeys that one rule.

The rewiring is always O(1)

Look at the assignments in each function: there are never more than two. No element is copied and nothing moves.

What separates the three cases is only how far you had to walk first.

insertAt calls insertFirst

Position 1 has no prev — there is no node before the first one. Rather than write a special case twice, insertAt hands the job to insertFirst and returns.

Reusing a function you have already tested is what the examiner wants to see.

Check yourself — 5 of 6
You change insertFirst to take Node* head instead of Node*& head, and call it on a list of four. What happens?
It compiles and does nothing visible. Inside the function, head = nw; sets the local copy. The function returns, the copy goes with the frame, and the caller’s head still points at the old first node.

The new node was created, and it still points into your list — but nothing points at it. It is unreachable and unfreeable. That is a leak, produced by one missing character.

Section 6

delete — and what it does not do

⏱ 7 min

Every new is a loan. delete pays it back.

The word is misleading, so it is worth being exact about what happens. delete p tells the heap “I have finished with the room at this address”. That is all it does.

Giving the memory back
▸

Press Next step. Watch p at the moment of the delete — it does not flinch. Then run it without the delete and watch what is left behind.

—

It does not change the pointer

p still holds the same address after the delete. It is now pointing at memory you have given away — dangling, exactly as in Section 2.

It does not erase anything

The bytes are untouched until the heap hands that room to someone else. So reading a deleted node often still “works”, and that is what makes it dangerous.

It does not follow next

Deleting one node frees one node. The rest of the list is not touched — which is why Section 8 needs a loop.

The habit worth forming

Write p = nullptr; straight after a delete whenever the pointer will still be around.

It costs one line and changes a silent wrong answer into an immediate crash — and a crash you can find. It also makes delete p safe to run twice, because deleting a null pointer is defined to do nothing.

Dig deeper

?What does “the cells go back” actually mean?
The heap keeps a record of which stretches of memory are in use and which are free — conceptually the free list your textbook calls AVAIL. new takes a stretch off it; delete puts one back.

Nothing is returned to the operating system, and nothing is wiped. The stretch is simply marked available again, so the next new can be handed the very same address — which is precisely how a dangling pointer ends up quietly writing into somebody else’s node.

Your exam notation calls this pair AVAIL and the operation “returning a node to the AVAIL list”. It is the same idea in different words.

Section 7

Delete — all three, in code

⏱ 12 min

Now the other half. The pictures are Class 1’s again; the only new thing in them is the delete you met a minute ago.

Every one of these functions does the same two jobs in the same order: unhook the node, then free it. Doing them the other way round frees a node that is still part of the list.

Deleting from the list
deleteFirst
▸

Press Next step.

—

Take hold before you unhook

In every one of these functions there is a line whose only job is to remember the node we are about to remove — FN, cur, or prev->next read before it is overwritten.

Skip it and the node is unhooked with nothing pointing at it. You cannot delete it, because you no longer know where it is. It is leaked, and every run of the program leaks another one.

deleteLast stops one node early

The walk tests prev->next->next != nullptr, not prev->next. It has to stop on the second to last node, because that is the one whose link must be cut.

This is why a tail pointer does not rescue delete-last, and why Class 5 spends time on exactly that.

Every function guards the empty list

if (head == nullptr) return; is the first line of all three. On an empty list there is no first node to take, nothing to walk, and nothing to free.

An examiner looking for four marks is looking for that line.

Check yourself — 6 of 6
In deleteFirst you swap the last two lines: delete FN; first, then head = FN->next;. What is wrong?
You are reading a node you have already freed. After delete FN, that room is on the free list, and FN->next is undefined behaviour — so head may be set to anything at all.

It will very often appear to work, because the bytes are usually still intact. Then one day the heap reuses that room between the two lines, and the whole list is gone. Read what you need, unhook, and only then free.

Section 8

Free the whole list

⏱ 7 min

Four news in Section 4, and not one delete. Every list you build has to be given back, and delete head frees exactly one node.

So it is a loop. And the loop has one trap in it, which is worth meeting now because it is the same trap in every question that walks and frees at the same time.

Giving four nodes back
▸

Press Next step. Watch why nxt has to exist.

—

The version that looks right

while (cur != nullptr) { delete cur; cur = cur->next; }

Read the second line: it asks the node we just freed where the next one is. The room is back on the free list, so the answer is whatever happens to be in those bytes.

Usually it still works, because nothing has reused them yet. Occasionally it walks off into memory that is not yours and the program dies. Save the next address first — that is the whole reason nxt exists.

A leak is silent

Forget to free and nothing happens. No warning, no crash, no wrong answer — the program just holds memory it will never use again.

You notice on the day it runs for hours, or on the day the marker runs it under a memory checker.

There is a better way, later

Writing delete by hand is how the exam asks for it, so you must be able to do it.

In real C++ the list would own its nodes and free them in a destructor, so forgetting becomes impossible. That is Class 6.

Where this leaves you

Everything you drew in Class 1 is now a program: build it, print it, insert three ways, delete three ways, and free it.

Two of those functions had to walk to the end to do a job that was otherwise one assignment. Next class we keep a second pointer on the last node and watch what it does — and, just as usefully, what it cannot do.

In an interview

💼“What is the difference between a memory leak and a dangling pointer?” asked constantly
They are opposite mistakes about the same pair of operations.

A leak is memory you still own but can no longer reach — you lost the address without freeing it. Nothing breaks; the program simply grows.

A dangling pointer is the reverse: you kept the address but gave the memory back. Nothing grows; the program reads or writes something that is no longer its own, and behaves unpredictably.

One line covers both, and it is worth saying exactly this: “a leak is memory without a pointer; a dangling pointer is a pointer without memory.”

AVAIL is the heap, written as a list

The exam's AVAIL is the chain of free cells. new takes a node off it; delete puts one back on it. When the answer sheet says “return the node to the AVAIL list”, it means the line you wrote today as delete cur;.

Beyond the exam

Interview corner

💼“What is a memory leak?” asked constantly
Memory you still own but can no longer reach, because you lost the last pointer to it without freeing it.

The best answer names the opposite in the same breath: “a leak is memory without a pointer; a dangling pointer is a pointer without memory.” Then give the one-line example from §5 — taking Node* head instead of Node*& head leaks a node on every call, silently.
💼“Why does delete not set the pointer to null?” C++ specific
Because it cannot: delete p is given the value of p, not p itself. It has no way to reach back and change your variable — and there may be five other pointers holding the same address that it does not even know about.

Hence the habit from §6: free it, then null it yourself.
💼“Stack or heap?” warm-up question
Stack: automatic, fast, sized at compile time, dies at the closing brace. Heap: manual, slower, sized while running, lives until freed.

The follow-up is always “so when do you use the heap?” and today is the answer: when the thing has to outlive the function that made it, or when you do not know how many of them there will be. A linked list is both at once.
💼Smart pointers Class 6
Modern C++ hands ownership to unique_ptr so that freeing happens automatically and a leak becomes hard to write. Knowing that new/delete is the manual version underneath is what makes the smart version make sense — which is why we did it by hand first.
