Where we are

Six operations, and every one of them takes head and tail as two separate arguments. Keeping the two in step is your job, on every line, in every file.

With one list that costs nothing. With two, the program is holding four pointers, and C++ has no way to say which head belongs to which tail. Today you hand that job to the language.

Section 1

Everything works, until there are two lists

⏱ 9 min

Every function you have written takes the list apart into two arguments:

insertLast(Node*& head, Node*& tail, int item)

With one list that is fine. With two, there are four pointers to keep straight. Build both, the way Class 5 built them:

Node *h1 = nullptr, *t1 = nullptr;   // list 1
Node *h2 = nullptr, *t2 = nullptr;   // list 2

insertFirst(h1, t1, 10);            // list 1:  10
insertFirst(h2, t2, 50);            // list 2:  50
insertLast (h2, t2, 60);            // list 2:  50 -> 60

h1 and t1 are list 1’s two ends, h2 and t2 are list 2’s. List 1 holds one node, so h1 and t1 land on the same node. List 2 holds two, so they land on different ones.

The bug is not where the crash is

The typo is on line 7. The program dies on line 18 — inside insertLast, reached from line 8: a function with nothing wrong with it, working on the list you never touched. Switch the two runs above and watch which function each one even enters.

Every argument had the right type, so the compiler had nothing to say. Two lists is four variables; ten lists is twenty. The fix is not more care. The fix is to make the wrong call impossible to write.

Making it impossible to write is the whole of section 2. Before that, one objection is worth answering if your class raises it.

🧩Dig deeper — could you not just use a struct?

Worth ten minutes if the class is with you, and worth skipping if it is not. It is the same answer arrived at from the other side.

Your turn

Write the signature of a function that builds a list of n nodes and hands it back to main.

Node* buildList(int n); returns the head, and the tail stays behind in the function. So you fix it, and the fix is the interesting part:

struct List { Node* head; Node* tail; }; List buildList(int n);

That works. One value, returned, stored in an array, copied. You have just written the first half of a class by hand.

What the struct does not do is stop anybody writing L.head = somewhere; from any line in the program and leaving L.tail pointing at a node that is no longer last. A class is that struct plus a fence: the two pointers put out of reach, and a named list of functions as the only way in. Section 2 builds both halves.

Check yourself — 1 of 6
Someone stops the crash by making insertLast defensive: it now starts with if (tail == nullptr) { head = tail = nw; return; }. The program runs to the end with no error. What does list 2 hold afterwards?
Just 70. head is a reference to h2, so head = tail = nw writes straight into h2. It now names the new node, and the only route to 50 and 60 is gone.

The check did what defensive checks usually do: it moved the symptom. No crash, no message, and two nodes leaked — which is worse, because now nothing tells you at all. The bug is still line 7, and the only fix that works is making that line unwriteable.

Section 2

A place to put an invariant

⏱ 13 min

The answer first, then the work

A class is the answer to section 1. It does two things, and at this point in the course that is the whole of what a class is:

  1. It makes head and tail one value. One name to pass, and nothing left to pair up by hand.
  2. It puts them out of reach. Only the functions listed inside the class can touch them.
class LinkedList {
    Node* head = nullptr;      // out of reach
    Node* tail = nullptr;
    int   n    = 0;

public:                        // the only way in
    void insertFirst(int item);
    void insertLast(int item);
    void insertAt(int pos, int item);
    void deleteFirst();
    void deleteLast();
    void deleteAt(int pos);
    void display() const;      // your Class 3 function
};

Two lists are now LinkedList a; and LinkedList b;. Each keeps its own head and tail inside itself, and you write a.deleteFirst(). There is no second argument to get wrong, so section 1’s typo is a line you cannot type. That is section 1 closed.

🧩Dig deeper — should Node go inside the class?

Both are written in real code, and the choice changes nothing about how the list works — only who is allowed to name the type.

Outside, as above — anyone can write Node* p;. This is what your exam shows, what every textbook shows, and what we use for the rest of the course.

Inside, as a private member — Node becomes LinkedList::Node, and nothing outside the class can even declare one. A library does it this way, because no caller has any business making a raw node.

Keep it outside here. The moment you nest it, every free function that used to take a Node* stops compiling — and in an exam you are usually given a global struct Node to work with.

The rest of this section is the part worth your time: watching your own program become that, one line at a time.

Section 3

Something you could not do before

⏱ 8 min

Safety is a good reason. A new ability is a better one.

“How long is this list?” has cost O(n) all segment: start at head and walk, counting. Nobody keeps a counter instead.

Your turn

Add one int n to your Class 5 code: n++ in every insert, n-- in every delete. The arithmetic is right every time.

So why can you still not trust it?

Because in a structured program nothing makes anyone use them. head is an ordinary variable in main, so any line in any file can go round the six functions and do this instead:

// somewhere else in the program, someone deletes a node by hand Node* d = head; head = head->next; delete d;

The list is one node shorter. n was never touched, so it still says four. length() now returns 4 for a list of 3, and nothing warns anybody.

A counter you cannot trust is worse than no counter, because you will read it and believe it.

Inside a class, that line does not compile. head is private, so the only code that can shorten the list is the methods. If n is ever wrong, the mistake is in one of them — a list of six functions you can read through in a minute. Before, the list was every line in the program.

What private is not

It is not about hiding anything from whoever runs your program. Nothing is encrypted and nothing is secret — private is checked by the compiler, and only while the program is being built.

It is not an unbreakable lock either. You can still write that hand-made delete: open the class, add a method that does it, or move head below public:. What you cannot do is write it by accident, from somewhere else, without anyone noticing.

private is an agreement between the people writing the code — “this list changes only through these functions” — and the compiler is what keeps the agreement from being broken without a deliberate edit to one file.

Six loose functions int length(Node* head) { int n = 0; for (Node* p = head; p != nullptr; p = p->next) n++; return n; } O(n) — and it is the only honest way, because no counter could be trusted.
→
One class class LinkedList { Node *head, *tail; int n = 0; public: int length() const { return n; } }; O(1) — because there are exactly six places that can change it.

The table gains a row that changes

Every row of Class 5 §6 was fixed by the shape of a linked list. This one is not. length() goes from O(n) to O(1), and the reason is not a cleverer algorithm — it is that the data finally has an owner.

The price, stated plainly

Six methods now have one more thing to remember, and it is the same kind of promise as tail from Class 5: every path that adds a node does n++, every path that removes one does n--.

The difference is that this promise can only be broken in six places, and they all sit in one file.

Check yourself — 3 of 6
A teammate adds one method to the class: Node* getHead() const { return head; }. Everything still compiles and every test passes. What has it cost you?
n is a guess again. private is not a magic word; it is a statement about reach. Hand the address out and the reach is back to everybody, keyword or not — and const does not help, because it only promises the method changes nothing.

This is the most common way a class quietly stops being one. Before you add a getter that returns a pointer to the inside, ask what the caller could then do with it.

Section 4

Two functions you never call

⏱ 10 min

A class can carry two special functions. Both run on their own.

The constructor LinkedList() runs the moment the object is made. It sets head and tail to NULL and n to 0. You wrote those three lines by hand at the top of every program in Class 5. Now the type does it, and it cannot be forgotten.

The destructor ~LinkedList() runs at the closing brace of the scope the object lives in. Whatever you put in it happens, every time, without being called.

Your turn

freeList(head) from Class 3 §8 gives a whole list back to the heap. Put that same loop in the destructor and it runs at the closing brace, without being called.

Name two moments when a hand-written freeList(head) would have been missed.

An early return. A function with three return statements needs three freeList calls, and the third one is the one that gets forgotten.

A thrown exception. The rest of the function never runs at all — but destructors still do, on the way out.

There is a third, and it is the honest one: you forget. The destructor cannot.

—

The object is on the stack. Its nodes are not.

Say this out loud, because it is the whole of section 5: the LinkedList object is three small variables in a stack frame, and the frame goes by itself at the brace.

The nodes are in the heap, and nothing takes those back for you. That gap is the only reason the destructor exists.

Check yourself — 4 of 6
A function writes LinkedList* p = new LinkedList;, adds 1000 nodes through p, and returns — with no delete p;. Does the destructor run?
No, and this is the one case the class does not save you. A destructor runs when the object is destroyed. A local object is destroyed at the closing brace; an object made with new is destroyed by delete, and by nothing else.

So new LinkedList with no delete leaks the object and all 1000 nodes, because the destructor that would have freed them never ran. Write LinkedList a; and the brace does it; write new LinkedList and you are back to remembering.

Section 5

The leak you cannot see

⏱ 8 min

Comment the destructor out and everything still works. That is the problem.

Your turn

This loop runs a thousand times. Each turn builds a three-node list, prints it, and lets it go out of scope. There is no destructor.

for (int i = 0; i < 1000; i++) { LinkedList a; a.insertLast(10); a.insertLast(20); a.insertLast(30); a.display(); }

What is on the screen when it finishes, and what is in memory?

On the screen: a thousand correct lines. No error, no warning, no crash.

In memory: 3,000 nodes that nothing points at any more. The three small variables of each object went with their stack frame; the nodes never went anywhere.

—

Why this is worse than a crash

A crash tells you where to look. A leak tells you nothing: the program is correct, the output is right, and the only symptom is that it gets slower and then, hours later, stops.

Class 3 §8 gave you the sentence for it: a leak is memory without a pointer. Here the pointer went out of scope and took the only route to 3,000 nodes with it.

This is not a problem the class invented. Write the same loop with loose pointers and forget one freeList(h);, and you get exactly this picture. The difference is only who is responsible for remembering — and in a structured program that is you, on every path out of every scope.

Put the destructor back and read the loop again

Nothing in main changes. Not one line. The closing brace of the loop body now frees three nodes, a thousand times, and the heap is flat when it finishes.

That is what a destructor is for, and it is the strongest argument for a class that this course will give you.

Check yourself — 5 of 6
Put the destructor back and run the same thousand-turn loop. How many times does it run, and how many nodes does each run give back?
A thousand times, three nodes each. LinkedList a; is written inside the loop body, so a new object is made and destroyed on every turn. The closing brace of a loop body ends a scope like any other.

Move that one line above the loop and the answer becomes the first one — one object, one destruction, and a list that grows to 3,000 nodes instead of a heap that is flat at the end of every turn. Same destructor, completely different program.

Section 6

The problem a class creates

⏱ 6 min

One honest paragraph before you leave, because a class is not free.

Looks harmless LinkedList a; a.insertLast(10); LinkedList b = a; Three pointers are copied. The nodes are not. Now a and b both believe they own them.
→
At the closing brace ~LinkedList() // b runs first ~LinkedList() // then a // the same nodes, // deleted twice A double free. The second destructor gives back memory that is already gone.

Say this exactly right

A class does not remove this danger. Write h2 = h1; with loose pointers and you have the identical bug.

What the class gives you is one place to fix it — a copy constructor that copies the nodes instead of the pointers. With loose pointers there is nowhere to put that fix, so it never gets written.

The rule has a name: if a class needs a destructor, it almost certainly needs a copy constructor and a copy assignment too. That is the rule of three.

Beyond this course

💼The modern answer: unique_ptr not examined
Modern C++ does not write raw new and delete in a data structure. It writes std::unique_ptr<Node> next;, which frees itself when the node holding it dies — so the destructor becomes empty and the double-free becomes a compile error rather than a crash.

It is genuinely better, and it is genuinely not what your exam asks for. You are learning new and delete because the exam asks for them and because you cannot understand what unique_ptr automates until you have done it by hand.

Worth knowing the name exists, so that reading real code later is not a surprise.
Check yourself — 6 of 6
LinkedList b = a; is the danger above. Which of these has exactly the same problem?
By value. A copy is a copy however it is made. void f(LinkedList v) copies a into v, and v’s destructor runs at the end of f — freeing the nodes a is still pointing at. The crash comes later, somewhere else.

LinkedList& makes no copy, and neither does a method call. This is why real code says const LinkedList& in signatures — and why the danger was never caused by the class: h2 = h1; with loose pointers is the identical bug, with nowhere to put the fix.

Reference

📜The whole class, in one piece — ready to compile

Everything from Classes 3, 5 and 6 assembled: the six operations, the tail pointer, the length counter and the destructor. Nothing in it is new — every line has been on screen already. This is the version to revise from, and the version to start Segment 4 from.

struct Node {
    int   data;
    Node* next;
};

class LinkedList {
    Node* head = nullptr;
    Node* tail = nullptr;
    int   n    = 0;

public:
    ~LinkedList();                       // frees every node

    int  length() const { return n; }
    bool empty()  const { return head == nullptr; }

    void insertFirst(int item);
    void insertLast(int item);
    void insertAt(int pos, int item);

    void deleteFirst();
    void deleteLast();
    void deleteAt(int pos);

    void display() const;                 // your Class 3 function
};

// ---------- insert ----------

void LinkedList::insertFirst(int item) {
    Node* nw = new Node;
    nw->data = item;
    nw->next = head;
    head = nw;

    if (tail == nullptr) tail = nw;      // the list was empty
    n++;
}

void LinkedList::insertLast(int item) {
    Node* nw = new Node;
    nw->data = item;
    nw->next = nullptr;

    if (head == nullptr) { head = tail = nw; n++; return; }

    tail->next = nw;
    tail = nw;
    n++;
}

void LinkedList::insertAt(int pos, int item) {
    if (pos == 1) { insertFirst(item); return; }

    Node* prev = head;
    int i = 1;
    while (i < pos - 1 && prev != nullptr) {
        prev = prev->next;
        i++;
    }
    if (prev == nullptr) return;         // no such position

    Node* nw = new Node;
    nw->data   = item;
    nw->next   = prev->next;
    prev->next = nw;

    if (nw->next == nullptr) tail = nw;  // it went on the end
    n++;
}

// ---------- delete ----------

void LinkedList::deleteFirst() {
    if (head == nullptr) return;

    Node* FN = head;
    head = FN->next;
    if (head == nullptr) tail = nullptr;  // that was the last node

    delete FN;
    n--;
}

void LinkedList::deleteLast() {
    if (head == nullptr) return;
    if (head == tail) {
        delete head; head = tail = nullptr; n--; return;
    }

    Node* prev = head;
    while (prev->next != tail)            // n - 2 hops
        prev = prev->next;

    prev->next = nullptr;
    delete tail;
    tail = prev;
    n--;
}

void LinkedList::deleteAt(int pos) {
    if (head == nullptr) return;
    if (pos == 1) { deleteFirst(); return; }

    Node* prev = head;
    int i = 1;
    while (i < pos - 1 && prev->next != nullptr) {
        prev = prev->next;
        i++;
    }
    if (prev->next == nullptr) return;

    Node* cur  = prev->next;
    prev->next = cur->next;
    delete cur;

    if (prev->next == nullptr) tail = prev;   // it was the last node
    n--;
}

// ---------- read, and clean up ----------

void LinkedList::display() const {
    Node* p = head;
    while (p != nullptr) {
        cout << p->data << " ";
        p = p->next;
    }
    cout << endl;
}

LinkedList::~LinkedList() {               // nobody calls this
    Node* cur = head;
    while (cur != nullptr) {
        Node* nxt = cur->next;            // save it before the delete
        delete cur;
        cur = nxt;
    }
    head = tail = nullptr;
    n = 0;
}

// ---------- using it ----------

int main() {
    LinkedList a;
    a.insertLast(10);
    a.insertLast(20);
    a.insertFirst(5);
    a.insertAt(3, 15);
    a.display();                            // 5 10 15 20
    cout << a.length() << endl;           // 4

    a.deleteLast();
    a.deleteAt(2);
    a.display();                            // 5 15

    return 0;                             // ~LinkedList() runs here
}

So why spend an hour on it

Three reasons, and none of them is the exam.

1. The destructor is the only mechanism in the language that fixes the leak you met in Class 3 §8 — and leaks are the one bug this segment can create that has no symptom.
2. Every interview list question hands you a ListNode* and a class around it. Reading that shape has to be free.

Beyond the exam

Where today actually pays

In an interview

💼“What is the rule of three?” asked constantly
If a class needs a destructor, it almost certainly also needs a copy constructor and a copy assignment operator — because whatever the destructor frees, a copy would free twice.

Your linked list is the shortest honest example there is: it takes memory with new, so it needs a destructor, so a bare copy is a double free. Say it with that example and you have answered the question and shown you have hit it.
💼“Why is a queue usually a linked list?” design
Because a queue adds at one end and removes from the other, and with head and tail both of those are O(1). An array can do it too, but only with wrap-around bookkeeping.
