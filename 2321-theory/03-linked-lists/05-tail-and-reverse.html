Where we are

You can build a list, walk it, search it, insert into it and delete from it. All six operations are written and running.

Every one of them that touches the end of the list starts the same way: walk from head until you get there. Today we stop paying that, and then find the one operation that refuses to be fixed.

Section 1

The cost you have been paying all week

⏱ 5 min

Every operation that touches the end of a list starts by walking there from head. That walk is the whole cost.

On five nodes nobody notices. On a million, every single append walks a million nodes to get there.

Your turn

Suppose somebody handed you the address of the last node, always correct, free of charge.

How long does insertLast take now — and is there a row in the table above that this does not fix?

insertLast becomes O(1). You are already standing on the last node, so there is nothing to search for.

deleteLast is not fixed. If you said so, you have found §4.

That second pointer is called tail.

tail is not free — it is a promise

Nothing keeps tail correct for you. It is right only for as long as every operation remembers to update it, and one that forgets breaks the list everywhere else.

That is §2, and it is where the marks are.

Check yourself — 1 of 6
A list has 1000 nodes and a correct tail. How many nodes does insertLast visit?
None. Visiting a node means arriving at it by following arrows from head. With tail you follow no arrows at all — you already hold the address and write straight to tail->next.

“1” is worth saying out loud, because the last node is certainly touched. But it is not visited, and the complexity is the point: O(1).

Section 2

Keeping tail true

⏱ 8 min

Two pointers now describe the list, and they have to agree with each other at all times:

The list has nodes. head is the first, tail is the last, and tail->next is NULL.

The list is empty. head and tail are both NULL. Never one and not the other.

Your turn

Three calls, one after another, on the list 10→20→30. For each, answer just yes or no: does tail have to change?

insertFirst(head, 5); insertLast(head, 40); deleteFirst(head);

Then the one that catches people out: what if the very first of those calls happened on an empty list instead?

No, yes, no. Adding at the front does not move the end of the list. Adding at the end does. Deleting the front does not — unless it was the only node, and then tail must become NULL too.

On an empty list, insertFirst must set both. The new node is the first node and the last node at the same time, and code that only assigns head leaves tail pointing at nothing while the list is not empty.

Two of the three runs below are the ones that catch people out. insertLast is the fourth, and it gets a section of its own.

The bug that gets written every single year

Somebody writes insertFirst, tests it on a list that already has nodes, and it works perfectly. The empty-list branch sets head and forgets tail.

Nothing fails yet. The list prints correctly, the length is right, and insertFirst keeps working. It breaks on the first call to insertLast, which writes to tail->next on a NULL tail — a crash in a function that is not the one with the bug in it.

Say this in the exam

If a question gives you a tail pointer, write one sentence before the code: “every operation that changes the first or last node must update head and tail together, and on an empty list both are NULL.”

It costs you ten seconds and it is exactly the understanding the question is checking.

Check yourself — 2 of 6
A list holds one node. You call deleteFirst. What must happen to tail?
Set it to NULL. That single node was the first node and the last node. Removing it empties the list, and an empty list has both pointers NULL.

“Move it to the previous node” is impossible here for two reasons: there is no previous node, and in a one-way list you could not reach it anyway. That second reason is §4.

What actually changed

Nothing about the list. The nodes are in the same places, holding the same addresses, joined in the same order.

What changed is what we wrote down in advance. Keeping one address to hand turned a search into a lookup, and that is the whole idea behind every index, cache and hash table you will meet later in this course.

The signature grew, and that is worth a sentence

The function now takes Node*& head, Node*& tail — two references, because on an empty list it has to change both. Passing them by value would change the copies and leave the caller’s list untouched, which is exactly the Class 3 §5 mistake with one more pointer to get wrong.

In Class 6 both pointers move inside a class and stop being arguments at all.

insertAt. tail records one address: the end. It says nothing about position 7, so reaching the middle of the list still costs a walk from head.

That is the honest limit of this trick. A pointer buys you the place it points at and nothing else — which is why §4 is about to be a disappointment.

Section 4

The one tail cannot rescue

⏱ 9 min

If a pointer to the last node fixed adding at the end, it ought to fix removing from the end too. It does not, and the reason is the most important sentence in this class.

Your turn

The list is 10→20→30→40→50→60 and tail is on 60. Remove the last node.

Write down every line you would run, in order. Then go back through your own list and check one thing: for each line, can you actually reach what it needs?

30’s next field. It currently holds 40’s address. Free 40 without changing it and 30 is left pointing at memory that has been given back — the dangling pointer from Class 3 §6, and the very next traversal follows it.

And you cannot reach 30 from 40. A one-way node holds the address of the one after it and nothing else. Standing on 40 tells you nothing about what came before.

So the only way to 30 is to start at head and walk. tail got you to the end instantly and then had nowhere to go.

One step there, a full walk back
deleteLast(head, tail)
▸

Watch what happens the moment the walk starts. tail is standing exactly where we want to be, and it is no help at all.

—
rewiringO(1) end to endO(n) nodes visitedn − 1

How many times does that loop run?

Ask it before you show the answer — it is the question that turns “O(n)” from a label into a count.

To delete the last node you need the node before it — on a list of n, that is node n − 1.

prev starts on node 1.

So prev = prev->next runs n − 2 times.

Six nodes, four hops. A thousand nodes, 998 hops. And the loop test runs once more than the body — n − 1 times — because it takes one extra check to discover it is false.

The same counting works for deleteAt(k): you need node k − 1, so the loop runs k − 2 times.

The sentence to keep

A one-way list can go to the end quickly. It can never come back.

Everything that is awkward about a singly linked list is a consequence of that one fact: delete needs a predecessor, reverse needs three pointers, and a tail pointer helps exactly one operation out of six.

So what would fix it?

Give every node the address of the one before it as well. Then tail->prev is the predecessor, and deleteLast becomes O(1) like its twin.

That is a two-way list, and it is Class 7. Notice we are not reaching for it yet on purpose — feeling this limit is what makes the extra field look worth its cost, rather than like more work for nothing.

Check yourself — 4 of 6
A list has a tail pointer. Which pair of complexities is correct for add at the end and delete at the end?
O(1) and O(n). This asymmetry is the examinable part, and it surprises people, so it makes a good question.

The reason fits in one line: adding at the end only needs the last node, which tail gives you. Deleting at the end needs the node before the last one, which nothing gives you — so you walk from head, and tail saves you nothing at all.

Section 5

Turning the whole list round

⏱ 10 min

Reversing a list means the same nodes, in the same places in memory, with every arrow pointing the other way. Nothing is created and nothing is destroyed — only next fields change.

Your turn

You have two O(1) operations already. deleteFirst takes a node off the front. insertFirst puts one on the front.

Using only those two, move every node onto a second, empty list.

What order do they end up in?

Backwards. The first node you take off is the first one you put on, so it ends up at the bottom of the new list. The last one you take off ends up on top.

Taking nodes off one end and putting them onto the same end reverses them — the same reason a stack of plates comes out upside down.

So you already know how to reverse a list. It costs one pass: n removals and n insertions, each O(1).

The version below does exactly that without the second list. Watch prev: it is the second list, growing one node at a time while the first one shrinks.

The same algorithm, in the spelling you already know

You have written this before without calling it reverse. Take the nodes off the front of the old list one at a time and insertFirst each one onto a new list: what comes out is the old list backwards.

Repeated insertFirst while (old != nullptr) { Node* n = old; old = old->next; n->next = fresh; fresh = n; } The way it is usually taught on the board. fresh is the list being built at the front.
=
Three pointers, in place while (cur != nullptr) { Node* nxt = cur->next; cur->next = prev; prev = cur; cur = nxt; } The same four moves, renamed. prev is that new list, and nxt is old.

They are the same code. Line for line: n = old is cur, old = old->next is saving nxt, n->next = fresh is the flip, and fresh = n is prev = cur. Learn either one and you have both.

The one-line mistake

Flip the arrow before saving nxt — cur->next = prev; and then cur = cur->next; — and the loop ends after a single turn with a list of one node.

The reason is on line 7: once it has run, cur->next no longer leads forward. It holds prev, which on the first turn is NULL. The other three nodes are still in the heap with nothing pointing at them — a leak as well as a bug.

That is why line 6 comes first, and it is the third time this rule has appeared: read what you are about to overwrite, before you overwrite it.

Do not forget the last line

When the loop ends, cur is NULL and prev is standing on the node that used to be last. That node is now the first one, so head = prev; is what makes the reversal real.

Leave it out and every arrow is correct while head still points at the old first node — which is now the end, so the list prints one value and stops.

And if the list has a tail pointer

Reversing swaps the two ends, so tail has to swap with head. The tidy way is to remember the old head before you start: it becomes the new tail.

A question that gives you a tail and asks for reverse is checking whether you noticed.

Check yourself — 5 of 6
In the working version, why must nxt = cur->next; come before cur->next = prev;?
The flip destroys the route. cur->next is the only thing in the entire program that knows where the rest of the list is. Overwrite it first and everything after cur becomes unreachable — still in the heap, still linked to each other, and impossible to find.

The habit generalises, and it has now appeared three times: read what you are about to overwrite, before you overwrite it. Delete does it with the victim’s address, freeing a list does it with nxt, and reverse does it here.

The three sentences that carry Segment 3

1. A linked list trades O(1) reading for O(1) growth. It never moves anything.
2. To change the list at a point, you need the node before that point.
3. Reading, writing and rewiring are free. Arriving is what costs.

Your turn — the last one before the test

Cover the table. For each of these, say the complexity and the reason out loud, in that order:

a. insert at the front  ·  b. delete the last node, no tail  ·  c. delete the last node, with a tail  ·  d. find the middle in one traversal  ·  e. reverse

a. O(1) — head is handed to you, so nothing is searched for.

b. O(n) — you need the node before the last, and the only way to it is from head.

c. Still O(n), for exactly the same reason. tail gets you to the last node, not to the one before it.

d. O(n), one traversal — two walkers, one moving twice as fast; when the hare ends, the tortoise is on the middle.

e. O(n) time, O(1) extra memory — three pointers, no new nodes.

If c came out of your mouth as O(1), read §4 once more before the test.

Check yourself — 6 of 6
One sentence explains why insertAt(k) and deleteLast are both O(n). Which one?
Both need a node they can only reach by walking. insertAt needs node k − 1; deleteLast needs the node before the last. Neither address is written down anywhere, so both are searches.

The first option is the array’s problem, not the list’s — a list never moves anything. The third confuses the cost of one heap call with the cost of the walk.

📜The whole program with a tail pointer — ready to compile

The same six operations as Class 3, every one of them now keeping tail true, plus reverse. The lines that exist only because of tail are the ones you saw tinted in §6.

struct Node {
    int   data;
    Node* next;
};

Node* head = nullptr;
Node* tail = nullptr;        // both NULL means the list is empty

// ---------- build ----------

void insertFirst(Node*& head, Node*& tail, int item) {
    Node* nw = new Node;
    nw->data = item;
    nw->next = head;
    head = nw;

    if (tail == nullptr) tail = nw;       // the list was empty
}

void insertLast(Node*& head, Node*& tail, int item) {
    Node* nw = new Node;
    nw->data = item;
    nw->next = nullptr;

    if (head == nullptr) { head = tail = nw; return; }

    tail->next = nw;                      // no walk: we hold the address
    tail = nw;
}

void insertAt(Node*& head, Node*& tail, int pos, int item) {
    if (pos == 1) { insertFirst(head, tail, item); return; }

    Node* prev = head;
    int i = 1;
    while (i < pos - 1 && prev != nullptr) {
        prev = prev->next;
        i++;
    }
    if (prev == nullptr) return;

    Node* nw = new Node;
    nw->data   = item;
    nw->next   = prev->next;
    prev->next = nw;

    if (nw->next == nullptr) tail = nw;   // it went on the end
}

// ---------- remove ----------

void deleteFirst(Node*& head, Node*& tail) {
    if (head == nullptr) return;

    Node* FN = head;
    head = FN->next;
    if (head == nullptr) tail = nullptr;  // that was the last node

    delete FN;
}

void deleteLast(Node*& head, Node*& tail) {
    if (head == nullptr) return;
    if (head == tail) {
        delete head; head = tail = nullptr; return;
    }

    Node* prev = head;
    while (prev->next != tail)            // n - 2 hops, tail or no tail
        prev = prev->next;

    prev->next = nullptr;
    delete tail;
    tail = prev;
}

void deleteAt(Node*& head, Node*& tail, int pos) {
    if (head == nullptr) return;
    if (pos == 1) { deleteFirst(head, tail); return; }

    Node* prev = head;
    int i = 1;
    while (i < pos - 1 && prev->next != nullptr) {
        prev = prev->next;
        i++;
    }
    if (prev->next == nullptr) return;

    Node* cur  = prev->next;
    prev->next = cur->next;
    delete cur;

    if (prev->next == nullptr) tail = prev;   // it was the last node
}

// ---------- see it ----------

void display(Node* head) {
    Node* p = head;
    while (p != nullptr) {
        cout << p->data << " ";
        p = p->next;
    }
    cout << endl;
}

// ---------- turn it round ----------

void reverse(Node*& head, Node*& tail) {
    Node* oldHead = head;                 // it becomes the new tail
    Node* prev = nullptr;
    Node* cur  = head;

    while (cur != nullptr) {
        Node* nxt = cur->next;            // the road out, saved first
        cur->next = prev;                 // the flip
        prev = cur;
        cur  = nxt;
    }
    head = prev;
    tail = oldHead;                       // the two ends swap
}

int main() {
    insertLast(head, tail, 10);
    insertLast(head, tail, 20);
    insertLast(head, tail, 30);
    insertFirst(head, tail, 5);           // tail does not move
    deleteLast(head, tail);               // tail moves back: O(n)
    reverse(head, tail);                  // 20 10 5
    return 0;
}

Take home

A pointer buys you the place it points at, and nothing else.

tail bought the end of the list, so add-at-the-end became free. It bought nothing about the node before the end, so delete-at-the-end did not move at all. Every structure in the rest of this course is an answer to the same question: which addresses are worth writing down in advance?

Tail is not a topic. It is a sentence.

No exam has ever set a question called “tail pointer”. What they set is “insert an item at the end” and “give the time complexity”, and a tail pointer is how you turn the second one into a mark instead of a shrug.

If the question does not mention a tail, say so and use one anyway: “without a tail pointer this is O(n); with one it is O(1), so I will keep a tail.” Naming the reason is what earns the mark.

Answer template

“Give the time complexity” — the version that scores

Every complexity answer in this segment has the same three parts, and most students write only the first.

1. The answer. O(1), or O(n).

2. What has to be found. “because it needs the node before the last one…”

3. Why that costs what it costs. “…and the only way to reach it is by walking from head.”

Worked, for the question that catches people out:

Half a mark deleteLast is O(n). True, and it demonstrates nothing. The examiner cannot tell this apart from a guess.
→
Full marks O(n). Deleting the last node means changing the next field of the node before it. A one-way node holds no address of its predecessor, so that node can only be reached by walking from head. A tail pointer does not help: it gives the last node, not the one before it. Four sentences, and every one of them is a thing you were meant to have understood.

The table to reproduce from memory

insertFirst and deleteFirst are O(1). insertLast is O(n), or O(1) with a tail. deleteLast is O(n), tail or no tail. Everything at a position is O(n). Search and traverse are O(n).

If you can write that and give the reason for the deleteLast row, you can answer any complexity question in Segment 3.

Beyond the exam

The same class, in an interview

In an interview

💼“Reverse a linked list” LeetCode 206 · easy
The single most asked linked-list question there is. Say the three pointers out loud before you write anything: “prev, cur, and a temporary for the next node, because the flip destroys it.”

The follow-up is “can you do it recursively?” — you can, and it costs O(n) stack space, so the loop is better. Saying that unprompted is worth more than writing the recursion.
💼“Why keep a tail pointer?” design
Because a queue needs both ends: you add at one and remove from the other. With head and tail on a linked list, both are O(1), and that is exactly how a queue is built — you will meet it in Segment 4.

The good follow-up answer is the cost: “the price is that every operation has to maintain it, and the empty-list case is where it usually goes wrong.”
💼“Make deleteLast O(1)” the real question
This is a trap, and the answer is not more pointers of the same kind. On a singly linked list it cannot be done, because the operation fundamentally needs a predecessor and the structure does not record one.

The right answer names the structural change: make it doubly linked, and then tail->prev is the predecessor and the operation is O(1). Saying “you cannot, unless you change the node” is a stronger answer than any amount of cleverness — and it is Class 7.

If you only rehearse one thing from this class

Rehearse the deleteLast answer, out loud, in twenty seconds: it is O(n), it needs the node before the last, a one-way node has no way back, and a tail pointer does not fix it.

It is one exam mark, one interview answer, and the entire argument for the two-way list in Class 7 — all in four sentences.
