Resolving Conflicts: A Smart Mapping Formula

Before designing standard resolutions, let's explore if we can bypass collisions entirely by applying a more rigorous mathematical formula. Instead of using a simple modulo 1000, we could design a formula that maps current regular students into one block of the array, and previous batches into separate sections based on admission year. Since rolls range up to 400:

// Clever Mapping Rule for an Array of size 1000
int index;
if (year == 26) {
    // Regular Batch maps directly to indices 0 - 400
    index = roll % 1000;  
} else if (year == 24) {
    // Batch 24 irregulars map to 401 - 800
    index = (400 + roll) % 1000;
} else if (year == 25) {
    // Batch 25 irregulars map to 801 - 999, wrapping to 0 - 200
    index = (800 + roll) % 1000;
}

5 Formalizing the Magic

Now that you've intuitively built the structures to solve our IIUC problem, let's map them to standard Computer Science vocabulary.

Key (K)

The unique identifier for the data.
E.g., Student ID 263040.

Hash Function H(K)

The math formula that shrinks the Key.
E.g., ID % 1000.

Hash Value

The resulting integer used as an index.
E.g., Index 40.

Hash Table

The actual array storing the records.
E.g., Array of size 1000.

Strategy A (Look Next Door) is formally called Open Addressing (Closed Hashing).

Strategy B (External Lists) is formally called Separate Chaining (Open Hashing).

Resolving Collisions: The Formal Methods

If we use Open Addressing (staying inside the array), how exactly do we "look for the next hole"? The variable $i$ represents the attempt number ($i=0, 1, 2...$).

Linear Probing

Jump by exactly 1 sequential slot on each attempt until an empty slot is found.

Example (M=10): Suppose base hash $H_1(k) = 2$ is already full.
• Attempt 1 ($i=1$): Probe index $(2 + 1) \pmod{10} = 3$
• Attempt 2 ($i=2$): Probe index $(2 + 2) \pmod{10} = 4$
Causes Primary Clustering (adjacent filled slots merge into long, slow-to-traverse blocks).
$$Idx = (H_1(k) + i) \pmod M$$
$H_1(k)$ = Base Hash, $i$ = Attempt

Quadratic Probing

Jump outward by perfectly square increments ($1, 4, 9, 16, \dots$).

Example (M=10): Suppose base hash $H_1(k) = 2$ is already full.
• Attempt 1 ($i=1$): Probe index $(2 + 1^2) \pmod{10} = 3$
• Attempt 2 ($i=2$): Probe index $(2 + 2^2) \pmod{10} = 6$
• Attempt 3 ($i=3$): Probe index $(2 + 3^2) \pmod{10} = 1$
Breaks primary clustering by skipping over adjacent blocks!
$$Idx = (H_1(k) + i^2) \pmod M$$
$i^2$ forces non-linear dispersal

Double Hashing

The jump stride itself is computed dynamically by a secondary hash function $H_2(k)$.

Example (M=10): Let base $H_1(k) = k \pmod{10}$ and stride $H_2(k) = 7 - (k \pmod 7)$. For $k=11$:
• Base Hash $H_1(11) = 1$
• Jump Stride $H_2(11) = 7 - (11 \pmod 7) = 3$
If slot $1$ is full, we probe index $(1 + 1 \cdot 3) = 4$, then $(1 + 2 \cdot 3) = 7$, etc.
Solves all clustering forms. Every key has a unique jump pattern!
$$Idx = (H_1(k) + i \cdot H_2(k)) \pmod M$$
$H_1(k)$ provides origin, $H_2(k)$ provides stride.

Why is Prime Modulo ($\pmod M$) Crucial?

In division-based hashing $H(k) = k \pmod M$, the selection of the table size $M$ is the single most critical factor in achieving true $O(1)$ amortized lookup. Computer scientists almost universally select a prime number for $M$.

Interactive Proof: Multiples of $5$ ($k = 5, 10, 15, 20...$)

Bad: Composite $M = 10$ $5 \pmod{10} = \mathbf{5}$
$10 \pmod{10} = \mathbf{0}$
$15 \pmod{10} = \mathbf{5}$
$20 \pmod{10} = \mathbf{0}$
Catastrophic clustering! Uses only slots 0 and 5!
Good: Prime $M = 11$ $5 \pmod{11} = \mathbf{5}$
$10 \pmod{11} = \mathbf{10}$
$15 \pmod{11} = \mathbf{4}$
$20 \pmod{11} = \mathbf{9}$
Beautiful, uniform distribution across the table!
Explore the Mathematical and Cycle Proofs
1. Shielding Against Key Patterns

Let $M$ be the size of the table, and let the subset of keys be offset by intervals of $c$ (where $c$ is a common divisor). We can write these keys as $k = r \cdot c$ for some integer $r$.

If we perform division hashing, the index assigned to a key is: $$Idx = (r \cdot c) \pmod M$$

If $M$ and $c$ share a greatest common divisor $d = \gcd(c, M) > 1$, then $M$ can be represented as $d \cdot m'$, and $c$ as $d \cdot c'$. The index can be rewritten as: $$Idx = (r \cdot c') \cdot d \pmod{d \cdot m'}$$

This algebraic identity guarantees that $Idx$ is always a multiple of $d$. Consequently, instead of scattering keys across all $M$ possible slots, the keys are strictly forced into a restricted subset of only $\frac{M}{d}$ slots!

2. Guaranteeing Complete Probe Cycles

In Double Hashing, we jump in steps of size $H_2(k)$. To visit every slot in an array without skipping open cells, we require: $$\gcd(H_2(k), M) = 1$$

If $M$ is a prime number, this greatest common divisor is mathematically guaranteed to equal $1$ for any possible secondary step size $1 \le H_2(k) < M$. The sequence will securely traverse all $M$ cells before looping.

Check yourself

Why is a prime table size M usually preferred?

If M shares a common factor with regular patterns in the keys, only a fraction of the slots ever get used. A prime shares no small factors with those patterns, so keys scatter across the whole table. (No size eliminates collisions — the pigeonhole principle still applies — and Java actually uses powers of two, not primes.)

In Separate Chaining, each index in the primary array points to an auxiliary data structure. Traditionally, this is a Singly Linked List. However, if a bucket receives too many collisions, search degrades to $O(L)$ where $L$ is the chain length.

Searching in Hash Tables

Searching a hash table requires evaluating the key's hash value, $H(K)$, and accessing that index directly. If a collision occurred during insertion, we must execute the matching probe strategy (for Open Addressing) or chain traversal (for Separate Chaining) until the item is found or search fails.

Searching with Probing

Start at index $H(K)$. If occupied by a different key, proceed to probe subsequent indices $(H(K) + f(i)) \pmod M$.

Stop Condition: Search terminates with a "Not Found" state immediate upon hitting a physically Empty slot.

Searching with Chaining

Go directly to list head at index $H(K)$. Traverse the list linearly until finding a key match, or hitting the null sentinel node.

Search Time Complexity & Load Factor ($\alpha$)

The efficiency of lookups depends directly on the Load Factor, $\alpha = \frac{N}{M}$ (ratio of keys to table size).

Chaining Style Best Case Average Case Worst Case
Separate Chaining (List) $O(1)$ $O(1 + \alpha)$ $O(N)$ (all keys in 1 bucket)
Treeified Chaining (Java 8) $O(1)$ $O(1 + \log L)$ $O(\log N)$ (balanced tree worst-case)
Open Addressing (Probing) $O(1)$ $O\left(\frac{1}{1-\alpha}\right)$ $O(M) \approx O(N)$ (probing full array)

*Note: As long as the load factor is kept small (e.g. $\alpha \le 0.75$ through dynamic resizing), the average-case search time complexity remains strictly constant time, $O(1)$.*

Deletion Complexities

The time complexity to delete a key in a hash table involves locating the item first (equivalent to a search operation) and unlinking/updating its state:

Separate Chaining Deletion

  • Best Case: $O(1)$ (located at head of chain).
  • Average Case: $O(1 + \alpha)$ (requires traversing a short bucket chain).
  • Worst Case: $O(N)$ (if all items are clumped into one linked bucket).

Open Addressing (Probing) Deletion

  • Best Case: $O(1)$ (element found directly at index $H(k)$).
  • Average Case: $O\left(\frac{1}{1-\alpha}\right)$ to locate, then writing the TOMB node is $O(1)$.
  • Worst Case: $O(M) \approx O(N)$ if we probe across the entire table.

Important Performance Warning: While Tombstones keep lookup chains intact, too many tombstones degrade search performance over time (as the search engine must probe past them instead of terminating early). Standard runtime libraries mitigate this by triggering a full rebuild / table rehash once a tombstone threshold is crossed.

Check yourself

In open addressing, why can't we delete a key by simply emptying its slot?

A search stops at the first empty slot it hits. Blanking a slot in the middle of a probe path makes everything placed further down that path look absent. A tombstone marker keeps the path intact while signalling the slot is reusable.

Industry Reality: Java, C++ & Load Factor

The Secret to Amortized O(1): Load Factor ($\alpha$)

$\alpha = \frac{N \text{ (keys)}}{M \text{ (table size)}}$. If the table gets too full, collisions skyrocket and $O(1)$ degrades to $O(N)$.

Dynamic Resizing: Standard libraries set a threshold (e.g., $\alpha = 0.75$). When reached, they allocate an array twice as large and $O(N)$ rehash everything. This penalty happens so rarely that the Amortized time remains strictly $O(1)$.

C++ STL

std::unordered_map is typically implemented using Separate Chaining. It uses contiguous arrays of pointers for excellent cache locality on the buckets, but nodes themselves are allocated on the heap.

#include <unordered_map>
std::unordered_map<std::string, int> marks;
marks["C263011"] = 88; // O(1) avg insert

Java HashMap

Java also uses Separate Chaining. To prevent malicious users from causing $O(N)$ searches by intentionally creating collisions, Java 8 added a feature: if a bucket's linked list grows beyond 8 elements, it automatically converts into a Red-Black Tree, dropping worst-case searches to $O(\log N)$.

import java.util.HashMap;
HashMap<String, Integer> marks = new HashMap<>();
marks.put("C263011", 88); // Amortized O(1)

Checkpoint — end of the Hashing Journey

Here is the path we took. Each step exists because the one before it broke.

Arrays, lists, trees — every search costs O(n) or O(log n)
Direct addressing — H(k) = k mod M: one jump, O(1)
Collisions — two keys, one slot; the wall every hack hits
Resolution — linear / quadratic probing, double hashing, chaining
Load factor α — resize before clustering kills O(1)

That, end to end, is a hash table — the structure behind Python's dict, Java's HashMap, and C++'s unordered_map.

You can now

  • Explain why H(k) = k mod M turns a search into one array jump — and why two keys can land on the same slot.
  • Resolve a collision three ways — linear probing, quadratic probing, double hashing — and chain when the table is crowded.
  • Choose a hash function (division, mid-square, folding) and say why a prime modulus protects it from patterned keys.
  • Delete safely with tombstones, and explain what breaks if you just empty the slot.
  • Read a load factor: know why Java resizes at α = 0.75 and what happens to probe counts as α → 1.

Predict before you leave: a table uses linear probing at α = 0.9. Roughly how many probes does an average successful lookup take? (½(1 + 1/(1−α)) ≈ 5.5 — and it explodes as α → 1. That is exactly why real tables resize early.)
