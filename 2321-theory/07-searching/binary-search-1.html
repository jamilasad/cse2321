Advanced Binary Search · Session One of Two

The Boundary

From "which occurrence?" to lower_bound and upper_bound

Classic binary search tells you whether a value exists. In this session we rebuild it to find a boundary instead — the exact position where a condition first becomes true. That single shift turns binary search into a tool for counting duplicates, inserting in order, and computing floor and ceiling, and it sets up the bigger idea in Session Two.

Session One — Learning Outcomes

By the end of this session, students will be able to:

1

Explain why classic binary search finds an occurrence of a duplicate, but not the first or last.

2

Write the boundary template (l = m / r = m, loop while r - l > 1) to find the first 1 in a 0…0 1…1 array.

3

Use the sentinels l = -1, r = n to handle the all-0s and all-1s edge cases.

4

Turn any comparison into a check(m) predicate, and state why it must be monotone.

5

Apply lower_bound and upper_bound to first/last occurrence, counting, insertion, floor, and ceiling.

Session One · The Boundary
1

A Quick Recap

Here is a sorted array of ten numbers. Our target is 7. Step through the classic algorithm and watch which line of code is running.

Each step compares a[mid] to the target and throws away half of what remains. Ten elements take about four steps, a thousand about ten, a billion about thirty. That halving is why binary search runs in $O(\log n)$.

We are about to ask this array a question it was not built to answer.

2

The Duplicates Dilemma

Same array. Same code. New target: 5. There are four of them, at indices 2, 3, 4 and 5.

The task: find the index of the last 5. Watch whether the classic algorithm can tell you that.

It stopped at index 4 and returned. That is not a bug. The code answered exactly the question it was asked: "does a 5 exist?" — and it does. It was never asked which 5.

But our real question is: where is the first 5? Where is the last 5?

Active Reflection

We are standing on a 5 at index 4. What is your instinct for finding the first one?

Think first. Then open.

Almost everyone says: "just walk left until the number changes."

Now imagine an array of one million elements, and every single one of them is a 5. That walk visits all of them. You spent $O(\log n)$ finding the element and then $O(n)$ finding its edge — so you spent $O(n)$.

We need the edge itself, in $O(\log n)$, without ever taking a step sideways.

3

Inventing Boundary Search

3.1  Stop comparing. Start labelling.

Ask every element one yes/no question: is a[i] > 5? Write 0 for no and 1 for yes.

All the 0s come first. Then all the 1s — because the array was sorted.

So: where is the first 1? The cell just before it is the last 5.

The question is no longer "where is the value 5." It is "where is the border between the 0s and the 1s." Find the border and you have the answer.

3.2  A brand-new problem: find the first 1 in an array of 0s and 1s

Same picture as above, but now the values are hidden. The array is some 0s followed by some 1s, and we want the index of the first 1. You have two pointers, L at index 0 and R at index 9. Each turn you may reveal one cell — the middle one — then move L or R onto it.

Play a few rounds before reading on. Notice how few cells you actually need to reveal.

Interactive Game

Rule 3 · lockedclose the gap …

3.3  What you just discovered

You revealed only about four cells out of ten — the same halving as binary search. The same algorithm solves this new problem. Only the question changed.

Look at your two moves. You never wrote m + 1 or m - 1. You wrote L = m and R = m, because m is the one cell whose value you just learned. You keep it as the new boundary instead of skipping past it.

You stopped when the two pointers were next to each other: R - L == 1. At that point L points to the last 0 and R points to the first 1.

The binary search algorithm did not change. We only changed the question — from "where is the value" to "where is the border."

We started at L = 0 and R = 9, the ends of the array. Section 5 shows why that choice can fail.

4

The Template — First Draft

Write down exactly what you did in the game. Nothing more, nothing clever. 

int first_true(vector<int>& a) {
    int l = 0, r = a.size() - 1;   // the two ends of the array

    while (r - l > 1) {             // while something is still unknown between them
        int m = (l + r) / 2;        // reveal the middle cell

        if (a[m] == 1) r = m;       // a 1 — the border is here or to the left
        else           l = m;       // a 0 — the border is strictly to the right
    }
    return r;                       // r = first 1        (l = last 0)
}

Why it is correct

a[l] is always 0 and a[r] is always 1. Both branches keep this true. When L and R become adjacent, L points to the last 0 and R points to the first 1 — so we return r.

Why it stops

m always lands between L and R. Moving L or R onto m makes the gap smaller every turn, until they are adjacent.

Why it is easy to remember

Both branches just write = m. No +1 or -1 to place on the right line, so there is no off-by-one to get wrong.

Run it on our labelled array and it returns 6 — the first 1. It works. Now let us try to break it.

5

When the Pointers Lie

The template worked on a mixed array. But two legal arrays we never tried: all 0s (no 1 to find) and all 1s (the answer is index 0). Run each on the same code.

With l = 0, r = n-1 both arrays return the wrong answer, and the program gives no error. Look at what that starting line assumes:

r = n - 1

assumes the last cell is a 1. In an all-0s array that is false — before the loop even starts.

l = 0

assumes the first cell is a 0. In an all-1s array that is false, and index 0 — the answer — is never checked.

The loop trusts these two assumptions and only works on the middle. So place the pointers one step outside the array, where no real element can make the assumption false.

The fix

int l = -1,   r = n;

Treat index -1 as a 0 and index n as a 1. Neither cell exists, so neither assumption can be false. All 0s → r stays at n ("no 1"). All 1s → r moves to 0. Both correct.

But a[-1] would crash. It would — if we ever read it. Look at the loop: it only ever reads a[m], and l < m < r keeps m safely inside. l and r are not addresses. They are claims about what we know.

A note for later. Where would an all-0s or all-1s array even come from? From labelling, exactly as we did in Section 3 — ask each element a yes/no question and write 0 or 1. Some questions produce all 0s or all 1s. Keep that in mind; in Section 8 it becomes the whole point.

Check yourself
Now reverse the problem. The array is some 1s followed by some 0s, like 1 1 1 0 0, and you want the first 0. What check makes the labels go 0…0 1…1 so the same template works?
The template always finds the first cell where the check is true. To find the first 0, make "is it a 0?" the check — then the 1s become 0-labels, the 0s become 1-labels, and the first true is the first 0. The loop never changes; only the check does.
6

The Array Was Never the Point — the check Is

The loop reads a[m] only to ask one yes/no question. Give that question a name — check(m) — and put it in its own function. The only line that changes is the if: 

bool check(int m) { return a[m] == 1; }   // "is the label at m a 1?"

int first_true() {
    int l = -1, r = n;
    while (r - l > 1) {
        int m = (l + r) / 2;
        if (a[m] == 1) r = m;          // old
        if (check(m)) r = m;         // new — same loop
        else           l = m;
    }
    return r;
}

Same l = -1, r = n, same while, same branches. The loop no longer needs an array — it needs a check(m) that returns true or false. Change the check, and the same nine lines solve a different problem.

The shift in thinking

You write the check. The binary search stays the same.

Every section from here is just a new check. It has one requirement — the labels must read 0 … 0 1 … 1. The next section shows what happens when they don't.

The version that hangs forever — can you spot why?

This looks reasonable, but on some inputs it loops forever. Read it before opening the explanation.

int first_true() {
    int l = 0, r = n - 1;
    while (l < r) {
        int m = (l + r) / 2;
        if (check(m)) r = m;
        else           l = m;   // <-- never moves past m
    }
    return r;
}

Why it hangs: when l and r are adjacent (r = l + 1), the midpoint is m = (l + r) / 2 = l. If check(m) is false we set l = m — that is l = l. Nothing changes, and the loop spins forever.

The template avoids this by design: it loops while r - l > 1 (stops when they are adjacent, never probing m = l) and starts at l = -1, r = n. That is exactly why we insist on the two rules together — drop either one and you get this.

7

Does Every check Work?

We can now plug in any check. But can we trust every check? Here is one whose labels are not a clean block — they go 1, then back to 0, then 1 again. Run our template on it and watch what it returns.

the labels

0011000111

The first 1 is at index 2. Run our repaired template and watch where it lands.

No error. No crash.
It returned index 10 — but the first 1 is at index 2.

The first probe landed on index 4, saw a 0, and moved L right — discarding indices 0 to 4, including the real first 1 at index 2. The template is built on one assumption: once the labels turn to 1, they stay 1. This array breaks that, so the search goes wrong from the first step.

This property has a name. A check is monotone when its labels, read left to right, never go from 1 back to 0:

monotone

0000001111

Once it turns on, it stays on. Safe.

not monotone

0011000111

It turns on, off, on. Binary search lies.

The one requirement, for every problem from here on

Your check must be monotone: 0 … 0 1 … 1.

Formally: if check(i) is true, then check(i+1) must be true. Prove that, and binary search is guaranteed. Skip it, and you get a confident wrong answer.

Quick check

Which of these label rows are safe for our template — that is, monotone?

A 0001111111

B 0110111111

C 0000000001

D 1110000000

Check your answer.

A and C are safe — the 1s never turn back to 0. B and D are not. B has a 0 after some 1s; D starts with 1s and then drops to 0. On B or D the template can skip the answer, exactly as it just did above.

8

So … Where Was the Last 5?

We opened the lesson with a question classic binary search could not answer: in [1, 3, 5, 5, 5, 5, 7, 9, 13, 13], find the index of the last 5. Can we solve it now? Recall three things we have built:

  • We can turn a sorted array into 0s followed by 1s by labelling it with a check.
  • Our template finds the first 1 in such a labelling.
  • Only the check changes between problems.

So the real question is: which check turns "find the last 5" into "find the first 1"?

Stop and think

Try to name that check(m) before opening the answer.

You have already seen it.

In Section 3 we labelled with check(m) = a[m] > 5 and got 0000001111.

The first 1 is at index 6 — the first element greater than 5. So the cell just before it, index 5, is the last 5.

So we solve it without writing any new search: choose a monotone check that turns the problem into "find the first 1," then reuse the same nine lines. The last 5 is one step before the first element greater than 5:

reading this line left to right

check(m) = ( a[m] > 5 )  →  first_true() = 6  →  last 5 = 6 − 1 = 5

Use the check a[m] > 5. The template returns 6, the first element greater than 5. Subtract 1 to get the last 5, at index 5.

See the full code for "last 5" 
// the check we chose: is a[m] past the last 5?
bool check(int m) { return a[m] > 5; }

int last_five(vector<int>& a) {
    int l = -1, r = a.size();
    while (r - l > 1) {
        int m = l + (r - l) / 2;
        if (check(m)) r = m;   // first index where check is true
        else           l = m;
    }
    return r - 1;              // one step before that = the last 5
}
9

The Two Checks with Names: lower_bound and upper_bound

With the check a[i] > 5 the border landed just past the last 5. Change one character — > to >= — and the border moves to the front of the block. Same array, same loop, a different question answered.

Drag x and toggle the check

lower_bound(x)

label with a[i] >= x

First index holding something not less than x. If x is present, this is the first x.

upper_bound(x)

label with a[i] > x

First index holding something strictly greater. The last x is one step before it.

The clearest way to picture the two bounds: lower_bound(x) is the leftmost position where x could be inserted and keep the array sorted; upper_bound(x) is the rightmost. Pick a case below and watch where the new value slots in and which cells shift to make room:

Both are our template. Only the check differs, by one character:

lower_bound

bool check(int m) {
    return a[m] >= x;
}
int l = -1, r = n;
while (r - l > 1) {
    int m = (l + r) / 2;
    if (check(m)) r = m;
    else           l = m;
}
return r;

upper_bound

bool check(int m) {
    return a[m] > x;
}
int l = -1, r = n;
while (r - l > 1) {
    int m = (l + r) / 2;
    if (check(m)) r = m;
    else           l = m;
}
return r;

Step through the four canonical cases below. Watch L and R move inward: an arrow shows which pointer jumped and in which direction. The returned r is the border — and for lower_bound(6) it points to where a 6 would be inserted, even though no 6 exists.

The trap. "Floor is lb(x) - 1" is wrong whenever x is actually present — then lb(x) points at x, so lb(x) - 1 gives you the largest element strictly less than x. Slide x to 5 above and read both off the screen.

Memorise this, it is the most-failed exam line

FLOOR  (largest ≤ x)

ub(x) − 1

CEIL  (smallest ≥ x)

lb(x)

Floor reaches past x and steps back one, so it needs ub. Ceil lands on or after x already, so it is just lb. The instinct lb(x) - 1 for floor is the wrong one.

10

You Don't Have to Write It: the C++ STL

You now understand exactly what these do, so use the library versions. On a sorted vector, the standard algorithms are the same two borders you just built: 

vector<int> a = {1,3,5,5,5,5,7,9,13,13};

bool found = binary_search(a.begin(), a.end(), 5);          // true / false only

auto lo = lower_bound(a.begin(), a.end(), 5);          // first >= 5   -> index 2
auto hi = upper_bound(a.begin(), a.end(), 5);          // first  > 5   -> index 6

int first = lo - a.begin();          // 2
int last  = hi - a.begin() - 1;      // 5
int count = hi - lo;                 // 4

binary_search is the classic "does it exist" answer. lower_bound and upper_bound are the two borders, and subtracting a.begin() turns the returned iterator into the index. Everything from Section 9 — first, last, count, floor, ceil — is just arithmetic on those two.

Interview landmine — read this once, remember it forever

On a std::set (or map), always call the member function s.lower_bound(x). It walks the tree in $O(\log n)$.

The free algorithm std::lower_bound(s.begin(), s.end(), x) compiles on a set — but a set's iterators are not random-access, so it cannot jump to the middle. It steps one node at a time and silently degrades to $O(n)$. It passes every small test and melts in production.

The rule: member function on tree-based containers (set, map) · free function on sorted arrays and vectors.
