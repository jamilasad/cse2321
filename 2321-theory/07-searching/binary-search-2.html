Advanced Binary Search · Session Two of Two

Binary Search on the Answer

Searching for a boundary when there is no array

In Session One the array was on screen. Here it disappears. We solve real problems — square roots, cutting ropes, eating speeds — by guessing an answer and asking one yes/no question about it, and we find the same boundary search underneath all of them.

Prerequisite: Session One — the boundary template, sentinels, and the check(m) abstraction.

Session Two — Learning Outcomes

By the end of this session, students will be able to:

1

Recognise that "binary search on the answer" is just searching for the 0→1 boundary of a check(m).

2

Design a monotone check(m) for a new problem — and read off the answer as l or r.

3

Test whether a check is monotone, and explain why the search fails when it is not.

4

Extend the method to real-valued answers, and recognise the pattern in real interview problems.

1

The Array Was Never the Point

You just met the question in the warm-up. Here is the proof. This is a sorted array from Session One — and our task is the classic one: find where it crosses from below 5 to 5-or-more (the lower_bound of 5).

Predict first: to find that crossing, does the search need the values 1, 3, 5, 5… — or only the answer to "a[i] ≥ 5?" at each cell?

bool check(int i) { return a[i] >= 5; }   // the only question we ever ask a cell

The point

The search only ever read the 0/1 answers from check. Once they existed, the values were dead weight — the array was just one way to produce them.

So here is the question that runs through all of Session Two: if we don't need an array, what if the answers came from arithmetic instead of memory?

Inventing: Integer Square Root

The goal: find $\lfloor \sqrt{x} \rfloor$ — the largest integer whose square is at most $x$. No sqrt() allowed, and no array exists.

⌊√50⌋ = 7
7²=49 ≤ 50 < 64=8²
⌊√49⌋ = 7
7²=49 ≤ 49 < 64=8²
⌊√64⌋ = 8
8²=64 ≤ 64 < 81=9²

Predict first: Section 1 proved that any 0/1 row can be searched. So — can you invent a check(m) that turns candidate answers into such a row here? Build it one card at a time.

Invent it — one card at a time

1. The Space: If we are guessing the answer, what is the absolute minimum and maximum it could be?

$L = 0$ (lowest possible)
$R = 50$ (highest possible)

2. The Guess: Let's guess $m = 8$. We need to know if 8 is too big. What single yes/no math question proves this without using sqrt()?

bool check(int m) {
    return m * m > 50;  // true if m is strictly too big
}

3. The Pattern: If we apply this question to guesses $m = 3, 4, \ldots, 12$, what are the boolean answers?

The Epiphany

Does this look familiar? It is exactly the 0…0 1…1 boundary from Session One. The first 1 appears at $m = 8$ (the first number that is too big). Therefore the correct floor is $8 - 1 = 7$.

We don't need a new algorithm. We just feed this check(m) into yesterday's template.

So here is the whole thing — the same boundary template as always, with check pulled out as a plain function (it takes x as a second argument now that it is no longer inside isqrt). Step through isqrt(50) and watch the trace:

Trace it — one line at a time

Watch which line runs, how check turns each guess into a 0/1, and how l and r close in on the boundary — all on the number line, with no array in sight.

bool check(long long m, long long x) { return m > x / m; // m*m > x, overflow-safe (true = too big)} long long isqrt(long long x) { // requires x >= 0 long long l = 0, r = x + 1; // 0 always fits; x+1 never does while (r - l > 1) { long long m = l + (r - l) / 2; if (check(m, x)) r = m; // too big → drop the right else l = m; // fits → raise the left } return l; // last m that fits == floor(sqrt(x))}
The number line · candidate answers 0…50
Why >, not ≥: we want the largest m with m*m ≤ x. Using m*m > x keeps perfect squares on the "fits" side, so isqrt(1024) = 32, not 31.
Why l = 0 here, not l = −1: don't copy the sentinel from Session One without thinking. In lower_bound we needed l = −1 because there might be no valid index — the sentinel had to sit below the whole range. Here we require x ≥ 0, and 0 is a genuine answer: 0·0 = 0 ≤ x always fits. So l = 0 is not a placeholder, it is a real lower bound — and it matters. With l = −1 the first midpoint is m = 0 whenever x ≤ 1, and check then computes x / 0. The "overflow-safe" line crashes on the two smallest inputs. The template is a tool, not a ritual.

Second Example: Cutting Ropes

Codeforces EDU · Binary Search, Step 2·B

You have n ropes of lengths aᵢ. You want k pieces that are all the same length L — find the largest L possible. A rope of length a gives ⌊a/L⌋ whole pieces (the leftover is wasted).

Add up the pieces from every rope. A length L works if the total is k or more — in symbols, total = Σ⌊aᵢ / L⌋ ≥ k.

Worked example — ropes [8, 5, 12, 7], need k = 6 pieces:

L = 4 → works

8→2, 5→1, 12→3, 7→1

The rope of length 8 gives 2 pieces of length 4, the rope of 5 gives 1, the rope of 12 gives 3, the rope of 7 gives 1.

total = 7 pieces, and 7 ≥ 6

L = 5 → fails

8→1, 5→1, 12→2, 7→1

Now the pieces are longer, so each rope gives fewer: 8 gives only 1, 5 gives 1, 12 gives 2, 7 gives 1.

total = 5 pieces, and 5 < 6

Stretching each piece from 4 to 5 drops the total from 7 down to 5 — below the 6 we need. So 4 is the largest length that still works: the answer is 4, not 5.

Your turn first

Before you open the simulator: what should check(L) return so the labels come out 0…0 1…1 (the shape our loop wants)?

Ask one question about L: "is this length too long?"

  • Count the pieces at length L, and return true when there are too few — total < k.
  • A small L gives many pieces → not too long → 0.
  • A large L gives too few pieces → too long → 1.
  • So the row reads 0…0 1…1, and the last 0 is the largest length that still works.
bool check(long long L) {          // true = L is too long
    long long pieces = 0;
    for (long long a : rope) pieces += a / L;   // whole pieces this rope gives
    return pieces < k;                     // too few pieces = too long
}
The four ropes, cut into L-long pieces
Piece length L = 3
that same L, written as one 0/1 cell

Feasibility is naturally 1 1 1 … 0 0 (small L works, large doesn't). To get the 0…0 1…1 the loop expects, check tests the negation — "too long." The last 0 (return l) is the largest length that still works. Same loop as sqrt — only check changed, and it is a plain function now: 

bool check(long long L, vector<long long>& rope, int k) {     // true = L too long (too few pieces)
    long long pieces = 0;
    for (long long a : rope) pieces += a / L;              // bigger L -> fewer pieces
    return pieces < k;
}

long long largestLength(vector<long long>& rope, int k, long long maxLen) {
    long long l = 0, r = maxLen + 1;              // lo = 1, hi = maxLen  --  SAME template
    while (r - l > 1) {
        long long m = l + (r - l) / 2;
        if (check(m, rope, k)) r = m;
        else                    l = m;
    }
    return l;                                     // last L that is NOT too long = largest feasible L
}

Generalizing the Pattern

Stop & Think

What did square root and ropes have in common? Say it in one sentence before reading on.

Both times: guess a value m, run a yes/no check(m), and the labels came out as all-0s-then-all-1s (or the mirror). So we search for the flip. Here is the whole loop, drawn once: 

flowchart TD
    S(["l, r = the two sentinels"]) --> E{"is there still a gap?
r - l > 1"}
    E -- "yes" --> A["guess the middle
m = l + (r - l) / 2"]
    A --> B["ask check(m)
if 1: r = m
if 0: l = m"]
    B -- "gap is now half as big" --> E
    E -- "no: l and r are neighbours" --> F(["the flip is between them"])
    style B fill:#ede9fe,stroke:#7c3aed,stroke-width:2px
    style F fill:#dcfce7,stroke:#16a34a,stroke-width:2px

The same template solves any problem with a monotone check. Generic:

// Binary search on the answer -- one template, every time
bool check(long long m) { /* true if m is "good enough" */ }

long long solve(long long lo, long long hi) {
    long long l = lo - 1, r = hi + 1;   // l: known-false side, r: known-true side
    while (r - l > 1) {
        long long m = l + (r - l) / 2;
        if (check(m)) r = m;
        else           l = m;
    }
    return r;   // r = first true. (Return l instead when you want the last false.)
}

The one rule that trips everyone: l or r?

The loop is byte-for-byte identical every time. The only thing that changes is which side you read off when it stops:

Want the first true? → return r

e.g. the smallest rope length that is too long — the first cell where check turns on.

Want the last false? → return l

$\lfloor\sqrt{x}\rfloor$ (last "fits"), and the largest rope length (last "not too long").

Sqrt returned l. Ropes returned l (the largest length that works) — but reading r from the very same run gives the smallest length that fails. Same loop — different read-off.

Your Turn: Koko Eating Bananas

LeetCode 875 · Koko Eating Bananas

Koko loves to eat bananas. There are n piles of bananas; the i-th pile has piles[i] bananas. The guards have gone and will come back in H hours.

Koko decides her eating speed v (bananas per hour). Each hour, she chooses one pile and eats v bananas from it. If that pile has fewer than v bananas left, she eats all of them instead, and will not eat any more bananas during that hour — the rest of the hour is simply wasted, and she only moves to another pile when the next hour starts.

Koko likes to eat slowly, but she still wants to finish all the bananas before the guards return.

Return the minimum integer speed v such that she can eat all the bananas within H hours.

That wasted-time rule is the whole reason a pile of p bananas costs ⌈p / v⌉ whole hours: leftovers never carry over into the next pile.

Worked example — piles [3, 6, 7, 11], guards return in H = 8 hours:

v = 4 → fast enough

3→1h, 6→2h, 7→2h, 11→3h

The pile of 3 is gone in one hour (she eats 3 and idles). The pile of 6 takes 2 hours (4 then 2). The pile of 7 also takes 2 (4 then 3). The pile of 11 takes 3 (4, 4, then 3).

total = 8 hours, and 8 ≤ 8

v = 3 → too slow

3→1h, 6→2h, 7→3h, 11→4h

Eating slower means more hours per pile: the pile of 7 now needs a third hour for its last banana, and the pile of 11 needs a fourth.

total = 10 hours, and 10 > 8

Every speed of 4 or more finishes in time; every speed below 4 does not. So 4 is the smallest speed that works — and that 0…0 1…1 shape is exactly what we search.

You have the template now. Fill in the four pillars yourself before revealing — this is the exam skill.

1. The space — range of v?

From 1 to max(pile) — faster than the biggest pile never helps.

2. The guess — what is m?

A candidate speed v.

3. The check — what does check(v) compute?

Add up the hours each pile needs at speed v — a pile of p bananas takes ⌈p/v⌉ hours (round up). Feasible if the total fits in H: Σ⌈pile/v⌉ ≤ H.

4. The boundary — return l or r?

Slow = infeasible (0), fast = feasible (1). We want the first feasible → return r.

Once you have your check, open the simulator: drag the speed and watch Koko eat each pile hour by hour, then compare the total against H. Same simulator shape as ropes — only the check changed.

The banana piles, eaten hour by hour at speed v
Speed v = 3 bananas/hr
that same v, written as one 0/1 cell

The loop is byte-identical to sqrt and ropes. Only check (now a plain function) and the returned side (r, not l) change:

bool check(long long v, vector<long long>& piles, long long H) {     // true = fast enough (hours ≤ H)
    long long hours = 0;
    for (long long p : piles) hours += (p + v - 1) / v;         // ceil(p / v)
    return hours <= H;
}

long long minSpeed(vector<long long>& piles, long long H, long long maxPile) {
    long long l = 0, r = maxPile + 1;            // lo = 1, hi = maxPile  --  SAME template
    while (r - l > 1) {
        long long m = l + (r - l) / 2;
        if (check(m, piles, H)) r = m;
        else                     l = m;
    }
    return r;                                     // first feasible (fast enough) speed
}

The Landmine: When the Search Lies

A frog must cross a river laid out as a row of cells: * is its start, . is open water it may land on, # is a rock it must avoid, and D is the far bank. It always jumps a fixed size s, landing on s, 2s, 3s, … until it reaches D. One extra rule: it is a small frog, so s can be at most half the path length. Find the smallest s that gets across.

Sample test case

*.#....#.#.D

Twelve cells, numbered 0…11. The frog starts on the * at 0, the far bank D is at 11, and rocks (#) sit at 2, 7, 9. At jump size s it lands on s, 2s, 3s, … — so s = 3 means landing on 3, 6, 9, and 9 is a rock. The half-length rule caps s at 6.

Predict first: "bigger jumps skip more cells, so once a size works, every bigger one does too." That sounds obviously monotone. Watch what actually happens.

Press a jump size and watch the frog hop. Each size is one candidate answer, and check(s) is simply "does it cross?" — 1 = crosses, 0 = lands on a rock:

Sample map *.#....#.#.D
Pick a jump size s
every jump size, written as one 0/1 cell
Looks perfectly safe

The row came out 000111 — all 0s, then all 1s, flipping once. Textbook monotone. So binary search must be safe here. Let's run it and submit.

It returned s = 4, which really is the smallest jump that crosses the sample. Green check, sample passes. Ship it? Here is the hidden test the judge runs:

Hidden map *..#.......D — a single rock, at position 3.

the same 0/1 row, for s = 1…6

See the dip at s = 3? A jump of 3 lands exactly on the rock, even though 2 (smaller) and 4 (larger) skip it. The row reads 010111 — it flips back, so it is not monotone.

Binary search needs a monotone check: all 0s then all 1s, flipping once. On the sample it does, so the search is right. On the hidden test a jump lands exactly on a rock a neighbour skips, so feasibility flips back — and the search confidently returns a working-but-not-smallest answer. Nothing errors; the sample even passed. That is what makes it dangerous.

  • 000111 — one clean flip, monotone, safe to binary-search.
  • 010111 — flips back at s = 3, the search lies (returns 4; the answer was 2).
How to actually prove a check is monotone

Three lines: Assume check(m) is true. Name the reason it passed. Show that reason still holds at m+1 — then labels can never fall back to 0.

On Koko: assume speed v finishes in ≤ H hours. Every pile took ⌈pile/v⌉ hours. At v+1 every ceiling stays equal or drops, so the total is still ≤ H. Feasible stays feasible. The frog check has no such argument — that is the tell.

Binary Search in Your Toolbox

Binary search on an answer is another tool next to the ones you already have:

Sorting Two pointers Greedy Prefix sums Binary search on the answer
The habit to build

On a new problem you almost never start by hunting for a check. You start by asking which tool fits — sorting? two pointers? greedy? … binary search on the answer? So the real habit is two steps:

1 · Guess the tool

Does the problem smell like "pick an answer, then test if it works," with harder-on-one-side behaviour? That shape is your cue to try binary search on the answer.

2 · Then find the check

Only now do you design a monotone check(m) and prove it flips 0→1 once. If you can, you are three lines from a solution.

Reaching for the tool first is what lets you even consider binary search on problems that never mention an array — square roots, ropes, eating speeds.

Practise the habit — name the tool before reading on:

Summary Card

Everything on one screen. Memorise the shape, not the lines — it is the same loop from Section 4.

l = lo - 1, r = hi + 1      // l: known-false side, r: known-true side
while (r - l > 1) {
    m = l + (r - l) / 2     // never overflows
    if (check(m)) r = m      // never m ± 1
    else          l = m
}
return r  // first true  (return l for last false)

1 · Reframe

Not "where is the value" but "where does check flip 0→1".

2 · Monotone or nothing

If the check flips back, the answer is garbage and nothing warns you. Proving monotonicity is the real work.

3 · Guess, don't read

m is a candidate answer; its label is computed by check(m) — no array needed.

4 · Cost

log(range) × cost(check) — the answer range and the work per check are two different sizes.

Binary Search on Fractions

Everything so far searched over integers. But the answer can be a real number — like $\sqrt{2}$. The check is identical (m × m > x); only one thing breaks.

Stop & Think

With real numbers, when do we stop? There is no "r - l == 1" — between any two reals there is always another. So how does the loop ever end?

Here we approximate $\sqrt{2}$. The bracket [l, r] straddles it, and each halving keeps the half that still contains the answer — so more and more leading digits stop changing. They lock in. Halve it and watch:

Approximating √2 — locked digits turn indigo

The digits never all lock — the interval shrinks forever but never reaches zero. So we don't wait for it to vanish; we stop on purpose. The check stays the same plain function as before:

bool check(double m, double x) { return m * m > x; }   // exactly the integer check, now on reals

Two ways to decide when to stop — open each and compare:

Loop A — fixed iteration count (recommended) 
double sqrtFixed(double x) {
    double l = 0, r = max(1.0, x);
    for (int i = 0; i < 100; i++) {   // fixed count -- cannot hang
        double m = (l + r) / 2;
        if (check(m, x)) r = m;
        else             l = m;
    }
    return l;                          // l and r agree to the limit of double (~15-16 digits)
}

100 halvings crush any sane interval past 10⁻¹⁵. It cannot hang, and you never think about tolerances. Note the ceiling: a double carries only ~15–16 significant digits, so after roughly 50–60 halvings l and r become adjacent doubles and the interval stops shrinking — the remaining iterations are free, but they buy you nothing. The √2 simulator below shows exactly this stall.

Loop B — epsilon tolerance 
double sqrtEps(double x) {
    double l = 0, r = max(1.0, x);
    while (r - l > 1e-9) {              // stop once the gap is small enough
        double m = (l + r) / 2;
        if (check(m, x)) r = m;
        else             l = m;
    }
    return l;
}

Reads naturally and is fine for modest ranges. But for huge x the gap between two adjacent doubles can already exceed 1e-9, so it never gets that small and spins forever — see the first trap below. Cap the iterations, or scale the epsilon to the magnitude of x.

Your turn (Codeforces EDU Step 2·E — "Equation")

Find x with $x^2 + \sqrt{x} = c$. It is strictly increasing for $x \ge 0$, so the same fixed loop works — the only new part is a check that returns m*m + sqrt(m) > c. Search x in [0, c].

Bonus: the full rope problem — when L can be any real length Codeforces EDU

Section 3 kept L a whole number. The original Codeforces version lets L be any real length — so it is exactly this section's fixed loop, with the rope check dropped in. Same "too long" test, now on a real L:

bool check(double L, vector<double>& rope, int k) {
    long long pieces = 0;
    for (double a : rope) pieces += (long long)(a / L);   // whole pieces at real length L
    return pieces < k;
}

double largestLength(vector<double>& rope, int k) {
    double l = 0, r = *max_element(rope.begin(), rope.end());
    for (int i = 0; i < 100; i++) {       // fixed loop -- real answer
        double m = (l + r) / 2;
        if (check(m, rope, k)) r = m;        // too long -> shrink
        else                   l = m;        // still fits -> grow
    }
    return l;                              // largest real length that still makes k pieces
}

Only two things changed from Section 3: the type is double, and the integer stop rule r - l > 1 became the fixed loop. The check is untouched.

The traps that bite here

The while (r - l > 1e-9) hang

This is Loop B's failure mode. Near 10¹⁸ two adjacent doubles are already about 128 apart — the gap can never drop below 1e-9, so the loop spins forever. A fixed iteration count sidesteps it entirely. The digit sim above never fully locks for the same reason.

The integer "floor-mid" infinite loop

Back in the integer world, writing while (l < r) { m = (l + r) / 2; if (check(m)) r = m; else l = m; } loops forever when r - l == 1: integer m rounds down to l, and l = m changes nothing. The r - l > 1 form (used all through this session) has no such fixed point.

Comparing floats with ==

Never test m * m == x for reals — rounding means it is almost never exactly equal. Compare against a tolerance, or (better) just run the fixed loop and trust the last l. The problem's error bound (usually 1e-6) tells you how many iterations are plenty.
