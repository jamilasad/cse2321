Section 1

Why we cannot measure in seconds

⏱ 6 min
Your turn

Two students solve the same problem and time their own program, each on their own laptop.

  • The first writes a loop. It finishes in 0.9 seconds.
  • The second writes a formula. It finishes in 1.4 seconds.

Which of the two wrote the better algorithm?

Before you answer — what would you need to know that these two numbers do not tell you?

Those two numbers cannot decide it. They were measured on two different laptops, with two different compilers, with two different sets of programs running in the background — and on whatever input each student happened to try.

Put both programs on one machine and give them a large enough input, and the gap stops being half a second. It becomes seconds against microseconds. The 0.9 against 1.4 was measuring the two machines, not the two ideas.

So we never time the clock. We count operations, and we watch how that count grows as the input grows. That count belongs to the algorithm, and it is the same on every machine on earth.

The clock is unreliable for three reasons:

Different machines

Your laptop and the judge’s server are not the same speed — and you never get to run your code on theirs.

Different languages

The same idea written in C++ and in Python can differ by fifty times without either one being a better algorithm.

Whatever else is running

A browser open behind your editor moves the number. Run the same program twice and you get two answers.

Time complexity = the growth rate of operations as the input size N increases.

We count operations, and we watch the shape of the growth — not the clock.

📌 The one number to carry all semester

A typical judge machine handles about 108 operations per second. Time limits are usually 1 to 2 seconds.

That single fact is what turns a constraint into a verdict. §2 does the arithmetic.

Case study 1

Sum of 1 to N — O(N) versus O(1)

⏱ 11 min
Sum of 1 to NCodeforces

Problem. You are given a single integer N. Print the sum of every whole number from 1 to N.

Input5Output15 1 + 2 + 3 + 4 + 5 = 15.
Input1000000000Output500000000500000000 The worst case the constraint allows — and look at the size of that answer, which turns out to be this section’s second lesson.

Constraint. 1 ≤ N ≤ 109 — and that line is the whole question. 109 is far past what a loop can do inside a time limit.

Open on Codeforces  →

Approach A · the loop

The obvious program, and the one almost everybody writes first. It is correct for every N.

#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;

    long long sum = 0;
    for (int i = 1; i <= n; i++) {
        sum += i;
    }

    cout << sum << endl;
    return 0;
}

Count the operations. The loop body runs once for every value from 1 to N. Everything else in the program is a handful of lines that run once. So the whole cost is the loop: N operations, which is O(N). At the worst the constraint allows, that is 1,000,000,000 additions.

The one sum to do before you write any code

worst-case operations ÷ 108 = seconds

A judge machine gets through roughly 108 operations every second. Dividing by it turns a count of operations into a time you can compare with the limit.

this problem, worst case
1,000,000,000 ÷ 108 = 10 seconds

The limit is 1 to 2 seconds. Approach A is five to ten times too slow — and no amount of tidying the loop body will change that. The verdict was decided by the constraint, not by the code.

Your turn

Approach A needs one step for every number between 1 and N. Ten seconds of them.

Can the same answer be produced in a fixed number of steps — the same number of steps whether N is 10 or 1,000,000,000?

sum = N × (N + 1) / 2. One addition, one multiplication, one division and one assignment — four operations, whatever N is.

Put four into the sum above: 4 ÷ 108 is 40 nanoseconds, and it stays 40 nanoseconds when N is a billion. That is what O(1) means — not “fast”, but does not grow.

Approach B · the formula

Three attempts at writing that one line. All three compile without a warning, and two of them print the wrong answer. Work through them in order — the second one is the mistake people make while fixing the first.

Attempt 1 the formula, written the obvious way
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;

    long long sum = n * (n + 1) / 2;

    cout << sum << endl;
    return 0;
}

It compiles, it runs, and for n = 1000000000 it prints the wrong answer. What does it print, and which part of that line is responsible?

prints−243309312  should be500000000500000000

Look at the type of the multiplication, not the type of sum. n is an int and n + 1 is an int, so C++ works out n * (n + 1) as an int — a 32-bit box whose largest value is 2,147,483,647.

The true product is 1,000,000,001,000,000,000. It does not fit, so it wraps round. The division then happens on the wrapped value, and only after all of that is the result copied into sum. Declaring sum a long long came one step too late.

Notice the tell: adding up positive numbers produced a negative one. That is almost always overflow.

Attempt 2 the fix most people write next
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;

    long long sum = (long long)( n * (n + 1) ) / 2;

    cout << sum << endl;
    return 0;
}

The product is now cast to long long. Does that fix it?

prints−243309312  should be500000000500000000

No. The same wrong answer. The brackets are worked out first, so the overflow has already happened before the cast is reached.

A cast converts a value that has already been calculated. It cannot go back and redo the calculation in a bigger type.

Attempt 3 the one that works
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;

    long long sum = (long long)n * (n + 1) / 2;

    cout << sum << endl;
    return 0;
}

One pair of brackets moved. Why is this one different?

prints500000000500000000  correct✓

(long long)n makes the left operand 64-bit before the multiplication. C++ then promotes n + 1 to match it, and the whole expression is worked out in 64 bits — where 1,000,000,001,000,000,000 fits with room to spare.

Two other ways of writing the same fix, both common: put 1LL * in front of the expression, or simply declare long long n; in the first place, so that every calculation n takes part in is 64-bit from the start.

In C++ the type of a calculation is decided by its operands — never by where the answer is going to be stored.

That one sentence explains all three attempts, and it is why the cast has to be on the left of the *.

Why the answer came out negative

An int is not a smaller version of a big number. It is a row of 32 binary digits, and nothing else. The product needs sixty.

Step through it. The two operands, the product and sum are all drawn on the same 64 columns, so a 32-bit value simply takes the right-hand half — which is where the whole problem lives.

Where the digits actually go

The analogy, in one breath

Multiplying two ints is like pouring water into a small bucket. Once it goes over the brim the water is gone — and tipping what is left into a larger tank will not bring it back.

long long sum is the tank. It was never the bucket.

Case study 2

Prime checking — and the √N idea

⏱ 9 min
Prime checkingCodeforces

Problem. You are given a single integer N. Print YES if it is prime and NO if it is not.

Input97OutputYES Nothing from 2 to 9 divides it, and 10 × 10 is already past 97.
Input1000000007OutputYES The worst case. A large prime has no divisor to find, so the loop never returns early — it runs all the way to the end.

Constraint. N can be as large as 1012 — so the worst case is a prime near a million million, and a loop that walks all the way to N would take hours.

Open on Codeforces  →

Approach A · test every number

The definition of a prime, written out exactly as it reads: try every divisor from 2 upwards.

#include <iostream>
using namespace std;

bool isPrime(long long n) {
    if (n < 2) return false;

    for (long long i = 2; i < n; i++)
        if (n % i == 0) return false;

    return true;
}

int main() {
    long long n;
    cin >> n;

    cout << (isPrime(n) ? "YES" : "NO") << endl;
    return 0;
}

Count the operations. The worst case is a number that is prime, because then the loop never returns early — it runs all the way, about N times. And the constraint allows N to be 1012.

approach A, worst case
1,000,000,000,000 ÷ 108 = 10,000 seconds

Just under three hours — to answer one question about one number. The same arithmetic as §2, and the same verdict: this cannot be the intended solution.

Your turn

Take N = 36. Here is every divisor it has:

123469121836

Nine of them — and the loop above still tests every number from 2 to 35 before it will commit to an answer.

How far do you really have to test before you can be certain there is no divisor at all? Give the number for 36 first, then the rule for any N.

For 36 you can stop at 6. In general you can stop at √N.

Here is the whole argument. Divisors come in pairs: if N = a × b then finding a hands you b for free. And a and b cannot both be larger than √N — if they were, their product would be larger than N. So every pair has at least one member at or below √N.

Test up to √N and you have already met one member of every pair there could be. Finding nothing there means there is nothing above it either.

See it for yourself

Every divisor pair of N, written out. The pairs approach each other from both ends and meet at √N — and everything to the right of the meeting point is a repeat of something on the left.

Approach B · stop at √N

The mathematics says √N. The code should not.

The obvious translation is i <= sqrt(n), and it is the one to unlearn. sqrt returns a double, and a double carries about 15 accurate digits — so for an N near 1012 the value can land a hair below the true root and the loop stops one test too early, which is a wrong answer rather than a slow one.

Write i * i <= n instead. It is exact integer arithmetic, it needs no library, and it says the same thing: keep going while i is still at or below the square root. Keep i a long long so that i * i itself cannot overflow — §2 explains why that matters.

#include <iostream>
using namespace std;

bool isPrime(long long n) {
    if (n < 2) return false;

    for (long long i = 2; i * i <= n; i++)
        if (n % i == 0) return false;

    return true;
}

int main() {
    long long n;
    cin >> n;

    cout << (isPrime(n) ? "YES" : "NO") << endl;
    return 0;
}
approach B, worst case
1,000,000 ÷ 108 = 0.01 seconds

√(1012) is 106, so the loop runs a million times instead of a million million.

10,000 s → 0.01 s

Just under three hours becomes a hundredth of a second — one million times faster, for one changed character. Nothing about the machine changed. Only the number of operations did.

Logarithmic time — O(log N)

⏱ 10 min

The definition, once

Definition — any base

bk = Nmeans the same thing aslogb N = k

The logarithm is the power. logb N is the number you have to raise b to in order to reach N, and b is called the base.

25 = 32log2 32 = 5
210 = 1024log2 1024 = 10
103 = 1000log10 1000 = 3

In computing the base is nearly always 2, because the thing that keeps happening is halving. When you see O(log N) written with no base at all, read it as base 2 — and note that the base would not change the answer anyway, because switching base only multiplies the whole thing by a constant, and Big-O throws constants away.

That is the last time you will need it. You will never compute a logarithm in this course, and there is no calculator in the exam hall. Put the definition away and keep one of the two pictures below instead — they say the same thing, and both are things you can count on your fingers.

Halving — how you will meet it

32 → 16 → 8 → 4 → 2 → 1 — five steps.

Throw away half of what is left, every time, until one thing remains. Binary search is exactly this. A thousand items take ten steps; a million take twenty.

Doubling — how you will count it

1 → 2 → 4 → 8 → 16 → 32 — five steps.

Start at 1 and double until you pass N. This is the one to count with, because doubling in your head is easy and halving a big number is not.

The log column, which is the whole point

Double 1 until you pass the constraint, and count. These are the only five you will meet:

N on the left, log2 N on the right — and the pattern is worth more than the numbers: every thousand-fold jump in N adds ten steps. Not ten times more work. Ten more steps.

What that buys you

A billion items, searched in 30 steps. A million million, in 40. At 108 operations a second, forty operations is 0.0000004 seconds — and it would still be forty if the input were a thousand times larger.

This is why O(log N) is treated as free in practice, and why the first question about any large constraint is “can I halve something?”

Why it matters

For N = one trillion, O(N) needs a trillion steps. O(log N) needs 40.

That is the whole reason binary search, balanced trees and heaps are worth the trouble of learning. For any input you will ever be given, logarithmic is as good as constant.

Nested loops and O(N²)

⏱ 12 min

Read the constraint. It is telling you the answer.

Almost every problem gives you a line like N ≤ 100,000. That single line already decides which solutions are allowed:

O(N) → 100,000 operations → ✅ very fast
O(N²) → (105)² = 1010 operations → ❌ impossible

At 108 operations per second, 1010 ÷ 108 = 100 seconds. The limit is 1–2 seconds.

The constraint, read backwards

Turn it around and the constraint stops being a limit and becomes a hint. For each size, this is the slowest shape that still finishes in about a second — anything faster is fine, anything slower is not.

for (int i=0; i<n; i++)

Half of N² is still N². Cutting the work in two does not change the shape of the growth, and the shape is the only thing Big-O reports.

Why “/2” and “−N” disappear

Multiply the brackets out and the exact count has three parts:

N(N−1)/2=(N²−N)÷2

N² survives

The fastest-growing part. Double N and this quadruples — that is the behaviour the answer is describing.

− N dropped

It grows, but far more slowly. At N = 1,000 it removes one part in a thousand, and the bigger N gets the less it matters.

÷ 2 dropped

A constant scale. It makes the work smaller, never slower — halving 1010 still leaves 5 × 109.

The ratio settles at 0.5 and stays there. It never drifts, never grows. That constant one-half is precisely what Big-O throws away — and throwing it away costs us nothing, because 0.5 × N² still doubles-and-doubles exactly like N² does.

Big-O asks one question: how fast does this grow as N goes to infinity?

It deliberately ignores constants (÷2, ×5) and lower terms (+N, +100), because they do not change whether your solution scales.

❌ The trap

string s = "";
for (int i = 1; i <= N; i++) {
    s = s + to_string(i);      // looks harmless. it is not.
}

There is no visible nested loop. It still runs in O(N²).

Why this is quadratic

s = s + x does not add to the end of s. It builds a whole new string: reserve memory, copy every character already there, add the new ones, throw the old string away. Every round.

The last four rounds of a run with N = 500

i = 497s is 1,380 characters longcopy 1,380, add 3
i = 498s is 1,383 characters longcopy 1,383, add 3
i = 499s is 1,386 characters longcopy 1,386, add 3
i = 500s is 1,389 characters longcopy 1,389, add 3

Four rounds: 12 characters added and 5,538 copied — and each round is worse than the one before it, because the string it has to copy has just grown.

The copying is the cost, and it grows every round. Run it and watch the total, not the string.

Hold Next i and it accelerates — about eight seconds from i = 1 to i = 500. Watch the bar, not the string.

Round 1 copies almost nothing, round 2 copies a little more, and round N copies everything. If each number adds about c characters, the copying across the whole loop adds up to

c×(1 + 2 + 3 + … + N)=c×N(N+1)/2

The c is a constant, so Big-O drops it exactly as §5 dropped the /2. What is left is 1 + 2 + 3 + … + N — the same sum as §2, and the same shape as the nested loop in §5. O(N²), with no nested loop in sight.

✅ The fix — O(N)

string s;
s.reserve(N * 6);          // ask for the memory once
for (int i = 1; i <= N; i++) {

}

Memory is allocated once · nothing is copied repeatedly · appends are O(1) amortised.

s = s + x and s += x look almost identical. One is O(N²) and one is O(N).

Section 7

Space complexity

⏱ 8 min

Same idea, different resource

Time complexity counts operations. Space complexity counts memory — variables and arrays — relative to the input size.

Case study: find the missing number

268 · Missing NumberLeetCode

Problem. You are given an array nums holding n distinct numbers taken from the range 0, 1, …, n. Exactly one number from that range is missing. Return it.

Inputnums = [3, 0, 1]Output2 n = 3, so the range is 0…3. The array holds 0, 1 and 3, so 2 is missing.
Inputnums = [9,6,4,2,3,5,7,0,1]Output8 n = 9, the range is 0…9, and 8 is the only one absent.

Constraints. 1 ≤ n ≤ 104 on LeetCode — but the same question is asked with n up to 109, and that is where the two solutions part company. Both are O(N) in time; only one survives on space.

Open on LeetCode  →

Approach A · tick off what you have seen

The first idea almost everyone has, and it is a good one: keep a box for every possible value, tick the ones that turn up, then look for the box nobody ticked.

int missingNumber(vector<int>& nums) {
    int n = nums.size();
    vector<bool> seen(n + 1, false);

    for (int x : nums) seen[x] = true;

    for (int i = 0; i <= n; i++)
        if (!seen[i]) return i;

    return -1;
}

Time O(N) — two passes, both linear. Space O(N) — and that is the half nobody counts. Step through it with a small case and watch the second row, not the first.

the array you were given, read one element at a time

nums

one box for every value from 0 to n, all false before a single number has been read

seen
memory held, whatever the input9 boxes — one per possible value
—

Nine boxes exist before the loop starts. Press Next.

Now scale the picture up

Nine boxes for n = 8. The same code with n = 1,000,000,000 asks for a billion boxes before it reads anything — and a vector<bool> packs eight of them to a byte, so that is still 125 MB. A typical memory limit is 256 MB, and the array is not the only thing in the program.

The time is fine. The memory is what kills it — and the verdict has its own name: MLE, Memory Limit Exceeded.

Your turn

Approach A allocates memory that grows with N. The numbers themselves are the ordinary ones, 0 to n, with exactly one gone.

Can you find the missing one using only a couple of variables — the same two variables whether n is 8 or a billion?

Approach B · add them all up

Add up the numbers you should have. Add up the numbers you do have. The difference is the one that is gone.

int missingNumber(vector<int>& nums) {
    int n = nums.size();

    long long expected = (long long)n * (n + 1) / 2;
    long long actual = 0;

    for (int x : nums) actual += x;

    return (int)(expected - actual);
}

These two lines are the whole memory footprint. Two long longs — sixteen bytes — and the loop below them adds nothing: x is one int reused every round. Whether n is 8 or a billion, the program holds the same two numbers. That is O(1) space.

Time O(N) — one pass. Space O(1) — two long longs, and that is the entire memory footprint whatever n is.

Two things worth noticing

1. expected is §2’s formula, doing real work — and it carries §2’s cast for exactly §2’s reason. With n = 109 the sum is about 5 × 1017, which is nowhere near fitting in an int.

2. Nothing was traded away. Approach B is not slower, not longer and not harder to read — it simply asks the question differently. The best space savings usually come from a better idea, not from a sacrifice.

Approach B uses two variables, no matter how big N gets. That is what O(1) space means.

And notice the callback to Class 2 — spending memory to save time is the time–space tradeoff. Here we spent none and lost nothing. When that is possible, take it.

🛑 Pop quiz — name the complexity

⏱ 6 min
Code 1
for (int i = 0; i < 2 * N; i++) {
    sum += i;
}
O(N). The loop runs 2N times, but constants are ignored in Big-O. O(2N) simplifies to O(N) — doubling the work does not change how it scales.
Code 2
for (int i = 0; i < N; i++) {
    for (int j = 0; j < 100; j++) {
        sum += i * j;
    }
}
O(N). Nested does not automatically mean squared. The inner loop runs exactly 100 times — a constant that does not depend on N. Total = 100N, and we drop the 100. Look at what the inner loop depends on, not at the indentation.
Code 3
while (N > 1) {
    N = N / 2;
    steps++;
}
O(log N). The input is cut in half every step. That is the signature of a logarithm — the halving picture from Section 4. For N = 1012 this is about 40 steps.
Code 4
string s = "";
for (int i = 1; i <= N; i++)
    s = s + "a";
O(N²) — the trap from Section 6. There is only one visible loop, but s = s + "a" copies the entire string each round: 1 + 2 + 3 + … + N = O(N²). Using s += "a" instead makes it genuinely O(N).

⏱ 2 min
1 Read the constraint first

N ≥ 105 means O(N²) is already dead. Decide that before you write a line, not after the submission times out.

2 Drop constants and smaller terms

O(2N) and O(100N) are O(N). O(N(N−1)/2) is O(N²). Only the fastest-growing part survives.

Real past questions

Copied from the papers

?Why Big O instead of seconds? — Autumn 2025, Q1(a) [1 + 2 marks]
"Explain why Big O notation is preferred over measuring algorithm time in seconds. Find the time complexity of (i) and (ii) on the following graph."

Model answer. Runtime in seconds depends on the machine, the programming language and other processes running at the time, so the same algorithm gives different numbers on different computers. Big O instead measures how the number of operations grows as the input size grows — a property of the algorithm itself, which is the same everywhere.

For the graph part, read the curves against the labelled ones: the steeper the curve, the worse the complexity. The order shown is O(1) < O(log n) < O(n) < O(n²) < O(2ⁿ) < O(n!).
?Time complexity of two functions — Spring 2025, Q1(c) [2 marks]
// (i)
int solve1(int n){
    int i = n, cnt = 0;
    while(i > 0){ i = i / 2; cnt++; }
    return cnt;
}

O(log n). The variable i is halved every round, so the loop runs about log₂n times — the halving pattern from Section 4.

// (ii)
int solve2(int n){
    int cnt = 0;
    for(int i=0; i<n; i++)
        for(int j=1; j<n; j*=2) cnt++;
    return cnt;
}

O(n log n). The outer loop runs n times. The inner loop multiplies j by 2 each round rather than adding 1, so it runs about log₂n times — not n times. n × log n.

⚠ The trap: a nested loop is not automatically O(n²). Always look at how the counter changes.

?Space complexity of a swap — Spring 2024 & Spring 2023, Q1(c) [2 marks]
"What do you mean by space complexity? What is the space complexity of the following functions? Explain." 
void swap(){
    int a, b, temp;
    temp = a; a = b; b = temp;
}

int sum(int a[], int n){
    int i, sum = 0;
    for(i = 0; i < n; i += 2) sum += a[i];
    return sum;
}

Space complexity is the total memory an algorithm needs, measured as a function of the input size.

swap: three integer variables, and that never changes when the input changes → O(1).

sum: only i and sum are created — the array was already given, so it is not extra space → O(1) auxiliary space. Its time is O(n) even with i += 2, because n/2 still grows linearly.

?Worst and average case of the standard algorithms — Spring 2025 & Spring 2024, Q2(d) [1.5 marks]
"Write down the worst case & average case time complexity for: i) Binary search ii) Linear search iii) Bubble Sort."
AlgorithmBestAverageWorst
Binary searchO(1)O(log n)O(log n)
Linear searchO(1)O(n)O(n)
Bubble sortO(n)*O(n²)O(n²)

* Bubble sort is O(n) in the best case only with the early-exit flag that stops when no swap happens in a pass. Without it, it is O(n²) always. Spring 2024 Q2(c) asked for exactly that modification.

✅ The pattern across all four papers

Complexity appears in Question 1 of every single paper, usually twice — once as a definition and once as "read this code and tell me its complexity". It is worth roughly 4 to 5 marks before you reach any data structure at all.

Interview questions

What they will ask

?What is the time complexity of your solution?
Asked after every single problem — the candidate in Class 1 wrote down that it was required with every answer.

Answer in one line, then justify in one line: "O(n log n) time and O(1) extra space — the sort dominates, and I only used a few variables."

Always give both time and space. Giving only time makes it look like you never thought about memory.
?Why do we ignore constants in Big-O?
Because Big-O answers "how does this scale?", not "how many operations exactly?".

O(2n) and O(n) both double their work when the input doubles — they behave the same way. But O(n) and O(n²) do not: doubling the input quadruples the second one. That difference is what decides whether your program finishes, so that is the difference Big-O keeps.

Say the honest caveat too: constants absolutely matter in practice — a 10× constant is real time. They just do not change the class.
?Given N ≤ 10⁵, what complexity do you need?
This is really a test of whether you can read constraints. Work it out out loud:

"10⁵ squared is 10¹⁰, and a judge does about 10⁸ per second, so O(N²) would need ~100 seconds — far over the limit. I need O(N log N) or better."

ConstraintWhat you can afford
N ≤ 10O(N!) or O(2ⁿ) — brute force everything
N ≤ 1,000O(N²) is fine
N ≤ 10⁵O(N log N) or O(N)
N ≤ 10⁹O(log N) or O(1) — or O(√N)

Memorising this table is worth more than any single algorithm.

?Difference between time and space complexity — and which matters more?
Time counts operations as the input grows. Space counts extra memory as the input grows.

Which matters more? "It depends on the limit you are about to break." Usually time is the binding constraint, but the missing-number example from Section 7 is the counter-case: both approaches are O(N) time, and only the O(1)-space one survives when N = 10⁹.

Also mention auxiliary space: the input array itself is not counted — only what you allocate on top of it.
?Can you give an example where an obvious optimisation does not change the complexity?
Perfect place for the Two Sum example from Section 5.

Changing for(j = 0) to for(j = i+1) halves the real work — genuinely twice as fast on a real machine. But it is still O(N²), because N(N−1)/2 still grows like N².

The insight to state: "it made the constant better, not the growth. To actually pass the constraint I need a hash map and O(N)." That sentence shows you understand what Big-O is for.
