Section 3

Now think about what just happened

⏱ 5 min

Your program says cout << x; The machine reaches into 12,884,901,888 boxes and hands back the exact four holding x.

How long did that take? Guess first.

Time to read one variable

~10

nanoseconds

One hundred million reads every second.

You blink in 100,000,000 nanoseconds. In that one blink, your computer could read that variable ten million times.

And it does not search. Out of 12.8 billion boxes it goes straight to the right one, first try, every time.

📌

Hold on to this. It is the whole course.

One read is unbelievably fast. But in Class 1, checking 3 billion Facebook names was 3 billion of these — which is exactly why it took 30 seconds.

Do anything enough times and even unbelievably fast becomes far too slow. That gap is where every data structure lives.

Dig deeper

?Is it really always 10 nanoseconds?
10 ns is the round teaching number. The truth has layers: the CPU keeps small fast caches near itself, so a hit is about 1 ns, while a trip out to main RAM is more like 60–100 ns. Your x is used constantly, so it lives in cache.

Why it matters: data sitting next to each other gets pulled into cache together — one reason contiguous memory beats scattered memory even when the Big-O is identical.
?How does it find the right box without searching?
Because the address is the answer. When the compiler sees int x it decides then and there where x will sit. The finished machine code contains no name "x" — it contains the address.

No lookup, no comparison. The question and the answer are the same number. That is exactly the trick a hash table copies in Segment 10.
?Why is disk so much slower?
RAM is electrical, no moving parts. An SSD is roughly 100,000 ns — ten thousand times slower. A spinning hard disk must physically move an arm: about 10,000,000 ns, a million times slower.

This is why B-trees exist — a structure designed to touch the disk as few times as possible.

Open one box: bits, and where int's range comes from

⏱ 12 min

Inside a box there are no numbers — only 8 tiny switches, each on (1) or off (0). One switch is a bit; eight of them are a byte.

Flip them. The same 8 bits, read three different ways.

Binary
00000000
As unsigned
0
As signed
0
As a char
·

The bits never change. Only the rule you read them with changes.

All 8 on: as unsigned that is 255; as signed it is −1. Same switches, both correct.

Where the range of a type comes from

Forget 32 bits. Start with one sign bit and a few value bits, and list every single combination.

Value bits:

0Sign bit 0 — zero and positives

1Sign bit 1 — the negatives

Read the list and the range falls out

The sign bit splits the list exactly in half. Each half has the same number of patterns, because the value bits do not care what the sign bit is doing.

The top half has to carry zero as well as the positives, so it stops one number lower. That is the whole reason the negative side reaches one further.

Why there is no −0

A wasteful design would let 0|00 mean +0 and 1|00 mean −0 — two patterns for the same value, and one number thrown away.

Real computers use two's complement instead, and put 1|00 to work as the most negative number. Nothing is wasted; every pattern means exactly one value.

Now scale it up

The pattern never changes — only the numbers get bigger.

Total bits4
2348163264

The rule — this is all you ever need

n bits  →  1 for the sign, n−1 for the value  →  range is −2n−1 to 2n−1 − 1

So an int with its 32 bits has 31 value bits: −2,147,483,648 to 2,147,483,647.

You never memorise these numbers. Count the bits and halve it.

Quick check
A short is 2 bytes. What is its biggest positive value?
32,767 = 215 − 1. 2 bytes = 16 bits. One goes to the sign, leaving 15 for the value. Those 15 bits make 215 = 32,768 patterns, and they must cover zero as well — so they run 0 to 32,767.

215 = 32,768 is the count of patterns, not the biggest one; it is the answer people give when they forget zero. 216 − 1 = 65,535 is right for an unsigned short, which spends no bit on a sign.

Two powers are worth knowing by sight: 210 = 1,024 and 215 = 32,768. Everything else is doubling.

int

How a negative number is stored

⏱ 14 min

Positive numbers are easy. 25 in 8 bits is 00011001, because 16 + 8 + 1 = 25.

But there is no minus switch. So how do we store -25?

The idea that does not work

"Let the left bit mean minus." Then 00000000 is +0 and 10000000 is −0. Two different zeros. And 5 + (−5) does not give 0. The machine would need extra rules for every subtraction. Too messy.

What we actually use: two's complement

Three steps. Learn them — this is a guaranteed exam question.

Make a number negative

  1. Write the positive number in binary.
  2. Flip every bit. 0 becomes 1, 1 becomes 0.
  3. Add 1.

Try it yourself. Put in any number from 1 to 127.

1Write in binary—
2Flip every bit—
3Add 1—
✓Result—

Two things this buys us

1. Addition just works

25 + (−25) in binary is 00011001 + 11100111. That equals 100000000. The 9th bit falls off the edge and is thrown away. What is left is 00000000 = zero. The machine needs no special rule for negatives.

2. Only one zero

There is exactly one pattern for 0. No +0 and −0 problem.

How to read a number quickly

Left bit is 0 → the number is positive or zero. Read it normally.
Left bit is 1 → the number is negative. That left bit is called the sign bit.

Why the negative side is one bigger

With 8 bits there are 256 patterns. One of them is used for zero. That leaves 255 to share. Positives get 127, negatives get 128. So the range is −128 to +127, not −127 to +127.

The bug that will cost you marks

Overflow: when the number falls off the edge

⏱ 6 min

An 8-bit number can hold up to 127. What happens if you add 1 to 127?

Press the button and find out. Keep pressing.

120
0 1 1 1 1 0 0 0
8-bit signed number. Keep adding 1.

What happened

127 is 01111111. Add 1 and it becomes 10000000. The left bit turned on — and the left bit means negative. So the answer is −128.

The computer did not crash. It did not warn you. It gave you a wrong answer with total confidence.

Dig deeper

?The same thing kills your Codeforces submissions
An int stops at 2,147,483,647 — about 2 × 109. Look at this very ordinary problem: 
// n numbers, each up to 1,000,000,000. Print the sum.
int n; cin >> n;              // n can be 100,000
int sum = 0;                  // <-- THE BUG
for (int i = 0; i < n; i++) { int x; cin >> x; sum += x; }
cout << sum;
Biggest possible sum: 100,000 × 1,000,000,000 = 1014. An int holds about 2 × 109. Result: Wrong Answer on test 7, silently.

The fix is one word: long long sum = 0;

The habit: before you write int, ask "how big can this get?" If it can pass 2 × 109, use long long.
?The nastier version — it overflows even when the destination is big
int a, b; cin >> a >> b;      // each up to 100,000
long long product = a * b;  // still wrong!
product is a long long — but a * b is computed as int × int first, and that overflows before the result is copied across. Declaring the destination big does not help.

Fix: long long product = (long long)a * b; — cast one side so the multiplication happens in 64 bits.
Quick check
You multiply two ints, each up to 100,000, and store it in an int. What happens?
It overflows. 100,000 × 100,000 = 10,000,000,000 = 1010. An int stops at about 2 × 109. And note option 3: it does not crash. That is what makes this bug so dangerous — you get a number, it just happens to be the wrong one.

A letter is just a small number wearing a costume

⏱ 8 min

There is no "letter" inside your computer. There is only a number. The world agreed on a table that says which number means which letter. That table is called ASCII.

Capitals

'A' = 65  →  'Z' = 90

Small letters

'a' = 97  →  'z' = 122

Digits

'0' = 48  →  '9' = 57

Type anything below. Watch the letters turn into numbers.

Look at the gap

'A' is 65. 'a' is 97. The gap is exactly 32. Always. For every letter.

So changing a capital to a small letter is not a "function". It is just + 32. The computer is doing arithmetic and calling it text.

Section 8

Why 0.1 + 0.2 is not 0.3

⏱ 11 min

Not a joke, and not a bug in your computer. True on every machine on Earth.

You expect

0.3

but you get

The computer says

0.30000000000000004

Why

0.1 cannot be written in binary. Not "hard" — impossible, the same way you cannot write 1⁄3 exactly in decimal.

1 ÷ 3 = 0.3333333… and never stops. Given 10 boxes you write 0.333333333 and lose a little.

In binary 0.1 does the same thing: 0.000110011001100… forever. The computer writes what fits and loses the rest — so what it stores is very slightly more than 0.1. Add two of those errors and you can see it.

How a real number is stored: IEEE-754

The bits are split into three parts, like scientific notation:

value = (−1)sign × 1.mantissa × 2(exponent − bias)

Sign — plus or minus.  Exponent — where the binary point sits.  Mantissa — the actual digits.

TypeTotal bitsSignExponentMantissaBiasReliable digits
float321823127~7
double64111521023~16

See the actual bits

Switch between the two types and type any number.

Try 0.5, then try 0.1

0.5 — the mantissa is all zeros. Stored perfectly, because 0.5 is exactly one half and binary is built from halves.
0.1 — the mantissa is 100110011001…, visibly repeating and then chopped off when the bits run out. That chop is the error.

Now switch to double with 0.1 still typed: the same repeating pattern, just 29 more bits before it gets chopped. More accurate — but still not exact.

The rule. Never break it.

Never use == to compare two floating point numbers.

❌ Wrong

if (a == b)

✅ Right

if (fabs(a - b) < 1e-9)

"If the gap is tiny, call them equal." The tiny number 1e-9 is called epsilon.

💡 The best fix of all

If the problem can be solved with integers, do that. Money? Store paisa as an int, not taka as a double. Averages? Compare a*d with c*b instead of dividing. The fastest way to beat floating point error is to not use floating point.

Dig deeper

?When should I use float instead of double?
Almost never, in this course or in contests. Use double by default.

float gives only ~7 reliable digits, and its errors build up fast. It exists for when you have millions of values and memory or bandwidth genuinely matters — graphics, machine learning, embedded devices.

On Codeforces, float is a trap. It will pass the samples and fail the real tests.
?Why is the mantissa written as "1.something"?
Because in binary every non-zero number can be shifted until it starts with a 1 — just like scientific notation writes 5,300 as 5.3 × 10³.

Since that leading digit is always 1, storing it would waste a bit. So it is not stored at all; the hardware just knows it is there. That is why a 23-bit mantissa actually gives you 24 bits of precision, free.
?What is the bias for?
The exponent has to represent both big numbers (2+50) and tiny ones (2−50), so it needs negatives — but the designers wanted to avoid two's complement here.

The fix: store the exponent as an ordinary unsigned number and subtract a fixed bias when reading it. For float the bias is 127, so a stored 128 means 21. A neat side effect: floats can then be compared as if they were plain integers.

Set A

Mid-term style — with model answers

?1. Represent −25 in 8-bit two's complement form. Show all steps. [3 marks]
Step 1 — write 25 in binary: 25 = 16 + 8 + 1 → 00011001
Step 2 — flip every bit: 11100110
Step 3 — add 1: 11100111

Answer: −25 = 11100111

Check your work: read 11100111 as unsigned = 128+64+32+4+2+1 = 231. Then 231 − 256 = −25. ✓
Marks are given for the three steps, not just the final answer. Always write all three.
?2. What is the range of an 8-bit signed integer? Why is the negative side one larger? [2 marks]
Range: −128 to +127.

8 bits give 28 = 256 different patterns. One pattern is used for zero. That leaves 255 patterns to split between positive and negative. Positives get 127 (1 to 127), negatives get 128 (−1 to −128).

So the range is not symmetric. There is one more negative number than positive.
?3. Why is two's complement used instead of a simple sign bit? [3 marks]
Two reasons.

1. Addition needs no special rule. With two's complement, 25 + (−25) = 00011001 + 11100111 = 1 00000000. The extra 9th bit is discarded, leaving 00000000 = 0. The same circuit adds positives and negatives. With a simple sign bit, the hardware would need to check signs and decide whether to add or subtract.

2. There is only one zero. A simple sign bit gives 00000000 (+0) and 10000000 (−0) — two patterns for the same value, which wastes a pattern and breaks equality checks.
?4. What is ASCII? Give the ASCII values of 'A', 'a' and '0'. [2 marks]
ASCII (American Standard Code for Information Interchange) is an agreed table that maps every character to a number, so that characters can be stored in memory as integers.

'A' = 65  ·  'a' = 97  ·  '0' = 48

Note the gap between a capital and its small letter is always 32.
?5. Explain how a real number is stored using IEEE-754 single precision. [3 marks]
A 32-bit float is divided into three fields:

Sign — 1 bit. 0 means positive, 1 means negative.
Exponent — 8 bits. Stored with a bias of 127. It says where the binary point sits.
Mantissa — 23 bits. The significant digits. A leading 1 is assumed and not stored.

value = (−1)sign × 1.mantissa × 2(exponent − 127)

A 64-bit double uses the same idea with 1 sign bit, 11 exponent bits and 52 mantissa bits.
?6. Why is 0.1 + 0.2 not exactly equal to 0.3? How should floats be compared? [3 marks]
In binary, 0.1 is a repeating fraction — 0.000110011001100... — exactly like 1/3 = 0.3333... in decimal. The mantissa has a fixed number of bits, so the value must be cut off. The number actually stored is very slightly larger than 0.1. The same happens to 0.2. When they are added the two small errors add up and become visible: the result is 0.30000000000000004.

Comparison: never use ==. Instead check that the difference is smaller than a very small value called epsilon:
if (fabs(a - b) < 1e-9)
?7. Differentiate between built-in and abstract data types with examples. [3 marks]
Built-in data type — provided by the language itself. In C: int, float, char, double.

Abstract data type — not provided by the language, so the programmer creates it. Also called a user-defined type. Example: C has no type for a date in dd/mm/yy form, so the programmer defines a Date type using struct or class.

An abstract data type is built using built-in types and other abstract types the programmer has already made.
?8. Define ADT. Why is it called "abstract"? What is abstraction? [3 marks]
An Abstract Data Type is a type whose behaviour is defined by a set of values and a set of operations. It states only what operations are to be performed, not how they will be implemented. It does not specify how the data is organised in memory or which algorithms are used.

It is called abstract because it gives an implementation-independent view.

Abstraction is the process of providing only the essentials and hiding the details.
?9. Explain the time–space tradeoff with an example. [3 marks]
The time–space tradeoff means a program can often be made faster by using more memory, or made to use less memory by accepting more running time.

Example. A company has 100 employees, each with a 5-digit ID used as the primary key. If the ID is used directly as the memory address of the record, a search needs no comparisons at all — it is instant. But a 5-digit ID means addresses from 00000 to 99999, so 100,000 memory locations must be reserved for only 100 records. The saving in time is not worth the cost in space, which is why a hash function is used instead to map the large key set into a small address set.

Set B

Find the bug

Four short programs. Each one is broken because of something in today's class. This is how the topic really tests you — not on paper, but at 2 a.m. when your submission says Wrong Answer.

?Bug 1 — n numbers, each up to 1,000,000,000. Print the sum. Fails on test 7.
int n; cin >> n;
int sum = 0;
for (int i = 0; i < n; i++) { int x; cin >> x; sum += x; }
cout << sum;
The bug: sum is an int. With n up to 105 and each x up to 109, the sum can reach 1014. An int stops at about 2 × 109.
The fix: long long sum = 0;
Note the individual x values are fine as int — only the total overflows.
?Bug 2 — count how many times each letter appears. Crashes.
int count[26] = {0};
for (char c : s)
    count[c]++;
The bug: c is the ASCII value. For 'a' that is 97, so the code writes to count[97] in an array of size 26. That is out of bounds.
The fix: count[c - 'a']++; — subtracting 'a' shifts the range from 97–122 down to 0–25.
?Bug 3 — check if the average is exactly 2.5. Prints nothing.
double avg = sum / (double)n;
if (avg == 2.5) cout << "yes";
The bug: == on a double. The division may produce 2.4999999999999996 or 2.5000000000000004, and neither equals 2.5.
The fix: if (fabs(avg - 2.5) < 1e-9)
The better fix: avoid the division entirely — check if (2 * sum == 5 * n) using integers. No floating point, no error, no epsilon.
?Bug 4 — multiply two numbers, each up to 105. Gives a negative answer.
int a, b; cin >> a >> b;
long long product = a * b;
cout << product;
The bug: this one is nasty. product is a long long — but a * b is calculated as int × int first, and that multiplication overflows before the result is copied into the long long. Declaring the destination big does not help.
The fix: long long product = (long long)a * b; — cast one side first, so the multiplication itself is done in 64 bits.
This exact bug costs students marks in contests every week. Look for it whenever you see a long long being assigned the product of two ints.
